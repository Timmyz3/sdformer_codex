# Local5 EREP 防聚合自报三层账本

> 2026-08-10 语义更新：本文首次版本把 Acc32 miter 摘要写在每个 input-head
> 行中。正式 v4 合同已修正为每个 window 一份 miter 摘要，因为可比较的 Acc32
> 边界是所有 input head 累加完成后的最终输出。当前实现与裁决见
> `docs/310_Local5_EREP正式Archive内容重放合同_20260810.md`。

## 1. 问题

旧 `local5_erep_statistics_v4.py` 的 `_validate_rows()` 只比较两组同源字段：

```text
admitted_rows.c0..c4 == command_ledger.c0..c4
```

如果未来 adapter 同时把两边写错，两个 JSON 仍可彼此一致。这只能证明“复制正确”，
不能证明 C0--C4 来自 RTL phase 和资源调度，是 formal G0 的防聚合自报 P0。

## 2. 三层合同

新增 `scripts/local5_erep_ledger_replay_v4.py`，将证据分成三层。

### 2.1 Head phase ledger

`head_phase_ledger.json` 的每个 input head 只含：

- sample/stage/block/window/input-head 身份；
- epoch record 数；
- fill、每 output tile direct、每 output tile execute 的 phase duration；
- phase 内各 1RW/FIFO/Acc resource 的精确 `(cycle, transaction identity)`；
- RTL trace SHA。Acc32 miter SHA 与 mismatch count 属于 window 行，不属于 head 行。

公共 window 行保存 H 个 output tile 的 prepare/drain phase。head ledger schema 中不允许
出现 C0、C1、C2、C3 或 C4，因此 adapter 不能在最底层偷带候选结论。

每个 phase 的 `phase_event_sha256` 由 duration 与 resource-event map 重新计算；cycle
必须严格递增、唯一且位于 phase 内。fill/execute 的 relation、epoch-slot、FIFO 命令数
必须与 epoch record 数一致，同一 record identity 的跨资源顺序必须完全一致，Acc32
mismatch 必须为 0。

### 2.2 Window schedule ledger

独立重放器把 phase ledger 解码回冻结的 `WindowCommandWork`，调用现有：

```text
local5_erep_command_schedule_v4.py
local5_erep_capacity_baselines_v4.py
```

重算 C0 direct、C1 reuse-only、C2 overlap-only、C3 EREP-S2 和 C4 relaxed oracle。
每候选记录 tail cycle、event count、event-ledger SHA、resource event count、epoch traffic、
context/slot 数；既有 scheduler 对所有资源执行无重叠审计。

### 2.3 Command ledger

统计器消费的逐窗摘要由重放器生成，包含 C0--C4、window-schedule SHA 和自身 canonical
SHA。`admitted_rows.command_ledger_sha256` 必须等于重放结果，而不是接受 adapter
任意给出的 digest。

正式统计入口还要求 admission receipt 同时绑定 head、window、command 三个文件的
字节 SHA，并要求 head ledger 的 manifest/projection SHA 与正式输入一致。

## 3. Mutation 证据

新增 `tests/test_local5_erep_ledger_replay_v4.py`，当前覆盖：

1. head ledger 不含候选 scalar，但能重放全部 C0--C4；
2. 同时修改 window 和 command 的 C3，并重算两层 digest，仍被 phase replay 拒绝；
3. 修改底层 direct phase duration会真实改变 C0，旧摘要随即失败；
4. phase digest 错误、同资源重复 cycle、非零 Acc32 mismatch 均 fail closed；
5. event identity 与 cycle 对应关系交换会改变 ledger，并因跨资源 identity 顺序失败；
6. `84` 改成 `84.0` 不能利用 Python 宽松相等绕过 canonical JSON 比较；
7. 单窗口 synthetic ledger 不能进入要求 1200 window/13800 head 的 formal 路径。

与既有 schedule、capacity、statistics 联合回归：

```text
38/38 PASS
```

固定 runtime 为 `/opt/conda/bin/python3.11`、Python 3.11.9、NumPy 2.1.1。默认系统
Python 不满足 runtime receipt 时先拒绝，这是正式门禁而非测试失败。

## 5. 尚未关闭的边界

本轮没有生成正式 `head_phase_ledger.json`，因为 GPU producer 尚未给出 13800-group
manifest，OUT_DIM32 正式 RTL replay 也未执行。phase 中的 RTL trace SHA 与 Acc32
miter SHA 只有在未来 receipt 同时绑定原始 trace archive 后才构成正式身份链。当前
schema 与统计器已经冻结 `rtl_trace_archive.npz`、`acc32_miter_archive.npz` 的 basename
和文件 SHA 交叉绑定；这两个正式文件尚未生成，所以 formal G0 继续 fail closed。

C1--C4 仍是 `[rtl校准]+[模型]`，不是候选 RTL。没有 EREP wrapper/filelist、没有
真实 `[prof]` 性能结果、没有 DC/STA/SAIF/PPA。只有正式 producer、OUT_DIM32
miter、三层账本和独立复审全部通过后，才允许 formal G0 admission。
