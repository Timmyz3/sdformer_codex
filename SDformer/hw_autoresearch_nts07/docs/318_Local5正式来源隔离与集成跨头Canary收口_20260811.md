> 日期：2026-08-11

## 1. 本轮解决的问题

Grok 交接时，正式 joint-head profile 已完成，但 Gate C 仍缺少三段来源隔离：

1. 软件 expected；
2. DUT actual；
3. 不读取原 profile 的只读 merge。

本轮没有实现 EREP 候选架构，而是先回答两个正确性问题：

- 单 head 的 H×H partial projection 能否与独立软件金参考一致；
- 真实 score/Shiftmax5、relation transpose、term、projection 和跨 head Acc32
  能否在同一个集成 DUT 内闭合。

## 3. 第一层：来源隔离 partial canary

最终整改包：

```text

```

坐标固定为：


### 3.1 三条独立路径

- 软件 expected 直接消费 producer 的 destination-major `item_*`：
  `destination, gate, lane, multiplicity`，不使用 descriptor 方向映射；

  `+NO_ACC_CHECK` 下不加载 `expected_acc.memh`；
- merge 只读取 task plan、expected、actual 和 receipt，不读取原 profile。

## 4. 第二层：集成 cross-head DUT canary

最终包：

```text
results/local5_erep_integrated_cross_head_canary_v4_final_20260811
```

### 4.1 实际数据流

```text
正式 descriptor
  -> 独立反演真实 Q / 邻域 K / invalid mask
  -> qfit_local5_score_leaf
       Q7 alpha-XNOR score
       masked integer Shiftmax5 Q1.7
  -> relation transpose
  -> source-major gate/lane term
  -> theta-folded dyadic INT8 projection weight
  -> qfit_local5_cross_head_tile_executor
       head 0 partial
       head 1 RMW accumulate
       head 2 RMW accumulate
  -> tile-major final Acc32
```

软件 expected 与这条 actual 路径相互独立：expected 走 producer destination-major
`item_*`，actual 走 descriptor 到 Q/K 的反演并重新计算 score/Shiftmax5。

### 4.2 数值结果

| 指标 | 结果 |
|---|---:|
| input head | 3 |
| output tile | 3 |
| checkpoint INT8 weight | 9,216 |
| final Acc32 / simulator | 43,200 |
| Icarus mismatch | 0 |
| Verilator mismatch | 0 |
| cross-simulator raw SHA | 相同 |
| 固定回归 cycle | 695,572 |

`695,572` 只是在固定 transaction-indexed service 下的回归延迟，不能写成 EREP、
full encoder 或部署性能。

### 4.3 Provenance 整改

第一次独立复审为 `3/5 Major Revision`，P1 是两个传递 helper 没有进入源码包。
整改后：

- vector manifest 绑定 generator、两个 helper 与 NumPy `1.26.4`；
- helper 进入 pycompile、source SHA 和确定性 source bundle；
- merge 复验 executable/tool SHA 和关键编译/运行参数；
- result SHA 直接包含 Icarus/Verilator executable；
- PASS 必须严格唯一；
- 增加 helper SHA、NumPy 版本、executable/tool SHA、命令参数和重复 PASS 的
  fail-closed 负测。

第二次独立复审对整改包给出 `4/5 Accept`。最终 `v4` 另外把 TB 的 head 数和
output tile 数参数化，并用 combined-input 路径重跑 H=3；该变化只用于验证设施，
不是生产 RTL 创新。随后已完成 H=6/12/24 分层 smoke，详见
`docs/319_Local5四Stage集成跨头Canary与Formal执行预算_20260811.md`。

## 6. 正式档案预算

结果：

```text
results/local5_formal_archive_capacity_budget_20260811/budget.json
```

正式 workload：

| 项 | 数量 |
|---|---:|
| joint window | 1,200 |
| input-head group | 13,800 |
| H×H task | 210,600 |
| final Acc32 | 198,720,000 |
| 若物化全部 partial Acc32 | 3,032,640,000 |

存储预算：

- 一份 final Acc32：`0.740 GiB`；
- expected + 一份 Verilator actual：`1.481 GiB`；
- expected + 两份 actual：`2.221 GiB`；
- 若物化一份全部 partial：`11.297 GiB`。

所以正式 archive 只允许保存 `output_tile -> source -> out` 的 final Acc32，不保存
3.03B 个中间 partial。

运行探针：同一 H=3 窗口 Verilator 为 `3.04 s`，Icarus 为 `54.50 s`。按 H×H
任务数保守外推：

- 全量 Verilator：约 `19.76 h`；
- 全量 Icarus：约 `354.25 h`。

这些值是 `[rtl校准模型]`，不是全量实测。正式执行建议：

1. Verilator 跑全量 100 个 sample shard，可断点续跑；
2. Icarus 只做 stage-stratified cross-simulator canary；
3. 每个 shard 独立 expected/actual/miter/SHA，最后只读汇总 admission；
4. 任一 mismatch 或 shard 缺失时 G0 保持 DENY。
