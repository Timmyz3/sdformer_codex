# DATE 审稿人视角：硬件创新与工作量差距评估

## 一、评审角色与证据范围

本报告由独立 subagent 以 DATE 硬件架构审稿人角色完成首轮评审，再由主 agent 对照仓库中的 RTL、profiling、回放、综合交付和系统模型进行交叉核验。

评审只承认以下证据边界：

| 等级 | 本项目可用证据 | 可以支持的结论 |
|---|---|---|
| `[prof]` | H67 profile100、ordered workload 统计 | workload 特征与架构动机 |
| `[RTL]` | Icarus/Verilator/SVA、整数金参考、Yosys LEC | 已实现模块的功能和结构正确性 |
| `[模型]` | cycle ledger、full-encoder budget、DSE | 候选趋势与设计空间，不是实测性能 |
| `[PPA]` | 当前缺失目标库 DC/STA、SRAM macro、mapped SAIF | 不能给出面积、功耗、频率和 EDP 结论 |

DATE 官方征稿范围明确覆盖 IC/SoC、新型硬件架构、AI 应用架构以及设计方法与工具。因而本报告重点检查：架构新颖性、系统边界、设计方法、硬件实现可信度和公平实验，而不是只检查 RTL 是否能仿真。参考：[DATE Call for Papers](https://www.date-conference.com/call-for-papers)、[DATE TPC](https://www.date-conference.com/tpc)。

## 二、总体审稿结论

### 2.1 当前判定

| 项目 | 结论 |
|---|---|
| 推荐意见 | **Reject** |
| 综合评分 | **2/5** |
| 当前接收概率估计 | **约 8%**，仅为审稿风险判断，不是会议统计预测 |
| 审稿信心 | 高 |
| 当前硬件定位 | 经过较严格验证的单 context 稀疏投影执行 slice |
| 尚不能使用的定位 | 完整 H67 encoder accelerator 或已签核 ASIC |

严格结论如下：

> 当前工作量足以证明一个有价值的微架构原型，但创新呈现、系统完整度、芯片级实验和软硬件闭环尚未达到 DATE 硬件论文的接收标准。最先需要补的不是更多控制 RTL，而是真实 bit trace、公平基线消融和目标工艺 PPA。

### 2.2 分项评分

| 维度 | 评分 | 审稿意见 |
|---|---:|---|
| 问题重要性 | 3.5/5 | 事件光流、稀疏 SNN/Transformer 和低功耗推理有明确价值 |
| workload 动机 | 4/5 | profile100 已揭示 K-zero、pair-empty 和 final-gate 等价类特征 |
| 架构新颖性 | 2/5 | 各机制单看接近常规 output-stationary、cache promotion 和多格式共享后端 |
| 架构完整度 | 1.5/5 | 当前主要是 projection slice，未覆盖完整 encoder 数据流和存储系统 |
| RTL 可信度 | 3.5/5 | 单 context 顶层、断言、默认规模回放和开放 LEC 较扎实 |
| 实验完整度 | 1.5/5 | 缺真实权重/激活回放、同约束基线、消融和芯片 PPA |
| 软硬件协同 | 2/5 | 目前更像 workload-driven specialization，尚未冻结部署数值合同 |
| 可复现性 | 3/5 | 脚本、证据等级和复现入口较清晰，但关键 PPA 环境缺失 |

## 三、当前工作的真实优势

### 3.1 workload 证据不是凭空假设

H67 profile100 已给出可用于架构设计的统计：

| 指标 | H67 结果 | 硬件意义 |
|---|---:|---|
| token K-zero | 约 88.68% | 支持 metadata-first、K-zero exact 路径和 SCS |
| pair empty | 约 73.99% | 支持精确空 pair issue，不需要近似剪枝 |
| pair motion-zero | 约 83.21% | 支持 Motion-XOR 支路 operand isolation |
| final-gate 乘积 work-item 减少 | 约 82.49% | 支持 final-gate 等价类投影合并 |
| gate 活跃 class p95/max | 3/6 | 支持 SLOTS=4 主配置和有界 fallback |

这些数据能证明“为什么值得做”，但不能直接证明“做完后有多少能效收益”。

### 3.2 已有 RTL 具有实际工程深度

当前已实现并验证的内容包括：

- Resident、IPD32W、RAW41 三种表示的实际 decoder；
- 共享 TDR、多播和 AccTile 投影后端；
- output-tile 外层、input-head 内层的 replay 调度；
- 首次 IPD miss 自动回填，后续 output tile resident replay；
- payload tag 与 execution tag、PLAN/COMMIT 原子提交；
- last-use 释放、整 context 有界 abort/flush；
- 默认 `T162 × L32 × H24 × O24` 的 trace-shaped 顶层回放；
- Icarus、Verilator、SVA、Yosys 综合可读和开放结构 LEC。

默认规模回放完成 576 个 session、529 次 resident hit、30,960 个 projection term 和 3,888 个 final token，构造整数参考零 mismatch。这些证据说明实现不是玩具级组合逻辑。

### 3.3 证据边界较诚实

现有文档已经明确区分 RTL 活动、结构综合、性能模型和缺失的目标库 PPA。这一点有助于避免论文中过度声明，也降低后续审阅返工。

## 四、主要拒稿原因

### 4.1 论文架构主线仍有漂移

早期文档以 DP-TME、LR-HTT、CCSP、full-encoder HIT-Flow 为主要叙事；最新实现则集中于 GateStack projection slice。审稿人会追问：

1. 论文究竟提出完整 encoder 加速器，还是 final-gate 稀疏投影引擎？
2. Motion-XOR、SCS、ATLIF、skip/residual 与 GateStack 的硬件边界是什么？
3. 早期贡献若不在最终 RTL/PPA 中，为何仍出现在贡献列表？

投稿前必须冻结一条主线，未实现的旧贡献只能放在算法背景或未来工作中。

### 4.2 三项现有机制尚不能独立撑起架构新颖性

当前三项机制分别容易被归类为：

- head-stacked output-tile-stationary：loop interchange 和 output-stationary 的 workload 适配；
- decode-once promotion：descriptor cache fill、memoization 或 parser 结果驻留；
- representation-heterogeneous compute-unified：多格式前端共享统一执行后端。

这些机制有价值，也已经落入 RTL，但如果拆成三条“首次提出”，容易被审稿人判断为常规技术组合。当前更可辩护的单一架构贡献是：

> **面向 final-gate 等价类的、容量安全且跨 output tile 驻留的精确稀疏投影数据流。**

IPD32W/RAW41 fallback、decode-once promotion 和 output-tile-stationary loop order 应作为这一核心数据流的三个协同机制，而不是三个互不相干的创新。

### 4.3 当前不是完整 encoder accelerator

当前单 context execution top 尚未集成：

- H67 Motion-XOR 与 SCS attention 在线 builder；
- 真实权重 SRAM、bias、requant 和最终定点输出；
- 93 个执行 ATLIF 节点的时间复用 lane cluster；
- S0/S1/S2 residual/skip SRAM 和端口仲裁；
- stage 间张量布局、投影、下采样和外存搬运；
- 双 context build/execute 重叠；
- 整 encoder descriptor scheduler 和系统带宽控制。

因此目前只能声称“projection execution slice”，不能声称“full encoder implemented”。如果论文坚持完整加速器定位，以上边界至少要进入可执行系统模型，并有关键路径 RTL/PPA 支撑。

### 4.4 回放不是网络真实 bit trace

当前默认规模测试只从 `sample0/S3.B0/window0` 继承 head 顺序、term/event/class 数量等统计形状；gate、lane、token payload 是确定性构造，测试权重为常数 `8'sd1`。

因此它可以证明：

- 控制协议和容量选择正确；
- resident/IPD/RAW 混合执行正确；
- 构造整数数据与参考模型一致；
- 生命周期和 payload 读取计数成立。

但它不能证明：

- H67 真实激活逐 bit 等价；
- 真实权重分布下的 accumulator、饱和与 requant 正确；
- 当前活动因子可以代表门级功耗；
- 单窗口结果代表四个 stage 的均值和尾延迟。

### 4.5 缺少可投稿的目标工艺 PPA

当前开放综合得到 3,982 个层次 cell、12 个逻辑 memory、43 个 `$mul`，开放 LEC 4,559/4,559 compare point 通过。这些结果只能证明结构可综合和开放网表等价。

仍缺少：

- 目标标准单元 `.db`、PVT 和 operating condition；
- SRAM compiler macro、真实端口、面积舍入和读写功耗；
- DC/Genus 的 WNS、TNS、面积、transition、fanout 报告；
- mapped netlist + SDF/门级活动；
- mapped SAIF 注释率、动态功耗、漏电和时钟树假设；
- netlist Formality/LEC；
- 布线拥塞或至少 physical-aware synthesis。

没有这些结果，论文不能给出面积、功耗、频率、能量或 EDP 主表。

### 4.6 缺少公平硬件基线与机制消融

当前 `43.25%` 是一个 trace-shaped 窗口中的 payload word 减少，不是能耗降低。模型中的 `1.400×` 又依赖双 context 和 85% delivery efficiency，而当前 RTL 是单 context。

必须在相同接口、位宽、lane 数、SRAM 容量、目标频率和工具约束下实现至少以下基线：

| 基线/消融 | 要回答的问题 |
|---|---|
| Direct/RAW41-only | 等价类压缩与 IPD 是否值得 |
| IPD32W、无 residency | decode-once promotion 的独立收益 |
| Depth0/64/80 | 驻留容量与命中、面积、功耗的拐点 |
| head-major partial-sum spill | output-tile-stationary 是否真正减少流量和周期 |
| 分离多格式后端 | unified backend 是否节省面积且不损失吞吐 |
| single/dual context | 重叠收益是否抵消端口冲突和控制开销 |
| 无 operand isolation | 真实切换和功耗优化来自哪里 |

### 4.7 系统吞吐闭环尚未成立

现有 full-encoder 模型中，列出的最强配置在保护系数后约为 22.43 FPS，未达到 30 FPS，且还没有完整计入所有系统开销。投稿时有两种诚实选择：

1. 通过并行度、重叠、存储端口和物理频率联合设计达到目标；
2. 撤销 30 FPS claim，改为报告明确工况下的 latency/energy Pareto。

不能继续把模型理想吞吐写成已实现实时性能。

### 4.8 软硬件协同尚未形成闭环

H67 已有较好的 AEE、AAE 和 spike 结果，但 GateStack 当前主要利用 final-gate 重复和稀疏分布，尚未证明以下合同已经由训练和部署共同冻结：

- 权重、bias、accumulator、gate 和 requant 位宽；
- 饱和、舍入、负数右移和 overflow 语义；
- residual/skip 的多 bit 数据格式；
- RTL-exact 模型在 valid825 上的精度；
- 不同表示路径对最终网络输出严格一致。

因此当前应表述为“真实 workload 驱动的硬件特化”，还不能强称完整算法-硬件协同设计。

## 五、逐项贡献审稿判断

| 候选贡献 | 实现状态 | 新颖性判断 | 投稿位置建议 |
|---|---|---|---|
| Head-stacked output-tile-stationary replay | `[RTL]` 成立 | 单独较弱，接近常规 output-stationary/loop interchange | 核心数据流的调度机制 |
| Decode-once descriptor promotion | `[RTL]` 成立 | 当前最清晰的微架构机制，但接近 cache promotion | 核心数据流的跨 tile 驻留机制 |
| Representation-heterogeneous, compute-unified | `[RTL]` 成立 | 三者中最有潜力，需证明比 RAW-only、分离后端更优 | 核心数据流的无损 fallback 与共享执行机制 |
| PLAN/COMMIT 双 tag | `[RTL]` 成立 | 主要是正确性和可实现性设计 | 实现细节或可靠控制贡献 |
| Last-use 分层生命周期 | `[RTL]` 部分成立 | 有工程价值，但单独不构成主创新 | 支撑双 context 和容量证明 |
| SCS/Shiftmax 占用类 | 叶级 RTL/模型存在 | 是算子微架构，不宜作为整篇唯一架构贡献 | attention 后端子模块 |
| H67 Motion-XOR 定点通路 | 算法/叶级路径 | 属于软硬件协同或算术优化 | 算法-硬件接口贡献 |

## 六、工作量是否达到 DATE 水平

### 6.1 已经完成的工作量

从工程角度，当前工作量不低：profile、数据格式、多个 decoder、共享后端、复杂控制、默认规模回放、断言、开放综合与 LEC 都已形成。问题不在于 RTL 行数，而在于论文需要的证据分布不均衡：控制与功能验证较多，公平评估与芯片级结果太少。

### 6.2 审稿人会认为缺失的工作量

| 类别 | 当前状态 | DATE 投稿所需状态 |
|---|---|---|
| 算法质量 | H67 full30/valid825 有结果 | 加入 RTL-exact 定点部署精度 |
| workload | profile100 较强 | 四 stage 真实 bit trace 与分位数 |
| 微架构 | 单 context projection slice 较完整 | 冻结主贡献并补公平 baseline |
| 系统架构 | 主要为模型与边界文档 | encoder 数据流、存储、调度和 Amdahl 闭环 |
| RTL 验证 | 较强 | 加真实权重/激活、长回归和 netlist 验证 |
| PPA | 无目标库结果 | DC/STA/SRAM/SAIF/LEC 完整主表 |
| 消融 | 主要是模型 | 同约束 RTL/综合消融 |
| 文献差异 | 已有映射 | 对最接近工作的机制级对照和不可替代性说明 |

所以当前是“原型工作量已经存在，投稿工作量没有闭环”，不是简单地再写若干 RTL 文件即可解决。

## 七、投稿前补强优先级

### P0：缺一项都存在直接拒稿风险

1. 导出 H67 四个 stage 的真实 gate/lane/token 位图，并保留顺序、窗口和 stage 标识。
2. 使用真实量化权重、bias、饱和与 requant 做 RTL 回放和软件 bit-exact 对照。
3. 实现 Direct/RAW41-only、IPD-no-residency、head-major spill 三个同接口基线。
4. 完成 Depth0/64/80、IPD/RAW、GateStack 开关和 single/dual context 消融。
5. 在同一目标库和约束下完成 DC/STA、SRAM macro、mapped SAIF 功耗及 netlist LEC。
6. 冻结累加、舍入、饱和、requant、residual/skip 数值合同，报告 valid825 部署精度。
7. 给出整 encoder 的周期、外存字节、片上存储、面积与能量分解，解决或撤销 30 FPS claim。

### P1：决定论文是否有竞争力

1. 实现双 context，并测量真实端口冲突、FIFO 占用和重叠效率。
2. 分 stage 报告收益，尤其解释模型收益较弱的 stage1。
3. 用真实 trace 报告 multicast efficiency、bank conflict、p50/p95/p99 latency 和最坏情况。
4. 实现 projection lane operand isolation、空 destination 阻断和 AccTile bank enable，并用 mapped SAIF 消融。
5. 对比统一后端、分离双路径后端和普通 streaming fusion。
6. 与近邻工作按相同或归一化的工艺、频率、精度、任务边界比较，明确哪些数字不能直接横比。

### P2：增强完整度但不是当前第一阻塞

1. 细粒度 abort 恢复，避免整 context 清空健康 slot/cache。
2. reset、异常、随机 backpressure 和长时间稳定性回归。
3. DFT、UPF、clock-gating cell 与 CDC/RDC 签核。
4. FPGA 原型或 physical-aware synthesis/布局拥塞结果。

## 八、建议冻结的论文主线

不建议继续把所有历史机制平铺为并列创新。更紧凑、可验证的 DATE 叙事如下：

### 8.1 一个核心架构贡献

**GateStack：面向 all-binary 事件光流 final-gate 等价类的容量安全跨 tile 驻留投影数据流。**

核心耦合关系：

```text
真实 final-gate 等价类
        |
        v
IPD32W compact representation --容量越界--> RAW41 exact fallback
        |
        v
首次解码同流 promotion --> 跨 output tile descriptor residency
        |
        v
output-tile-stationary/head-stacked replay
        |
        v
统一 TDR + multicast + AccTile + operand isolation
```

该组合的论文价值必须由三个对照证明：

- 相对 direct/head-major 的数据移动和周期收益；
- 相对无 residency 的 decode/payload/能量收益；
- 相对多后端实现的面积、吞吐和控制收益。

### 8.2 一个软硬件协同贡献

利用 H67 all-binary、Motion-XOR 和 final Q1.7 gate 的真实分布，冻结等价类键、容量阈值和无损 fallback；用部署量化模型证明网络精度不因表示和数据流变化而改变。

### 8.3 一个系统实现贡献

将 SCS attention、GateStack projection、ATLIF 时间复用执行和 skip/residual 存储纳入统一 encoder schedule，给出完整数据移动、吞吐和能量分账。关键模块可以重点 RTL，非关键控制可以行为模型，但系统口径必须闭合。

## 九、目前禁止使用的论文 claim

- “完整 HIT-Flow/full encoder 已实现。”
- “达到 30 FPS”或“满足 500 MHz 时序。”
- “实测加速 1.400×。”
- “节能 43.25%。”该数字当前只是单个构造窗口的 payload-word 减少。
- “89.84% projection 功耗。”该数字是 RTL toggle 占比，不是功耗。
- “真实 H67 网络逐 bit RTL 等价。”
- “已完成 DC/LEC 签核。”目前只有 DC 交付准备和 Yosys 开放 LEC。
- “Depth=80 命中率 RTL 实测 99.9826%。”该命中率属于 profile/模型口径。
- “IPD32W 减少 86.44% 物理 SRAM 容量。”没有 macro 舍入与 PPA 前不能这样表述。
- “三项机制均为首次提出。”必须完成最近工作检索和机制级差异论证。

当前可以使用的克制表述：

- 单 context projection execution slice 已完成 RTL 集成；
- 默认规模 trace-shaped 回放整数结果零 mismatch；
- Resident/IPD32W/RAW41 三种路径共享投影后端；
- Yosys 开放结构综合和 RTL-to-structural LEC 通过；
- 在一个构造窗口中，descriptor residency 将 payload 读取 word 数降低 43.25%；
- 目标库 PPA 和真实网络 bit-trace 回放仍待完成。

## 十、建议的评审问题清单

投稿前应能用表格和图直接回答以下问题：

1. 与最接近的 compressed sparse attention/projection、output-stationary 和 descriptor cache 工作相比，GateStack 哪个耦合机制不可由常规组合直接得到？
2. 为什么 final-gate 等价类必须与跨 output tile residency 一起设计？
3. IPD32W 越界时 RAW41 fallback 的周期、面积和尾延迟代价是多少？
4. 为什么统一后端优于 dense/sparse 双后端？其面积、利用率和吞吐交叉点在哪里？
5. 四个 stage 中分别节省了多少外存、片上 SRAM、乘法活动和周期？
6. 真实量化模型与 RTL 的 bit-exact 精度是否保持 H67 ep19 结果？
7. GateStack 占整 encoder 面积、功耗和帧延迟多少？Amdahl 上限是多少？
8. SRAM macro、bank、端口和互连是否在目标频率下可实现？
9. 论文中的每个 speedup/energy 数字是 `[RTL]`、`[模型]` 还是 `[PPA]`？

## 十一、下一阶段执行顺序

```text
P0-1 真实四 stage bit trace + 真实量化权重/偏置
  -> P0-2 Direct / no-residency / head-major 同接口基线
  -> P0-3 bit-exact RTL 回放与机制消融
  -> P0-4 目标库 DC + SRAM macro + mapped SAIF + netlist LEC
  -> P0-5 full-encoder 周期/带宽/面积/能量闭环
  -> P1 双 context、operand isolation 与分 stage 优化
  -> 重新进行一次独立 DATE 审稿
```

不应先继续扩写新的架构名词。只有当真实 trace、基线和 PPA 证明现有核心耦合确实带来净收益后，再决定是否增加双 context 或更复杂互连。

## 十二、最终判断

现有硬件工作不是“没有架构”，而是“已经有一个可运行的稀疏投影数据流，但它的论文级新颖性和系统级收益尚未被实验锁死”。

最合理的补强方式不是把 output-stationary、cache 和多格式后端分别包装成三个新概念，而是将它们收束为一个 H67 特有的、精确且容量安全的跨 tile 等价类驻留数据流，并用真实 bit trace、同约束基线、芯片 PPA 和整 encoder 分账证明该组合不可替代。
