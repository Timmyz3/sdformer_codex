# 片上三格式Builder前端与生命周期压力闭环

## 1. 本轮回答的问题

上一轮已经证明运行时RAW41/IPD32W/FADC24回放和IPD-only residency可行，但格式仍由测试向量或外部descriptor提供。DATE审稿视角下，这留下两个明显缺口：

1. 芯片如何根据当前head的真实数据自己决定格式；
2. 旧window的延迟释放会不会破坏新window refill后的驻留状态。

本轮关闭了第二项，并完成第一项的可综合策略前端。完整payload serializer仍未关闭，因此架构状态仍是条件冻结，不是DC签核。

## 2. 格式与策略合同

### 2.1 三种格式

| 格式 | 精确大小 | 主要用途 |
|---|---|---|
| RAW41 | `162 × (32+9) = 6642 bit`，物理槽104×64=6656 bit | 无条件精确回退 |
| IPD32W | `16 + 8×ceil(T/2) + E` byte | 常规低/中fanout head，支持descriptor residency |
| FADC24 | `16 + 3×T + Σmin(fanout_i,21)` byte | IPD容量溢出的高fanout救援 |

FADC的list/bitmap tie规则保持现有金参考：`fanout<=21`使用list，`fanout>21`使用21-byte bitmap。

### 2.2 容量优先策略

```text
metadata_error = 本地计数溢出 OR 零长度term OR 上游builder_error

if metadata_error:
    RAW41
else if active_classes<=4 and IPD_bytes<=832:
    IPD32W
else if FADC_bytes<=832:
    FADC24
else:
    RAW41
```

该策略不使用stage ID，也不按最小payload盲选。原因是已完成的真实RTL回放显示：FADC在S0/S2虽然payload更短，但没有减少执行term，反而分别比IPD无驻留慢约5.6%和4.5%；明确收益出现在IPD溢出、FADC避免RAW退化的S3 head。

若现有四class上游builder发生class overflow，必须在finalize时拉高`head_end_builder_error`，强制RAW。只有当未来builder保证提供完整class>4 term流时，策略才允许FADC承接class容量。

## 3. 真实Workload决策

单样本、四stage、首block、首window的逐位trace得到：

| Stage | Head | IPD32W | FADC24 | RAW41 | 选中word |
|---:|---:|---:|---:|---:|---:|
| S0 | 3 | 3 | 0 | 0 | 62 |
| S1 | 6 | 6 | 0 | 0 | 12 |
| S2 | 12 | 12 | 0 | 0 | 153 |
| S3 | 24 | 23 | 1 | 0 | 634 |

唯一FADC head为S3/H4：3个active class、61个term、814个event、15个bitmap term；IPD需要1078 byte，FADC为815 byte。因此同一条无stage-oracle规则自然复现了此前手工观察到的S3救援。

Profile100缺少逐term fanout，只能给容量上下界，不能生成精确FADC/RAW分布：

| Stage | Head实例 | IPD精确数 | FADC下界 | FADC上界 | RAW下界 | RAW上界 |
|---:|---:|---:|---:|---:|---:|---:|
| S0 | 264000 | 248919 | 3012 | 15081 | 0 | 12069 |
| S1 | 144000 | 143910 | 28 | 90 | 0 | 62 |
| S2 | 216000 | 215306 | 340 | 694 | 0 | 354 |
| S3 | 48000 | 47106 | 248 | 894 | 0 | 646 |

上述边界还未区分上游class overflow；论文主表必须等待扩大逐位trace，不能直接把FADC上界当成实际选择数。

## 4. 三种Builder微架构候选

| 候选 | 结构 | 优点 | 缺点 | 当前决策 |
|---|---|---|---|---|
| C0串行单workspace | RAW capture后串行统计、决策、序列化 | 控制简单，适合作为功能基线 | builder延迟完全暴露 | 保留基线 |
| C1双workspace共享serializer | 两组RAW scratch/term directory ping-pong，共享统计与serializer | 可重叠下一head捕获和当前head emit，面积受控 | 需严格生命周期和bank端口合同 | 推荐主线 |
| C2并行双候选buffer | 同时生成IPD/FADC，再按cost选择 | 决策灵活 | 两套832-byte buffer、双写流和验证代价高 | 暂缓 |

推荐C1不是因为ping-pong本身新颖，而是它能把H67特有的容量救援格式、exact RAW fallback、IPD residency和统一投影后端组织成一个可审计执行体系。

## 5. 完整Builder数据流

```text
final-gate/K token stream
  -> ping-pong RAW scratch，始终保留完整162×41 bit
  -> active token/class统计
  -> OBI/term枚举：累加T、E、bitmap_terms、Σmin(fanout,21)
  -> typed policy：IPD -> FADC rescue -> RAW
  -> format冻结
  -> descriptor directory顺序读
  -> destination list/bitmap二次扫描
  -> 64-bit serializer
  -> atomic head-slot commit
```

完整实现应采用metadata-first两遍构建，而不是并行生成两套候选payload：

1. `CAPTURE/ANALYZE`：RAW scratch保证回退完整性，同时建立term directory与fanout；
2. `DECIDE/EMIT`：格式冻结后只序列化一种压缩格式，或直接打包RAW；
3. C1用另一workspace捕获下一head，隐藏稳定态的部分构建延迟。

不能把该流程描述为单遍流式编码。首填充、末排空、slot反压和workspace冲突都必须进入周期模型。

### 5.1 建议存储组织

每个workspace的逻辑下界：

| 存储 | 逻辑规模 | 建议组织 |
|---|---:|---|
| RAW scratch | 6656 bit | 1W1R、token-major |
| 4×32 destination bitmap | 20736 bit | 4 class × lane bank，162 bit分段 |
| fanout counter | 1024 bit | 128×8 bit，小RF或寄存器组 |
| term occupancy/directory | 约3-4 Kib | 顺序descriptor RF |

单workspace约4 KiB量级，双workspace约8 KiB量级，均未计macro padding。162-bit bitmap不能直接按平坦寄存器面积外推，必须做分段bank和目标SRAM评估。

## 6. 已实现RTL

```text
gatestack_typed_builder_frontend
  |- gatestack_format_metadata_accumulator
  `- gatestack_typed_format_policy
```

### 6.1 Metadata accumulator

输入是head begin、逐term destination count和head finalize。模块顺序累加：

- term count；
- event count；
- bitmap term count；
- `Σmin(fanout,21)`；
- 本地饱和/零term错误；
- 上游`builder_error`。

所有计数显式扩位和饱和，任何错误都强制RAW，避免宽度截断后误选压缩格式。

### 6.2 Typed policy

Policy是纯组合、无状态模块，只做精确尺寸计算和格式选择；`3×term_count`采用移位加法。格式、payload bit数、64-bit word数和reason随metadata response一起冻结。

Residency不由policy决定：IPD是否驻留仍属于replay plan；FADC/RAW默认cold replay，避免跨越模块职责。

### 7.2 Residency生命周期压力

2 context × 4 head、2006次操作的shadow-model压力回归结果：243次cacheable fill、17次bypass、910次hit、435次miss、238次正确释放、162次空释放、571次stale-tag释放。双模拟器/SVA通过，最终cache valid状态与shadow model零失配。

## 8. DATE贡献边界

本轮可以支持的表述：

> 提出并实现容量优先的精确三格式构建策略前端，使统一GateStack数据流在逐head运行时选择IPD、FADC容量救援或RAW回退，并通过tag-qualified生命周期保护维持跨window驻留一致性。

但它不能单独充当DATE主架构创新。更完整的贡献必须是：

1. final-gate term复用、容量安全三格式slot与统一投影后端的一体化数据流；
2. metadata-first两遍构建和双workspace重叠，量化真实builder开销；
3. exact RAW fallback与tag-qualified IPD residency共同形成可证明的生命周期；
4. 同边界RAW/IPD/FADC、单/双workspace和serializer消融的cycle/PPA/EDP证据。

不能声称：已经完成在线payload编码、已经达到500 MHz、已经节能、已经完成完整H67 encoder加速器或已经满足DATE接收标准。
