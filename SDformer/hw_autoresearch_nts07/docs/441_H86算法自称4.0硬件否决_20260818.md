# H86 算法自称 4.0：本机硬件否决

日期：2026-08-18。90 分钟监视到点后核对。不改 359。不抢 H82 GPU。不写生产 RTL。

算法仓 `H86_ALGORITHM_REVIEW_20260818.md` 写了 **4.0** 和 `CLAIM_4_0=YES`。本机按 `docs/433` 和双线优先序（`docs/439`）独立打回。

## 1. 先认他们做对的

H86 比 H83–H85 像样：

- Shiftmax 回到 **窗级** 一类一票（H82），没有再切成 H85 行级。
- 成员表只在空间行 0 存 packed 列号 `0..14`；行 >0 只有 `member_insert` / `member_delete`。
- expand 用 `prev + insert − delete` 重建，禁 `codes` / `token_gate` / `member_mask` / 513 档 occupancy。
- C8.1 是幸存 class 的 **member** Jaccard，不是类名 `reuse_set`。
- 他们自己的 6 个单测本机 CPU 复跑通过。overlay SHA `66d0a339…` 与合同一致。
- DATE 投稿身份他们仍写 **H67**。H82 仍占卡。没有开 H86 训。

这些够当 **C8 算子/对象草稿**。不够当 DATE 4.0。

## 2. 为什么硬件这边仍是 NO

`docs/433`：创新 4.0 = 新算子合同 **并且** 改掉存储/执行对象。委员会给 ≥4 的，是以前论文里不存在的合同，再配一个 **只为这个合同存在的引擎**。

| 433 门槛 | H86 现场 |
|---|---|
| 新算子合同 | 窗级一类一票，有。尚无 rank-1 SHA、无 AEE。 |
| 改存储/执行对象 | PyTorch 里成员改成 insert/delete。**没有 directory RTL。** 现网仍是 C7：`exp * multiplicity` + 450 带分名单。 |
| 只为该合同存在的引擎 | 没有。expand 最后仍是 dest-owned `K_i * gate_c`。 |
| 41% 名单 | **轴就错了。** |

H86 的“行”是 **一个 15×15 窗里的空间行**，列号 `0..14`。PTPX 41.1% 是 **每条硬件 T450 扫描行** 上的 450 条 active 名单（138 行 × 225 pair）。窗内 15 列 CSR 再省，也不是那 41%。他们自己也写了：不要把 padded-15 说成测到的 CSR 节省。

本机 `scripts/h82_hwscan_delta_directory.py` 才是 41% 那根轴：相邻滑窗 ≈ 相邻 T450 行。合成场上 member Jaccard 0.003–0.028，成员增删约是整表重写的 1.9 倍。H86 的窗内 member TV **训不到** 这条缝。

算法 4.0 还缺他们自己列的：H86 训练、checkpoint SHA、DSEC/MVSEC、rank-1 member Jaccard。没有这些就写 `CLAIM_4_0=YES`，是把“对象草稿过了单测”当成 DATE 分数。
