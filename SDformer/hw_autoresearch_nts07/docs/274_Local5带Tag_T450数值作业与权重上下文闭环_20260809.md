# Local5 带 Tag T450 数值作业与权重上下文闭环

日期：2026-08-09

## 1. 本轮结论

本轮只推进上一轮评审指定的最高优先级缺口：把 Local5 单个 input-head、单个
output-tile 的 T450 数值链，从 testbench 直接灌数改为带身份的 Token、weight 和
result 数据服务作业。

- `[rtl]` 新增 `qfit_local5_tagged_t450_job_engine`，实际执行
  `score/Shiftmax5 -> relation transpose -> source-major term -> TCFM5 -> Acc32`；
- `[rtl]` 两个连续作业完成 900 次 Q/K Token 请求/响应、128 次权重请求/响应和
  1800 个 Acc32 ready/valid 结果；
- `[rtl]` 第二个作业重新加载符号相反的权重，1800 个结果中的后 900 个逐项等于
  Python oracle 的相反数；
- `[rtl]` 四种 1--4 周期服务延迟/随机反压种子在 Icarus 与 Verilator/SVA 中周期
  和账本一致；
- `[rtl]` 实际覆盖 `job_done` 反压，四种种子均观察到 4 拍稳定保持；
- `[rtl]` Token/weight response 的 12 类身份、显式 error、unsolicited/duplicate
  故障均被 fail-closed 捕获，错误后不再发请求或结果；
- `[rtl]` 旧 TCFM5/Linear-5/T450/OUT32 回归全部重新通过。

这仍不是 Local5 全 encoder。当前闭合粒度是“一个 input head 对一个 output tile
产生一组 partial Acc32”。12-block scheduler 尚未连接该引擎，多个 input head 的
partial Acc32 尚未合并。

## 2. 为什么这一层是必要的

上一轮 `docs/273` 只证明了 12-block 控制拓扑：每帧 1320 个窗口语义组、6720 个
output-tile request 和 54000 个 input-head job/replay request。它没有证明这些请求
真的取得 Q/K、切换正确权重、运行数值核并写出结果。

旧单 tile TB 则从相邻层次直接驱动 `weight/in/read` 端口，不能回答：

1. 请求与返回如何绑定到同一个 input head 和 output tile；
2. 延迟响应、错 tag 和输出反压是否会污染下一个作业；
3. 权重是否能在不 reset 芯片的情况下完成 `release -> reload`；
4. `job_done` 是否真的晚于最后一个 Acc32 结果接受和流水排空。

新作业层把这四项变成显式协议，而不是 testbench 隐含顺序。

## 3. 数值数据流

```text
job {tag, input_head, output_tile}
  |
  +-> 64 次 tagged weight request/response（当前 OUT_DIM=2）
  |     {tag, input_head, output_tile, lane, out, int8 weight}
  |     -> TCFM5 weight load/commit
  |
  +-> projection_start
  |
  +-> 450 次 tagged Token request/response
  |     request  = {tag, input_head, token_id, plane, y, x}
  |     response = {tag, input_head, token_id, Q32, K[5][32], valid_mask[5]}
  |        |
  |        v
  |     Q7 score + Q1.7 Shiftmax5
  |        -> relation transpose
  |        -> source-major term
  |        -> TCFM5 five-bank projection
  |        -> Acc32 partial result
  |
  +-> 900 次 tagged result ready/valid
  |     {tag, input_head, output_tile, plane, y, x, out, Acc32, last}
  |
  +-> weight_context_release
  |
  +-> job_done {tag, input_head, error}
```

`job_done` 只在以下条件全部满足后出现：450 个 Token 已返回、数值流已经 drain、
projection 已 close、900 个 Acc32 结果均被下游接受、权重上下文完成 release。结果
反压时，tag、坐标、数据和 `last` 必须保持不变。

## 4. 接口合同

| 接口 | 方向 | 关键字段 | 当前合同 |
|---|---|---|---|
| job | scheduler -> engine | tag/input_head/output_tile | 空闲时接受一个作业 |
| Token request | engine -> SRAM service | tag/head/token_id/plane/y/x | 每次只允许一个 outstanding |
| Token response | SRAM service -> engine | tag/head/token_id/Q/K/mask | 身份或 error 不符立即 fail-closed |
| weight request | engine -> weight service | tag/head/tile/lane/out | 每次只允许一个 outstanding |
| weight response | weight service -> engine | 同请求字段/int8 | 64 项完整后才能 start |
| result | engine -> accumulator service | tag/head/tile/坐标/Acc32/last | 标准 ready/valid，反压保持 |
| job done | engine -> scheduler | tag/head/error | 最后结果和 release 之后出现 |

当前 `tag` 是 24-bit 透明身份，尚未冻结为 `{stage, block, window, output_tile}` 的论文
编码。这个编码必须在 scheduler 集成顶层统一完成，不能在两个模块各自推导。

## 5. 权重上下文生命周期

本轮给 TCFM5 后端和 Local5 tile 增加显式：

```text
LOAD -> RUN -> DONE/read -> RELEASE -> LOAD
```

`weight_context_release_ready` 只有在 projection done、无读请求和无读返回在途时成立。
合法 release 清空 `weights_loaded/weight_seen/weight_count`，随后允许另一组权重重新
装载；提前 release 置协议错误。

测试连续运行两个相同 Q/K 作业：

| 作业 | output tile | 权重 | 期望 |
|---:|---:|---|---|
| 0 | 0 | Python oracle 原权重 | `Acc32 = oracle` |
| 1 | 1 | 每项权重取负 | `Acc32 = -oracle` |

这比“第二次也完成”更严格，因为若 release 没有真正清空旧上下文、地址错位或最后
一项权重没有提交，结果不会逐项精确取反。

## 6. 验证结果

一键入口：

```bash
sim_qfit/run_qfit_local5_tagged_t450_job_engine_checks.sh
```

报告：

```text
results/qfit_local5_tagged_t450_job_engine_20260809/report.{md,json}
```

### 6.1 独立 Python oracle

固定数据种子 `0x45052026` 生成：

| 项目 | 数量 |
|---|---:|
| T450 输入 | 450 |
| source-major term | 19191 |
| destination update | 33954 |
| 单作业 OUT_DIM=2 Acc32 | 900 |

输入包含全零/全一边界、真实几何 invalid mask，以及运行时额外 invalid candidate。

### 6.2 四种服务时序

| 服务种子 | Icarus 周期 | Verilator/SVA 周期 | Token | Weight | Result | done stall |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 47603 | 47603 | 900 | 128 | 1800 | 4 |
| 17717 | 47607 | 47607 | 900 | 128 | 1800 | 4 |
| 44257 | 47612 | 47612 | 900 | 128 | 1800 | 4 |
| 48879 | 47687 | 47687 | 900 | 128 | 1800 | 4 |

周期包含 testbench 的 1--4 周期 Token/weight response latency 和随机 ready，只用于
协议回归，不是 SRAM macro 周期、端到端吞吐或 FPS。

### 6.3 SVA 与故障注入

SVA 覆盖：

- Token request、weight request、result 和 job_done 在反压下保持；
- Token id 与 `(plane,y,x)` 几何一致；
- weight lane/out 和 result 坐标不越界；
- `last` 只在最后一个 Acc32 结果上成立；
- clean job_done 前累计 Token/weight/result 账本完整；
- response 账本不能领先 request；
- Token/weight response 在反压下字段保持；
- 已接受的 response 身份错配或显式 error 在下一拍进入 protocol error；
- 非等待状态出现 unsolicited/duplicate response 时必须进入 protocol error；
- protocol_error 粘滞，错误后不再发外部工作。

故障 TB 依次覆盖以下 12 种模式：

1. Token tag、head、token id 身份错配和显式 error；
2. weight tag、head、output tile、lane、out 身份错配和显式 error；
3. 无 Token 请求时的 unsolicited response；
4. 已接受 weight response 后的 duplicate response。

Icarus 与 Verilator/SVA 的 24 次故障运行全部进入 fail-closed error completion，且
错误后连续观察 12 周期无新请求或结果。正常路径还对每个作业施加确定性的两拍
`job_done` 反压，四种种子均累计 4 拍 stall，期间 done tag/head/error 保持稳定。

### 6.4 旧回归

| 回归 | 结果 |
|---|---:|
| Linear-5 exhaustive mask Icarus/Verilator-SVA/Yosys | PASS |
| TCFM5 两个权重上下文直接回归 | PASS |
| T450 多数据种子与随机/定向反压 | PASS，Acc32 mismatch=0 |
| T450 OUT_DIM=32 production-width smoke | PASS，Acc32 mismatch=0 |

OUT_DIM=32 已在旧 tile shell 验证，但本轮 tagged-job 顶层的正式签核参数仍是
OUT_DIM=2。因此不能写“tagged T450 OUT32 已闭环”。

### 6.5 开放综合代理

| 口径 | generic cell |
|---|---:|
| Yosys hierarchy top | 296 |
| Yosys flatten | 8145 |

该数值只证明层次可综合读取。它不是 DC 面积、STA 频率、SAIF 功耗或 ASIC PPA，

## 7. 本轮负结果与修复

### 7.1 第二作业启动死锁

首版 `job_ready` 同时依赖底层 `tile_weight_ready`。首作业 release 后，底层的权重
合法性还取决于作业引擎当前暴露的旧 lane/out 坐标，导致引擎已经空闲但新作业无法
被接受。修复为 `job_ready` 只表达作业层空闲和无 tile error；新作业锁存后再通过
标准 weight request/response 状态机等待底层 ready。两个相反权重上下文随后通过。

### 7.2 错 Tag TB 提前响应

首版故障 TB 在 request valid 出现后、request 上升沿握手前就拉高 response valid，
RTL 正确将其判为 unsolicited response，但 TB 仍等待原目标路径而超时。修复为先在
上升沿完成 request 握手，再延迟到负沿产生错 Tag response。当前 PASS 验证的是
“已接受请求后的身份错配”，不是更弱的无请求响应。

### 7.3 退化服务种子跨模拟器差异及闭环

初版 `SERVICE_SEED=1` 下两个模拟器的数值和业务账本一致，但周期分别为 47579 和
47591，相差 12 拍。根因是 TB 在 `posedge` 活动区中解除 reset，同时服务模型也在
`posedge` 更新 LFSR，形成模拟器调度顺序相关的 testbench race。将 reset 解除移到
`negedge` 后，Icarus 与 Verilator/SVA 均为 47603 周期，Token/weight/result 账本和
4 拍 `job_done` stall 完全一致。种子 1 已恢复为正式签核种子。

该修复关闭的是验证环境竞争，不改变 DUT。当前仍未引入 SRAM macro 时序模型，
所以这四组周期只能证明协议确定性，不能外推部署吞吐。

## 8. DATE 证据边界

可以写：

> `[rtl]` Local5 的单 input-head/单 output-tile T450 数值作业已通过带 tag 的
> Token、weight 和 Acc32 result 服务闭环，并在两个权重上下文、四种随机服务
> 时序、`job_done` 反压和 12 类 response 故障注入下保持 bit-exact/fail-closed。

不能写：

- “Local5 12-block 全 encoder RTL 已闭环”；
- “54000 个 input-head job 已完成真实数值回放”；
- “跨 input-head Acc32 已归约”；
- “relation memo 已集成”；
- “tagged-job OUT32 已签核”；
- “约 47.6k cycle 是部署吞吐”；
- “Yosys 8145 cell 是 ASIC 面积”；
- “tag、reload FSM、FIFO 或 banking 是 DATE 创新”。

## 9. 下一轮唯一最高优先级

下一轮应实现一个 output-tile 数值作业控制层，把 `docs/273` 的 head-job 请求真正
接到本轮 T450 引擎，并完成跨 input-head Acc32 合并：

```text
tile_start(stage/block/window/output_tile)
  -> for input_head = 0 .. heads-1
       run tagged T450 partial job
       merge 450 x OUT_DIM partial Acc32 into tile accumulator
  -> drain final accumulated tile results
  -> tile_done
```

签核条件是：至少一个多 input-head 作业在随机 Token/weight/result 反压下，与 Python
`sum(partial_head)` oracle 逐项一致；中间 head 不得提前 `tile_done`，错 head/tag 不得
产生 partial write。完成这个包后再接 relation memo 的首访建立/后续回放生命周期。

Motion 线继续维护现有 SCS/NMF/DCTF/RQTB2S 多样本回归；本轮没有删除 Motion，也
没有将 Local5 的局部闭环解释为最终主线冻结。

## 10. 独立 DATE 初审与修复

独立只读审稿人对初版给出：

| 范围 | 评分 | 建议 |
|---|---:|---|
| 本轮带 Tag T450 局部证据包 | 3.6/5 | Weak Accept（仅局部证据包） |
| 整个 Local5 硬件线 | 3.3/5 | Weak Reject / Major Revision |

审稿人确认 OUT_DIM=2 范围内没有高严重度数值错误，但指出：scheduler 与数值核仍
分离、没有跨头 Acc32；本轮正式参数不是 OUT32；种子 1 存在 TB race；故障注入和
response SVA 太窄；lint 只能称 exit-code PASS；内部子模块命令接口仍是当前工程的
command-style 合同，不是可任意复用的标准 ready/valid。

本轮已关闭可在当前边界内关闭的三项：

- 修复 reset 释放竞争，四个正式种子跨模拟器逐周期一致；
- 把错误覆盖扩展到 12 类 response 故障，并补 response 稳定性、身份检查和
  unsolicited/duplicate SVA；
- 对 `job_done` 施加真实反压，并把 lint 表述收紧为“exit-code PASS，含已审阅警告”。

未通过包装掩盖的剩余主缺口是 OUT32 三输入头 tile 归约以及 scheduler 的真实连接。
这两项必须作为同一个下一轮证据包完成，之后才能重新评价 Local5 的系统完整度。

修复后的独立收口复审给出：局部包 `3.8/5，Weak Accept`，整个 Local5
`3.4/5，Weak Reject / Major Revision`。复审确认 reset race、response 故障矩阵、
`job_done` 反压、lint 口径和未闭合边界均已实质关闭；唯一新增意见是 response
稳定性 SVA 当时只锁身份字段，没有锁 Q/K/mask 和 weight data payload。

该意见随后已修复：`p_token_response_stable` 现同时约束 Q、5 路 K 和 valid mask，
`p_weight_response_stable` 同时约束 INT8 weight data。补丁后的四种正常时序、12 类
故障矩阵、Icarus、Verilator/SVA、lint 和 Yosys 全流程已重新 PASS。因此局部包的
response 协议意见按本轮证据关闭；整个 Local5 的 3.4/5 仍不提升，因为 OUT32
跨头数值集成在本文件范围内尚未完成。
