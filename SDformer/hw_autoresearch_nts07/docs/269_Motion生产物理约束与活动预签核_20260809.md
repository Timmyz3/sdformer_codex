# Motion生产物理约束与活动预签核

## 1. 本轮问题

上一轮Motion ZKQI三方对照已经证明RQTB2S、PairBitmap-ZKQI和TTB8-ZKQI在138条真实fullres T450 head-row、四种反压模式下保持bit-exact，但开放物理证据存在未约束宏端点、DRV和固定频率口径不严的问题。本轮只收口以下边界：

1. 三方使用同一顶层接口、同一5 ns SDC、同一六个SRAM代理宏和同一floorplan；
2. setup、hold、max-cap、max-slew、max-fanout、DRC和未约束端点必须同时为零；
3. 20-bit active descriptor绑定32-bit代理宏后必须与行为存储等价；
4. 活动证据只按真实RTL工作事件分账，不把事件数伪装成功耗或EDP。

## 2. 结论

本轮状态为**PASS**，但证据等级仅为`[rtl]+[rtl活动代理]+[open-pnr代理]`。

- `[rtl]`：描述符从28 bit压到数学上足够的20 bit；宏模式和行为模式在Icarus、Verilator下等价。
- `[rtl活动代理]`：TTB8-ZKQI相对RQTB2S减少53.13%的score计算和45.49%的Q/K读取bit；含共同预载后周期减少12.83%。
- `[open-pnr代理]`：三方在共同200 MHz约束下均无setup/hold/DRV/DRC/未约束端点违例。
- `[open-pnr代理]`：TTB8-ZKQI全实例面积增加2.09%，固定200 MHz吞吐提升1.147倍，面积归一吞吐为1.124倍。
- 负结果：PairBitmap-ZKQI虽减少score和读活动，但无反压周期不变；面积增加1.28%后，固定200 MHz面积归一吞吐只有0.987倍。

这说明Motion主张应是“exact zero-K work gating + TTB层次issue skipping”的组合。PairBitmap只能作为隔离work gating的强基线，不能单独写成吞吐创新。

## 3. RTL与宏合同修正

### 3.1 20-bit active descriptor

真实active descriptor只需要：

| 字段 | 位宽 |
|---|---:|
| pair id | 8 |
| exact score class value | 8 |
| temporal mask | 2 |
| active mask | 2 |
| 合计 | 20 |

原16-bit score字段被缩为8 bit。该score来自有限离散class，8 bit保持精确，不是截断近似。描述符因此由28 bit降至20 bit。

### 3.2 32-bit开放宏padding

开放流程只有`fakeram45_256x32`。功能数据只读低20 bit；高12 bit复制低位数据并在写拍使用整字mask写入。这样做有两个目的：

1. 不使用false path掩盖未约束宏输入；
2. 对开放物理代理保守计入整字写活动。

目标DC阶段应替换为真实20-bit SRAM编译器宏，不能沿用32-bit padding面积和功耗作为最终结果。

### 3.3 宏模式等价

新增功能宏模型和行为/宏双实例miter，覆盖：

- 单项写；
- 偶/奇bank同拍双写；
- 地址0、1、448、449；
- padding为全0和全1的两类数据；
- 随机read-response反压；
- 132次有金参考读回。

Icarus与Verilator均通过，未出现协议错误。复现入口：

```bash
sim_h67/run_h67_active_descriptor_store_macro_miter.sh
```

## 4. 物理闭环的失败演进

本轮保留了失败结果，不只保留最终成功目录。

### 4.1 失败一：24个未约束宏端点

最初目录宏只有低20个write-mask位被驱动，两个bank各12个高位端点未约束，共24个。该问题通过整字mask和padding合同修正；最终三方未约束端点均为0，没有加入false path或disable-timing例外。

### 4.2 失败二：无cap margin时22个max-cap违例

第一次5 ns生产顶层布线后，baseline时序和DRC通过，但存在22个max-cap违例，因此不能签核。

### 4.3 失败三：共同CAP_MARGIN=40时TTB8差18 ps

使用共同`CAP_MARGIN=40`后，baseline和PairBitmap通过，TTB8的WNS为-0.0183 ns。没有单独放宽TTB8，而是给三方统一加入`SETUP_SLACK_MARGIN=0.05 ns`重新完整布局布线。

### 4.4 最终共同约束

| 条目 | 三方共同值 |
|---|---|
| 工艺代理 | Nangate45 OpenROAD |
| 时钟周期 | 5 ns，200 MHz |
| CAP_MARGIN | 40 |
| SETUP_SLACK_MARGIN | 0.05 ns |
| die/core | 900x700 um / 880x680 um |
| SRAM宏 | 6个`fakeram45_256x32` |

| false path/disable timing | 无 |

## 6. RTL工作事件活动代理

| 候选 | 元数据检查/分发 | score次数 | Q/K读bit | 执行周期 | 含预载周期 |
|---|---:|---:|---:|---:|---:|
| RQTB2S | 31050 pair | 31050 | 4641312 | 85625 | 116675 |
| PairBitmap-ZKQI | 31050 pair | 14554 | 2529824 | 85625 | 116675 |
| TTB8-ZKQI | 4002 bundle + 14554 active pair | 14554 | 2529824 | 70657 | 101707 |

分账得到：

- exact zero-K直注入使score次数下降53.13%；
- exact Q/K payload gating使读取bit下降45.49%；
- PairBitmap仍执行31050次逐pair检查，因此无反压周期不变；
- TTB8改为4002次bundle header检查加14554次active-pair分发，执行周期下降17.48%；
- 共同31050周期预载削弱端到端收益，含预载后周期下降12.83%。

这些计数的单次能量不同，不能任意加权为总功耗。OpenROAD报告中的静态IR分析也没有真实活动、SAIF和可信VSRC合同，本轮不引用其IR数值。

## 7. DATE层面的意义

### 7.1 本轮补强了什么

TTB8-ZKQI现在不再只是一个扫描器RTL：

1. workload证据表明score/read work gating与issue skipping作用不同；
2. PairBitmap作为同算法、同zero-K语义、不同issue机制的强基线，隔离了TTB层次跳扫收益；
3. 三方在真实trace、随机反压、行为/宏等价和同宏物理约束下闭环；
4. 失败结果证明收益不是来自隐藏未约束端点或候选专属约束。

### 7.2 仍不能支撑什么

本轮仍不能称为DATE可接收的完整系统证据，原因是：

- 只有sample0/window0，缺少多sample、多window的mean/p95/p99；
- 无门级SAIF、DC、PTPX和目标SRAM宏，无法给出功耗、能量和EDP；
- 当前范围是attention row子系统，不是full encoder FPS；
- TTB8是有实测收益的机制，但其架构新颖性必须与Motion的exact zero-K三类注入、统一temporal-pair数据流和完整encoder调度共同表述。

## 8. 下一步

Motion线下一优先级是多样本trace与门级活动输入合同，而不是继续堆扫描器变体。Local5线仍优先完成`score/Shiftmax5 -> relation transpose -> source-major term -> TCFM5 -> Acc32`端到端RTL，并补12-block时间复用、真实trace和随机反压。

双线新机制继续开放，但候选必须先满足：真实profile有结构性机会、强基线下有独立收益、数值语义可证明、最小RTL能进入同约束评估。未满足者只保留为`[待验证]`，不列为论文贡献。
