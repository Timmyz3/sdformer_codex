# NTS11 硬件小白入门路线图

**版本**：2026-06-22  
**对象**：准备从 NTS11 软件实验进入 DATE 硬件设计的协作者  
**定位**：这不是目录，而是一份分阶段学习手册。每一阶段都告诉你要学什么、为什么学、对应 NTS11 的哪一段数据流、要画什么图、读哪些文件、学完怎么自测。  
**主线**：先摸清真实数据流，再看模块接口和存储生命周期，最后才进入 RTL。当前硬件主线按 all-binary UniBin-H60 方案学习。

### 第 1 天：端到端数据流和 skip/residual

目标不是理解所有模块细节，而是知道一帧数据从输入到输出经过哪些大块，以及哪些数据要被保存下来以后再用。

你要读：

```text
本文件第 2 节：端到端推理图
本文件第 3 节：residual / skip 连接
third_party/SDformerFlow/models/STSwinNet_SNN/Spiking_swin_transformer3D.py
```

重点只看这些函数或类名，不要全文件硬啃：

```text
Spiking_SwinTransformerBlock3D.forward
Spiking_Swin_BasicLayer.forward
Spiking_SwinTransformer3D_v2.forward
SpikingformerFlowNet.forward
skip_concat / skip_sum
```

你要画两张图。

第一张是粗数据流图：

```text
Event/Voxel
→ Patch residual stack
→ S0 H60 x2
→ Downsample0
→ S1 H60 x2
→ Downsample1
→ S2 H60 x6
→ Downsample2
→ S3 H60 x2
→ Bottleneck resblocks
→ Decoder0/1/2/3
→ prediction sum over T
→ flow
```

第二张是 skip 生命周期图：

```text
Swin block shortcut0: block input → ADD0
Swin block shortcut1: ADD0 output → ADD1
S0/S1/S2 skip: downsample 前 stage output → 对应 decoder
S3 skip: final-stage output → bottleneck 后 decoder0
prediction feedback: pred(i-1) → decoder(i), i > 0
```

你要特别记住：

```text
downsample 分叉只有 S0/S1/S2；
decoder encoder-skip 输入有 S3/S2/S1/S0 四个；
Swin block 内部每个 block 有 ADD0 和 ADD1 两次短 residual。
```

第 1 天自测：

1. 为什么 S0/S1/S2 的 skip 是 downsample 前输出？
2. S3 为什么不是 downsample 前 skip？
3. 每个 H60 Swin block 里 H60 之外还有哪两个 ADD？
4. decoder 除了 encoder skip，还有哪条 previous prediction feedback？
5. 哪些 buffer 是短生命周期，哪些是长生命周期？

### 第 2 天：数据格式、bitwidth 和 buffer 生命周期

目标是把“数据是什么”说清楚。你不需要会写 RTL，但要能说出每条边的数据位宽和存储位置。

你要读：

```text
本文件第 4、7、8 节
docs/23_AllBinary_P0_profiling实测结果.md
docs/26_AllBinary主线真实数据流与硬件重排设计.md
```

你要做一张表，至少包含：

| 数据 | 来源 | 消费者 | 位宽 | 生命周期 | 建议存储 |
|---|---|---|---:|---|---|
| Q event | ATLIF-Q | H60 score | 1-bit | 一个 window/row | packed event SRAM |
| K event | ATLIF-K | H60 score/gated-K | 1-bit | 一个 window/row | packed event SRAM |
| score | consensus engine | Shiftmax | INT16 | 一个 token row | score buffer |
| gate | Shiftmax | gated-K | INT8 | 一个 token row | gate buffer 或 streaming |
| shortcut0 | block input | ADD0 | 定点/event | 同 block 内短周期 | local buffer |
| shortcut1 | ADD0 output | ADD1 | 定点/event | 同 block 内短周期 | local buffer |
| S0/S1/S2 skip | BasicLayer downsample 前 | decoder | 1-bit/定点 | 长周期 | encoder skip SRAM |
| S3 skip | final stage output | decoder0 | 1-bit/定点 | 中长周期 | activation/skip SRAM |
| pred feedback | decoder prediction | 下一 decoder | 定点 flow/feature | 中周期 | prediction buffer |

第 2 天要理解三个硬件问题：

1. **位宽决定 SRAM 面积和带宽**  
   1-bit Q/K event 比 2-bit ternary event 直接省 event SRAM 和读带宽。

2. **生命周期决定能不能放 local buffer**  
   Swin ADD0/ADD1 的 shortcut 很短，可以放局部 buffer；S0/S1/S2 skip 要跨过 bottleneck 和 decoder，必须进长生命周期 SRAM。

3. **数据格式不一定全网一样**  
   H60 Q/K 可以是 1-bit event，但 residual ADD、decoder、flow 可能仍是定点 activation 或 accumulator。不要把“all-binary H60 主线”误解成“整网每一条线都是 1-bit”。

第 2 天自测：

1. 为什么 `score` 不能用 1-bit？
2. 为什么 `gate` 不是 event？
3. 为什么 S0 skip 比 shortcut0 更需要 SRAM？
4. all-binary 主要省的是哪类存储和计算？
5. 哪些数据需要 accumulator？

### 第 3 天：H60 一行 token-row 怎么算

目标是把 H60 当成一个小硬件核理解，而不是当成论文公式理解。你只看一行 query token 对一个 window 内所有 key token 的计算。

你要读：

```text

docs/25_UniBinH60_DCReady_RTL设计验证与代码审阅.md
```

先背这个顺序：

```text
load token row
→ compute overlap/q_active/k_active/mismatch
→ fuse TX/SC score
→ find row max
→ approximate exp2
→ row sum
→ generate INT8 gate
→ gated-K output
```

对应 RTL 状态机：

```text

ST_FIND_MAX
ST_SUM_EXP
ST_EMIT
ST_DONE
```

你要画一张 H60 row 微架构图：

```text

        |
        v
AND + popcount(Q) + popcount(K) + popcount(Q&K)
        |
        v
TX/SC fuse: score = overlap + μ*(overlap-mismatch)
        |
        v
score_mem
        |
        v
row_max → exp2_approx → row_sum → gate
        |
        v
gated-K output stream
```

第 3 天必须能解释 ready-valid：

```text
in_valid  : 上游说输入有效
in_ready  : H60 core 说我能接

```

第 3 天自测：

1. 为什么 H60 core 要保存一整 row 的 score？

5. 当前 RTL 的 Shiftmax 为什么还不能算 bit-accurate signoff？

### 第 5 天：TTB、empty skip 和硬件省功耗

要理解 TTB：

```text
TTB = Token-Time Bundle
```



## 0. 先建立正确心智模型

### 0.1 你现在真正要学的不是 Verilog

刚开始做硬件时最容易犯的错是直接看 RTL 或开始写模块。这样会很快卡住，因为你还不知道：

1. 数据从哪里来；
2. 每一步数据长什么样；
3. 哪些是 1-bit spike，哪些是 2-bit ternary event；
4. 哪些模块只是 PyTorch logical site，哪些才应该是物理硬件；
5. 一帧推理到底按什么顺序执行。

所以第一阶段目标不是“写硬件”，而是能把 NTS11 推理过程画出来。

### 0.2 NTS11 的一句话

NTS11 早期硬件设想是：

```text
全 encoder 统一 H60 attention
+ 统一 ATLIF wrapper
+ ternary/binary Q/K event coding 可选
+ TX/SC consensus score
+ single Shiftmax gate
+ gated-K event output
```

但当前 DATE 硬件主线已经收敛到 **all-binary UniBin-H60**：

```text
全 encoder 统一 H60 attention
+ 105 个 ATLIF logical site 全部输出 binary event
+ Q/K event 全部 1-bit
+ TX/SC consensus 用 popcount/overlap/mismatch 实现
+ single INT8-ish Shiftmax token gate
+ gated-K output
+ 1-bit packed event SRAM
+ TTB empty issue gating
```

所以你学习时要把“早期 NTS11 思路”和“当前 all-binary 硬件主线”分开：

| 项目 | 早期 NTS11 | 当前 UniBin-H60 主线 |
|---|---|---|
| Q/K event | ternary 或 mixed | binary 1-bit |
| ATLIF 输出 | binary/ternary wrapper 混合探索 | 全部 binary |
| attention 覆盖 | full encoder H60 | full encoder H60 |
| 硬件主卖点 | 统一 H60，减少 mixed datapath | 统一 H60 + 统一 1-bit event datapath |
| DATE 叙事 | 从混合路径转向统一 H60 | all-binary event transformer accelerator |

它和 NTS07/09 最大区别不是指标表里的某个数，而是：

```text
NTS07/09: 部分 block 是 H60，部分仍是原生 QKFormer / PSN / carrier 混合路径
NTS11   : encoder attention 全部统一成 H60 路径
```

### 0.3 你要反复记住的硬件原则

PyTorch module 数量不等于硬件实例数量。

```text
105 个 ATLIF logical sites
≠ 105 套 ATLIF 硬件

12 个 Shiftmax attention logical sites
≠ 12 套 Shiftmax 硬件
```

硬件更合理的方式是：

```text
少量共享 ATLIF encode lanes
+ 少量共享 H60 / Shiftmax engine
+ descriptor 控制当前处理哪个 stage/block/module
```

## 2. 阶段 1：看懂端到端推理图

### 2.1 为什么第一步必须学推理图

硬件执行的是推理路径，不是训练路径。  
训练里的 loss、gradient、optimizer、threshold update 都不是第一版推理硬件要执行的东西。

你先要知道一帧数据经过哪些模块，顺序是什么。

### 2.2 NTS11 推理主链

先背下来这条链：

```text
事件输入
→ voxel grid
→ patch embedding
→ S0: H60 block ×2
→ downsample 0
→ S1: H60 block ×2
→ downsample 1
→ S2: H60 block ×6
→ downsample 2
→ S3: H60 block ×2
→ bottleneck resblock
→ decoder，同时读回 S3/S2/S1/S0 的 encoder skip
→ flow prediction
```

你可以把它理解成一个 U-Net 风格 encoder-decoder，只是 encoder 里每个 Swin block 的 attention core 都换成 H60。

注意这里的“主链”只是最简记忆版。真实代码不是一条没有分叉的流水线，至少还有三类旁路：

1. 每个 Swin block 内部有 attention residual 和 MLP residual；
2. encoder stage output 会保存给 decoder，其中 S0/S1/S2 是 downsample 前分叉，S3 是 final-stage output 旁路；
3. decoder 除了读 encoder skip，还会从第二个 decoder stage 开始读上一尺度 prediction。

### 2.3 每一段大概在做什么

| 段 | 作用 | 是否 H60 | 硬件引擎 |
|----|------|----------|----------|
| event / voxel | 把事件流变成体素张量 | 否 | Event Scatter |
| patch embedding | 把输入变成 encoder feature | 否 | Sparse/Dense MAC + ATLIF |
| S0/S1/S2/S3 block | 编码局部时空特征 | 是 | H60 engine + Sparse MAC |
| downsample | stage 间降分辨率、升通道 | 否 | Sparse MAC + ATLIF |
| bottleneck | 深层特征处理 | 否 | Sparse MAC |
| decoder | 上采样和输出光流 | 否 | Dense/Sparse MAC |

### 2.4 NTS11 的 encoder stage

## 3. 阶段 1.5：看懂所有 residual / skip 连接

### 3.1 为什么 residual / skip 不能漏

如果只看 H60，会误以为 encoder 是：

```text
输入 → H60 → MLP → 下一个 block
```

但源码里的真实 block 是：

```text
shortcut0 = block_input
attn_out  = H60_SSA(block_input)
x1        = attn_out + shortcut0

shortcut1 = x1
mlp_out   = MLP(x1)
x2        = mlp_out + shortcut1
```

这意味着硬件必须在 H60 engine 工作时保存 `shortcut0`，在 MLP engine 工作时保存 `shortcut1`。这不是 PyTorch 里一行 `+` 的问题，而是 SRAM/寄存器文件生命周期和读写带宽问题。

对应源码：

```text
third_party/SDformerFlow/models/STSwinNet_SNN/Spiking_swin_transformer3D.py
Spiking_SwinTransformerBlock3D.forward:
  shortcut = x
  x = self.SSA(...)
  x = self.sew_function(self.drop_path(x), shortcut, "ADD")
  x = self.sew_function(self.mlp(...), x, "ADD")
```

### 3.2 Swin block 内部 residual

一个 NTS11 H60 block 的硬件图要画成：

```text
                ┌──────────────────────────────┐
block input ───►│ window/norm/shift/partition   │
      │         └──────────────┬───────────────┘
      │                        ▼
      │                 H60 attention core
      │           TX/SC score → Shiftmax → gated-K
      │                        │
      └──────── shortcut0 ─────┼──► ADD0
                               ▼
                              x1
                               │
                               ├── shortcut1
                               ▼
                              MLP
                               │
                               └──► ADD1 ───► block output
```

这里 H60 是统一 attention core，但它不是整个 block。完整 block 还包括：

| 子步骤 | 做什么 | 对硬件的要求 |
|--------|--------|--------------|
| norm / window / shift | 变换 token 排布 | 地址生成器、padding/crop、mask |
| H60 core | TX/SC score、Shiftmax、gated-K | 共享 H60 engine |
| ADD0 | attention 输出加 block input | 保存 shortcut0，做逐元素加 |
| MLP | 通道混合 | Sparse/Dense MAC + ATLIF |
| ADD1 | MLP 输出加 x1 | 保存 shortcut1，做逐元素加 |

所以 DATE 论文中不能只画 `H60 engine`。至少要画出 `H60 engine` 外面有一个 `Swin residual shell`。

### 3.3 BasicLayer 的两个输出

每个 encoder stage 的 `BasicLayer.forward` 返回两个东西：

```text
x_out, x
```

含义不同：

| 名称 | 来源 | 去哪里 | 硬件含义 |
|------|------|--------|----------|
| `x` | 当前 stage 所有 Swin block 之后；若有 downsample，则在 downsample 之前 | 存入 `outs`，给 decoder long skip | 长生命周期 encoder skip SRAM |
| `x_out` | `x` 经过 PatchMerging/downsample 之后 | 送到下一 stage | 主链激活 buffer |

对应源码：

```text
Spiking_Swin_BasicLayer.forward:
  for blk in self.swin_blocks:
      x = blk(x, attn_mask)
  if self.downsample is not None:
      x_out = self.downsample(x)
  else:
      x_out = x
  return x_out, x

Spiking_SwinTransformer3D_v2.forward:
  x, out_x = layer(x.contiguous())
  out = rearrange(out_x, 'n d h w c -> n c d h w')
  outs.append(out)
```

这点非常关键：对 S0/S1/S2，decoder skip 读到的是 `downsample 前` 的 stage 输出，不是送往下一 stage 的 `x_out`。对 S3，因为最后一层没有 downsample，`x_out == x`，但代码仍会把这个 final-stage output 放进 `outs`，后面 decoder 第 0 层还会重新读它。

### 3.4 downsample 不是 residual，但它是数据流分叉点

NTS11 的 downsample 采用 `MS_SpikingPatchMerging` 路径，代码逻辑是：

```text
x0 = x[:, :, 0::2, 0::2, :]
x1 = x[:, :, 1::2, 0::2, :]
x2 = x[:, :, 0::2, 1::2, :]
x3 = x[:, :, 1::2, 1::2, :]
x  = concat([x0, x1, x2, x3], channel)
x  = ATLIF / SN
x  = reduction
x  = norm
```

它不是 skip add，但它在 S0/S1/S2 同时连接两个生命周期：

1. downsample 前的 `x` 要保存给 decoder；
2. downsample 后的 `x_out` 要继续往下一 stage 走。

这解释了为什么 profiling 里 `downsample_event` 是 NTS11 热点之一。它既有空间重排和通道扩展，又处在 encoder skip 写回的分叉点。

S3 没有 downsample，所以不能说“S3 是 downsample 前 skip”。S3 的准确说法是：final-stage output 同时作为 bottleneck 输入，并作为 decoder 第 0 层的 encoder skip，需要在 bottleneck residual blocks 执行期间保留原始 S3 output。

### 3.5 Patch embedding 里也有 residual

输入进入 encoder 前不是简单卷积一下就结束。`Spiking_PatchEmbedLocal.forward` 的主结构是：

```text
xs  = head(x)
out = residual_encoding(xs)
out = proj(out)
```

其中 `residual_encoding` 是 4 个 residual block 的栈。若走 MS 版本，每个 `MS_ResBlock` 内部是：

```text
identity = x
x = SN1 → Conv1 → Norm1
x = SN2 → Conv2 → Norm2
out = x + identity
```

硬件含义：

| 路径 | 是否 H60 | 是否要 residual buffer |
|------|----------|------------------------|
| patch head | 否 | 否或短生命周期 |
| patch residual_encoding | 否 | 是，每个 residual block 需要 identity |
| patch proj | 否 | 视实现需要 |

这部分不属于 H60，但会贡献 ATLIF、卷积、feature SRAM 访问，不能从硬件估算里删掉。

### 3.6 Bottleneck resblock

encoder 输出的最深层 feature 会经过 `self.resblocks`：

```text
blocks = self.encoders(x)
x = blocks[-1]
for resblock in self.resblocks:
    x = resblock(x)
```

这些 `resblock` 同样是 residual 结构，不是普通串联卷积。硬件上可以复用 patch residual / MLP 附近的加法和 activation buffer，但要单独在调度表里保留 identity 生命周期。

### 3.7 Decoder long skip

decoder 每个尺度都会先融合 encoder skip：

```text
x = self.skip_ftn(x, blocks[self.num_encoders - i - 1], dim=2)
```

这里 tensor 布局是 `T, B, C, H, W`，所以 `dim=2` 是 channel 维。若 `skip_type=concat`，就是沿通道拼接；若 `skip_type=sum`，就是先 padding 对齐再逐元素相加。

`skip_concat` 源码行为：

```text
diffY/diffX = x2 spatial - x1 spatial
x1 = ZeroPad2d(...)(x1)
return cat([x1, x2], dim=channel)
```

硬件含义：

| skip 类型 | 算术 | 主要代价 |
|-----------|------|----------|
| concat | 不加法，通道拼接 | SRAM 读写、地址拼接、decoder 输入通道变宽 |
| sum | 逐元素加 | 对齐 padding、加法、同形状约束 |

所以 decoder 不是只从 bottleneck 往上采样，它每一层都要读一个 encoder output skip。对 NTS11/en4：

| decoder i | 代码索引 | 读到的 encoder output | 是否 downsample 前分叉 |
|-----------|----------|-----------------------|------------------------|
| 0 | `blocks[3]` | S3 output | 否，S3 无 downsample |
| 1 | `blocks[2]` | S2 output | 是 |
| 2 | `blocks[1]` | S1 output | 是 |
| 3 | `blocks[0]` | S0 output | 是 |

因此“downsample 分叉”只有 0/1/2，但“decoder encoder-skip 输入”有 3/2/1/0 四个。

### 3.8 Decoder previous prediction feedback

decoder 还有第二条 skip：

```text
if i > 0:
    x = self.skip_ftn(predictions[-1], x, dim=2)
```

也就是说从第二个 decoder stage 开始，上一尺度的 `pred_out` 会反馈到当前 decoder 输入。硬件上需要保存上一尺度 prediction，并在下一尺度 decoder 前参与 concat/sum。

这条路径容易被漏掉，但对控制很重要，因为它让 decoder 输入不仅依赖：

```text
bottleneck feature + encoder skip
```

还依赖：

```text
previous multires prediction
```

### 3.9 最终 flow 的时间维求和

`SpikingformerFlowNet.forward` 里每个 multi-resolution prediction 会做：

```text
flow = torch.sum(flow, dim=0)
interpolate(flow, original_H, original_W)
```

所以最后输出不是保留 `T` 维的 event tensor，而是把时间步上的 flow prediction 累加成普通 flow map，再插值到输入分辨率。

硬件上这对应一个 time-reduction accumulator 和 resize/postprocess 单元。第一版 DATE 方案可以把 resize 作为片外/后处理，但论文评估口径要说明是否计入。

### 3.10 residual / skip 生命周期表

| 路径 | 产生位置 | 消费位置 | 生命周期 | 建议存储 |
|------|----------|----------|----------|----------|
| Swin ADD0 shortcut | 每个 Swin block 输入 | 同 block H60 后 | 极短 | local RF / line buffer / activation SRAM bank |
| Swin ADD1 shortcut | ADD0 输出 | 同 block MLP 后 | 极短 | local RF / activation SRAM bank |
| S0/S1/S2 stage skip | BasicLayer downsample 前输出 | decoder 对应尺度 | 长 | encoder skip SRAM |
| S3 final-stage skip | 最后一层 BasicLayer 输出，无 downsample | bottleneck 后的 decoder0 | 中到长 | 可留 activation SRAM，也可写 encoder skip SRAM |
| Downsample output | PatchMerging 后 | 下一 stage | 中 | ping-pong activation SRAM |
| Patch residual identity | patch residual block 输入 | 同 residual block 末尾 | 短 | local activation buffer |
| Bottleneck identity | bottleneck resblock 输入 | 同 resblock 末尾 | 短 | local activation buffer |
| Prediction feedback | decoder 上一尺度 pred | 下一 decoder stage | 中 | prediction buffer |
| Time-reduction accumulator | multi-res flow T 步输出 | flow map 输出 | 中 | accumulator buffer |

### 3.11 硬件设计口径修正

因此 NTS11 的正确硬件叙事是：

```text
统一 H60 attention core
+ Swin residual shell
+ encoder skip SRAM
+ decoder feedback skip
+ shared ATLIF / MAC / add-concat datapath
```

不是：

```text
统一 H60 attention core 替代整网所有计算
```

这也会影响 profiling 清单。除了 ATLIF count、Shiftmax count、spikes、energy，还要补：

1. S0/S1/S2 pre-downsample skip tensor 的 shape 和写回字节数；
2. S3 final-stage output 在 bottleneck 期间的保留方式和字节数；
3. 每个 decoder stage 读 encoder skip 的字节数；
4. prediction feedback 的 shape、通道数和读写字节数；
5. Swin block ADD0/ADD1 的逐元素加次数；
6. concat skip 后 decoder 输入通道膨胀比例；
7. time-reduction accumulator 的输出尺度和累加次数。

## 4. 阶段 2：看懂每一步数据格式

### 4.1 为什么数据格式比公式更重要

硬件真正关心的是：

```text
这个数据几 bit？
一拍读多少？
存在 SRAM 哪个 bank？
下一模块按什么顺序消费？
```

同一个数学公式，在硬件上可能因为数据格式不同，面积和功耗差很多。

### 4.2 当前 all-binary 主线里最重要的数据类型

| 数据 | 逻辑含义 | 建议硬件格式 |
|------|----------|--------------|
| voxel grid | 事件栅格输入 | 定点或 FP16，第一版可视为片外输入 |
| activation | ATLIF 前的连续值 | 定点，后续需要量化 sweep |
| binary ATLIF event | 二值脉冲 | 1-bit |
| Q event | H60 query event | 1-bit packed |
| K event | H60 key event | 1-bit packed |
| TX/SC score | token consensus score | INT16 或更窄定点 |
| Shiftmax gate | token gate | INT8 当前已验证误差很小 |
| gated-K output | attention 输出 | INT accumulator |
| skip feature | encoder long skip / residual shortcut | 1-bit event 或定点 activation，取决于位置 |
| flow | 最终光流 | 定点或 FP16 输出 |

这里最重要的变化是：

```text
Q/K 不再按主路径 2-bit ternary event 学；
当前硬件主线按 1-bit Q/K event 学。
```

旧的 ternary 设计可以作为 ablation 或备选路线保留在论文 discussion 里，但你学习 RTL 和数据流时应该先按 all-binary 理解。

### 4.3 binary event 是什么

binary ATLIF 输出：

```text
0 或 +1
```

硬件可以用 1 bit 表示：

```text
0 = no spike
1 = positive spike
```

这种数据适合：

1. MLP；
2. projection；
3. resblock；
4. decoder 中仍保留 spiking neuron 的地方；
5. all_non_qk wrapper 覆盖的路径。

### 4.4 ternary event 现在怎么理解

ternary event 是早期 NTS11 的重要探索，它表示：

```text
-1, 0, +1
```

常见 2-bit 编码是：

```text
00 = 0
01 = +1
10 = -1
11 = reserved / mask
```

但当前 all-binary 主线里，不要把它当成主路径。你只需要知道：

1. ternary 会让 Q/K compare 变成 same/opposite/one-sided/both-zero 分类；
2. ternary event SRAM 至少要 2-bit/element；
3. ternary gated-K 需要 add/sub/skip；
4. all-binary 去掉了负事件和 opposite polarity 分类，所以硬件更好讲。

### 4.5 Q/K event 为什么重要

H60 的核心输入不是 dense Q/K tensor，而是 binary Q/K event。

传统 attention：

```text
score = Q @ K^T
```

当前 UniBin-H60：

```text
Q_event, K_event ∈ {0, 1}
→ AND / OR / popcount
→ popcount
→ TX/SC score
```

这意味着硬件可以少做乘法，多做比较、计数和加法。

当前 RTL 里的核心统计量是：

```text
q_active = popcount(Q)
k_active = popcount(K)
overlap  = popcount(Q & K)
mismatch = q_active + k_active - 2 * overlap

TX = overlap
SC = overlap - mismatch
score = TX + μ * SC
```

这就是你需要先学会的 H60 score，不要一开始陷入 softmax 或 dense matrix multiplication。

|----------|----------|----------|------|------|

| ATLIF binary | activation | binary event | 1-bit | 当前主路径 |
| H60 score | Q/K 1-bit event | score | INT16 | overlap/mismatch |

## 5. 阶段 3：看懂 ATLIF wrapper

### 5.1 ATLIF 在当前主线里解决什么问题

ATLIF 的作用是把连续 activation 变成 sparse event。

软件里看起来有很多 ATLIF wrapper logical site，但硬件上它应该统一成一个共享 event encoder。当前 all-binary 主线里，第一版硬件只需要把 ATLIF 输出统一理解成：

```text
event ∈ {0, 1}
```

也就是没有负事件、没有 ternary packer、没有 dual rail event SRAM。

### 5.2 当前先学 binary ATLIF

binary ATLIF：

```text
if x_centered > threshold:
  event = +1
else:
  event = 0
```

硬件动作是：

```text
read activation
read center / threshold
x_centered = activation - center
compare
pack 1-bit event
write event SRAM
```

当前你只需要知道 ternary ATLIF 是被 all-binary 主线绕开的复杂度来源。它可以以后作为论文 ablation 或未来扩展，不作为第一版硬件学习重点。

### 5.3 center 和 threshold 是什么

很多 ATLIF 不只是比较 `x` 和阈值，还会用 center：

```text
x_centered = x - center
```

然后再比较：

```text
x_centered > +threshold
x_centered < -threshold
```

硬件上就意味着需要：

1. threshold SRAM；
2. center SRAM；
3. subtract；
4. comparator；
5. 1-bit event packer。

### 5.4 为什么 105 个 ATLIF 不等于 105 套硬件

NTS11 的 `105` 是模型里需要被 ATLIF wrapper 覆盖的位置数量。  
硬件可以用同一组 comparator lanes 反复处理不同位置。

硬件 descriptor 告诉 ATLIF unit 当前处理谁：

```text
module_id
input_base_addr
output_base_addr
threshold_addr
center_addr
shape
event_mode = binary
pack_format
```

这就是“logical site”和“physical unit”的区别。

### 5.5 你要画的 ATLIF wrapper 图

```text
activation SRAM
     |
     v
[read activation tile]
     |
     v
[read threshold / center]
     |
     v
[subtract center]
     |
     v
[comparator lanes]
     |
     +--> binary packer  --> 1-bit event SRAM
```

## 6. 阶段 4：看懂 H60 attention 内部数据流

### 6.1 H60 是 NTS11 的核心

NTS11 的硬件故事成立，是因为 encoder attention 全部统一成 H60。

一个 H60 block 内部可以拆成：

```text
Q/K event encode
→ TX/SC score
→ Shiftmax
→ gated-K accumulation
→ output projection / next path
```

### 6.2 H60 输入是什么

输入是：

```text
Q_event: 1-bit binary packed vector
K_event: 1-bit binary packed vector
```

按 window/head/token/channel 组织。  
一个 window 里有多个 token，每个 token 有多个 channel。

你暂时不需要记住每个 stage 的精确 shape，但要知道：

```text
S0 window 多，分辨率高；
S3 window 少，通道深；
H60 engine 不变，descriptor 变。
```

### 6.3 TX score 怎么算

当前 all-binary 主线把 TX 理解成 Q/K 的共同激活数量：

```text
TX = popcount(Q & K)
```

也就是：

| Q | K | 是否贡献 TX |
|---|---|---|
| 0 | 0 | 否 |
| 0 | 1 | 否 |
| 1 | 0 | 否 |
| 1 | 1 | 是 |

硬件上就是 AND 后接 popcount。

### 6.4 SC score 怎么算

当前 all-binary 主线把 SC 理解成 overlap 和 mismatch 的 consensus：

```text
q_active = popcount(Q)
k_active = popcount(K)
overlap  = popcount(Q & K)
mismatch = q_active + k_active - 2 * overlap
SC       = overlap - mismatch
```

直觉是：

```text
Q/K 同时 active → 加分
只有一边 active → 扣分
两边都 inactive → 不贡献
```

### 6.5 TX/SC 为什么能共享硬件

TX 和 SC 都需要同一组基础统计量：

```text
popcount(Q)
popcount(K)
popcount(Q & K)
```

所以硬件不应该为 TX 和 SC 各做一套 datapath，而应该共享：

```text
Q/K bit reader
AND lane
popcount tree
small adder/subtractor
μ scaling
score saturator
```

这就是论文里可以讲的 **Binary Consensus Score Engine**。

### 6.6 Shiftmax 做什么

H60 不用 softmax，而用 Shiftmax：

```text
gate_i = 2^score_i / 2^ceil(log2(sum_j 2^score_j))
```

硬件分成：

```text
score
→ exp2 LUT
→ sum reduction
→ ceil(log2)
→ right shift normalize
→ gate
```

为什么它硬件友好：

1. `2^x` 可以 LUT；
2. 除法近似成 shift；
3. 输出 gate 是定点；
4. 不需要完整 softmax exp/div。

当前 DC-ready RTL 里是一个 INT8-ish scaffold：

```text
row max
→ exp2 approximation
→ row sum
→ gate_from_exp
```

它能跑通综合和仿真，但还需要和 PyTorch deployment quant 的 golden vector 做 bit-accurate 对齐。

### 6.7 gated-K 做什么

有了 gate 后，输出不是 dense V matmul，而是：

```text
output_i = Σ_j gate_ij * K_event_j
```

当前 all-binary 里如果只看 K event：

```text
K = 1 → 输出 gate × K_value 或加权事件
K = 0 → 跳过
```

所以 gated-K 不需要 dense V matmul。若 K carrier 是多 bit value，仍需要小位宽乘法或 shift/add；若 K 也完全 event 化，则可以进一步变成 add/skip。

## 7. 阶段 5：看懂 SRAM、buffer 和 descriptor

### 7.1 为什么 SRAM 是硬件设计核心

很多时候硬件不是算不动，而是数据搬不动。

NTS11 的关键 buffer 至少包括：

| buffer | 内容 | 格式 |
|--------|------|------|
| activation buffer | ATLIF 前后 feature | 定点 / FP |
| binary event SRAM | binary event | 1-bit packed |
| optional ternary event SRAM | 旧版/备选 ternary ablation | 2-bit packed，当前主线不作为必需项 |
| score buffer | TX/SC/fused score | INT |
| gate buffer | Shiftmax gate | INT |
| threshold SRAM | ATLIF threshold | 定点 |
| center SRAM | ATLIF center | 定点 |
| descriptor SRAM | layer/block 参数 | control words |
| weight buffer | conv / MLP weights | INT / fixed |

### 7.2 为什么需要 packed event SRAM

如果 binary event 用 8-bit 存，就浪费 8 倍空间。当前主线最重要的是把 Q/K 和 ATLIF event 都压成 1-bit packed。

建议：

```text
binary event: 1 bit / element
optional ternary event: 2 bit / element，只用于备选实验
```

这样 Q/K event traffic 才能真正体现 event coding 的优势。

### 7.3 descriptor 是什么

descriptor 是控制器给共享硬件单元的一组参数。

例如一个 H60 block descriptor：

```text
stage_id
block_id
num_heads
head_dim
num_windows
tokens_per_window
q_event_base
k_event_base
score_base
gate_base
output_base
threshold_base
center_base
```

一个 ATLIF descriptor：

```text
module_id
event_mode
input_base
output_base
threshold_base
center_base
num_elements
pack_format
```

### 7.4 你要画的 SRAM 表

画一张表：

| SRAM | 谁写 | 谁读 | 数据格式 | 是否按 stage 复用 |
|------|------|------|----------|------------------|
| Q event SRAM | ATLIF Q | H60 score | 2-bit | 是 |
| K event SRAM | ATLIF K | H60 score/gated-K | 2-bit | 是 |
| score SRAM | H60 score | Shiftmax | INT | 是 |
| gate SRAM | Shiftmax | gated-K | INT | 是 |
| binary event SRAM | ATLIF | Sparse MAC | 1-bit | 是 |

### 8.1 模块接口要解决什么

| 字段 | 含义 |

#### 7.3.3 Shiftmax unit

## 9. 阶段 7：看懂调度

### 9.1 调度是什么

调度就是：

```text
哪个 engine 在什么时候处理哪一块数据。
```

NTS11 的调度不是按 PyTorch module 创建硬件，而是按 descriptor 复用硬件。

### 9.2 一帧推理的粗调度

```text
frame_start

run event_scatter
run patch_embedding

for stage in [S0, S1, S2, S3]:
  for block in stage.blocks:
    run ATLIF encode Q/K
    run H60 score
    run Shiftmax
    run gated-K
    run projection
    run MLP

  if stage has downsample:
    run downsample

run bottleneck_resblock
run decoder
run flow_head

frame_done
```

### 9.3 细一点的 H60 调度

```text
for head in heads:
  for window in windows:
    load Q/K event tile
    compute TX/SC score
    run Shiftmax
    run gated-K
    write output tile
```

进一步考虑 Timestep：

```text
for bundle in window × timestep_group:
  if bundle empty:
    skip
  elif bundle sparse:
    run sparse lane
  else:
    run dense/vector lane
```

这就是后续 `UniH60-Bundle` 的基础。

### 9.4 为什么 NTS11 比 mixed datapath 好调度

NTS07/09 的问题：

```text
部分 block 走 H60
部分 block 走原生 QKFormer attention
可能还有 carrier / PSN 混合路径
```

控制器要在不同 attention ISA 之间切换。

NTS11：

```text
encoder attention 恒为 H60
stage 差异只体现在 descriptor
```

所以 controller 更像一个统一 H60 scheduler。

## 10. 阶段 8：看懂面积、功耗、吞吐口径

### 10.1 面积怎么算

面积按物理单元算，不按 logical site 算。

错误口径：

```text
area = 105 × ATLIF + 12 × Shiftmax
```

正确口径：

```text
area =
  ATLIF encode lanes
  + H60 classify/popcount lanes
  + Shiftmax LUT/reduction
  + gated-K accumulator
  + sparse MAC lanes
  + dense decoder MAC
  + SRAM banks
  + controller / DMA
```

### 10.2 功耗怎么算

功耗至少拆成：

| 项 | 为什么重要 |
|----|------------|
| event SRAM read/write | event 多时通常是大头 |
| Q/K event buffer | H60 每个 block 都用 |
| score/gate buffer | Shiftmax 需要 |
| ternary compare/popcount | H60 score |
| gated-K accumulator | attention output |
| sparse MAC | MLP/downsample/projection |
| dense decoder | decoder 仍可能很贵 |
| controller/DMA | 调度与搬运开销 |

### 10.3 吞吐怎么算

一帧 latency：

```text
latency_frame =
  latency_scatter
  + latency_patch
  + latency_S0
  + latency_S1
  + latency_S2
  + latency_S3
  + latency_bottleneck
  + latency_decoder
```

H60 block latency：

```text
latency_h60 =
  latency_qk_encode
  + latency_tx_sc_score
  + latency_shiftmax
  + latency_gated_k
  + latency_writeback
```

### 10.4 NTS11 当前硬件数字怎么看

已有统计：

| 方案 | total_spikes | energy | H60 blocks | ATLIF |
|------|--------------|--------|------------|-------|
| NTS07b | 36.8003G | 31581.35 uJ | 6 | 34 |
| NTS09e | 38.9417G | 31845.17 uJ | 6 | 34 |
| NTS11bj | 29.0414G | 23032.66 uJ | 12 | 105 |

解释：

1. NTS11 logical site 更多；
2. 但 total spikes 和 energy 更低；
3. encoder attention 数据流更统一；
4. 需要用共享硬件和 descriptor 复用来避免面积爆炸；
5. 需要补 gate/bundle profiling 来证明结构化 skip 可用。

## 14. 当前最重要的提醒

NTS11 的 DATE 故事不是：

```text
模块更少。
```

而是：

```text
数据流更统一。
```

NTS07/09 看起来模块少，但硬件要支持 mixed datapath。  
NTS11 看起来 ATLIF/Shiftmax logical site 多，但 encoder attention 全部统一成 H60，可以讲成一个共享 event-attention ISA。

所以你学习时要一直问：

```text
这个模块是不是同一套硬件可以复用？
这个数据是不是同一种 event 格式？
这个 stage 差异是不是只需要 descriptor 改参数？
```

能回答这三个问题，才算真正开始进入硬件设计。
