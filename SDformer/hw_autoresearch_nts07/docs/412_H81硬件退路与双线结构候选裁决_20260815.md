# H81 硬件退路与双线结构候选裁决

本文件独立复核 `docs/411`，不修改生产 RTL 和

## 1. 结论

1. H81 不会让现有硬件推倒重做。它是 H67 score 算子的编译期子模式：
   `binary_motion_xor_alpha=0`。
2. H81 目前不能替换硬件主线。它没有 MVSEC、硬件 trace 或 RQTB 等价率，且
   H67/H81 只是 recipe-level control，不是逐优化步骤因果消融。
3. 如果后续算法选择 H81，现有 Q/K store、temporal-pair layout、RQTB packet、
   weighted SCS/Shiftmax、K recovery、projection、Acc 和 12-block 调度均可复用；
   需要替换/特化的是 score-front，并重新生成全部 checkpoint-bound 证据。
4. Local5 不是因为 H81 出现就作废。它仍是独立五邻域模型/数据流，但在 MVSEC
   单序列失败和 RTL checkpoint 未对齐前，不能写成跨数据集精度主线。
5. 本轮两个结构协同候选均 NO-GO，不以新模型为借口继续扩 RTL。

当前分数不变：Motion 创新 `3.2/5`、Local5 创新 `3.1/5`；两线综合均约
`3.1/5 Borderline Reject`。

## 2. H81 对现有硬件的真实改动

冻结 H67 score 为：

```text
score_t = RNE(4*overlap_t + motion(K0 xor K1) + same_zero_t/16)
```

H81 只是：

```text
score_t = RNE(4*overlap_t + same_zero_t/16)
```

`rtl_h67/h67_motionxor_score_q7.sv` 已有 `ENABLE_MOTION_XOR` 参数，因此叶级
算术能力已经存在。当前问题是若干 H67 wrapper 将该参数硬连为 `1'b1`，以及 MSSB5
固定归约五个统计字段。这是编译期特化问题，不是新 attention 后端。

| 流水阶段 | H81 是否复用 | 需要的动作 |
|---|---|---|
| 64-bit temporal Q/K pair layout | 全复用 | 无 |
| dual-bank K store / FIFO / backpressure | 全复用 | 新 trace 回归 |
| score-front | 部分复用 | motion 关断；MSSB5 改成四统计特化或使用双 direct no-motion |
| score equality / RQTB packet | 逻辑全复用 | 必须先测 H81 pair equality，重做公平周期 |
| weighted SCS / Shiftmax | 全复用 | 重新验证 score class/denominator 范围 |
| ordered K recovery | 全复用 | 新 gate/K miter |
| projection / Acc32 | 全复用 | 绑定 H81 checkpoint 权重 |
| 12-block scheduler / shell | 全复用 | 绑定 H81 stage/head trace |

因此可复用的是 score 之后的完整数据通路和大部分 score 之前的存储/接口；不能复用的
是 H67 score 数值证据和由该数值分布得到的周期/PPA结论。

## 3. 如果 H81 后续成为算法主线

### G0：先判定，不改 RTL

算法侧必须导出 H81 选定 checkpoint 的：

- all12、T450、hardware-order Q/K/score/gate trace；
- 至少 10 sample，并按 scene、事件密度和 stage 分层；
- valid825 与 MVSEC 身份、checkpoint/config SHA；
- QF5-QF8 最终部署位宽。

硬件侧只读计算：

- no-motion score 的 pair equality、RQTB slot 和 class occupancy；
- score、SCS/Shiftmax、K-read、projection 的周期占比；
- Q/K temporal toggle，判断是否有编译期 clock-gating 机会；
- 与 H67 相同强基线下的预期 cycle/area/activity。

### G1：满足条件才接参数

仅当以下条件同时满足，才把 `ENABLE_MOTION_XOR` 贯穿生产 wrapper：

1. H81 被算法选择器正式选为 paper checkpoint；
2. H81 RQTB 相对 Fixed2S 的组件周期收益至少 `10%`，或相同吞吐下 EDP 预计至少
   `15%`；
3. score-front 特化不增加最坏关键路径和存储端口；
4. 所有 score/gate/K/Acc32 与独立整数参考零失配。

默认参数继续保持 H67 模式，禁止无 trace 先改封存主锚点。

### G2：H81 硬件证据重建

若 G1 通过，需要重做而不是沿用 H67 数字：

- H81 Fixed2S vs RQTB2S 多样本 Icarus/Verilator+SVA；
- 真实 INT8 全输出通道、bias/BN/requant/residual 边界；
- 同一公平 LFSR 的 VCD/SAIF；
- 同库、同 SDC、同 SRAM 宏的 DC/STA/PTPX；
- full-block/encoder Amdahl。

H81 模式是产品/模型兼容性，不单列为 DATE 新贡献。若 H81 的 RQTB 收益不足，不能
为了保留已有 RTL 强行把它写成 Motion 的替代主线。

## 4. 双线的论文退路

### 当前方案

- 算法主线仍为 H67 ep35：理由是已有 MVSEC 过门和完整硬件 provenance，不是
  DSEC 相对 H81 多出 `0.069%` AEE。
- Motion 贡献句只写：对冻结 H67 部署中真实存在的 Q7 temporal score 等价类进行
  可逆归并。不得写成精度来源。
- Local5 贡献句只写：固定五邻域下的 exact topology-resident execution。DSEC
  额外收益只能作为模型结果，并同时披露 MVSEC `indoor_flying1` 失败和硬件
  checkpoint 尚未更新。
- H81 进算法消融表，并显式说明它是 no-motion control、无独立硬件 provenance。

### 触发切线

1. 若 H81 后续拿到 MVSEC、spike/精度 Pareto 明显优于 H67，并且 H81-RQTB G0
   通过，则把同一硬件改成 no-motion 编译模式并重建证据；不新建第三套后端。
2. 若 H81 胜出但 RQTB G0 失败，Motion 硬件必须降为 H67 variant case study；论文
   需要重新选择主硬件对象，不能靠包装挽救。
3. 若 Local5 40→50、同 checkpoint RTL、MVSEC 和等面积 EDP 全部过门，才允许
   Local5 升为第一硬件贡献。
4. 若 H81-RQTB 与 Local5 都不过门，退路是缩稿为可信的专用 attention
   microarchitecture，或推迟投稿；不存在不经新证据直接达到 best-paper 的办法。

## 5. 本轮结构候选 NO-GO

证据：
`results/structural_codesign_candidate_screen_20260815/report.json`。

### Local5 topology-orbit

即使假设 self/vertical/horizontal 各自只生成一个 gate，并把两个 K 在线折成 2-bit
count：

- orbit term：`27,260,734`；
- 现有 source-owned term：`9,870,505`；
- orbit/source：`2.7618x`；
- 相对 raw edge-lane 仅少 `6.53%`。

它从 source-owned 跨 destination 复用退回 destination-owned，故无须训练或 RTL。

### Motion structural shared-score

在 ep35 十样本、1,380 行真实 Q/K 上，用三个 pair 统计生成单一共享 score：

- RQTB slot `342,973`，结构共享 slot `310,500`，增量上限仅 `9.47%`；
- gate exact token rate `88.19%`；
- projection 前 32-lane 聚合 relative-L1 p95 `3.61%`。

它不是冻结 H67 exact，且没有减少核心 160 个 lane predicate，只删少量 finalizer/
descriptor。按预注册 `10%` slot 门槛直接 NO-GO，不训练、不接 RTL。

## 6. 对用户问题的直接回答

1. **双线硬件不会因 H81 立即作废。** Motion 大部分硬件可作为 H81 的编译期子模式；
   Local5 是另一种模型/数据流。
2. **H81 后续可以做，改动是中等验证量、小到中等 RTL量。** 最大工作是重建
   checkpoint-bound 证据，不是重新设计 projection/存储后端。
3. **现在不应提前做 H81 RTL。** 没有 H81 trace 和 RQTB go/no-go，先参数化只会制造
   第三套无证据分支。
4. **真正的风险是论文叙事，不是代码资产。** Motion 必须从“精度引擎”收窄为
   “冻结 H67 的 exact 部署加速”；Local5 不能把单数据集增益写成泛化结论。
