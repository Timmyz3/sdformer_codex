# C1主问题改为复用驱动调度，而非端口微调

2026-09-05。用户再次明确：机制和对应执行组织优先，1RW是第二问题。
本文是下一版架构设计，不是新RTL/PPA结果。旧C1保留为直接基线。

## 1. 缺的不是一个调度器名字

旧C1已有stable popcount/index顺序、前瞻、两response槽、双目录buffer、
三段matcher与反压；不能说它完全没调度。但这些主要解决合法性和握手，
没有根据复用结果的实际位置、等待和剩余消费者主动编排工作。

[Prosperity §V-D/VI](https://arxiv.org/html/2503.03379v1)的闭环包括关系
检测、prefix剪枝、快速顺序生成、地址供数和两阶段流水；只拿subset式子
而把这些当免费模型就不完整。也不能把“再加stable sort或double buffer”
当新机制，因为两边都已经有相关结构。

下一版统一问题：**已发现的复用，怎样变成实际执行和访存收益？**
先固定forest，把调度差测干净；随后才改parent选择。不是同时加四个matcher。

## 2. 机制一：由就绪集合发射，不被固定下一行卡住

先把选好的parent关系做成可直接消费的紧凑目录：每行parent、first-child、
next-sibling和consumer count。单parent forest只有线性条数的边，不需要
保存检测器产生的全部候选邻接矩阵。链表/forest本身不是新数据结构。

设计候选在matcher输出父边时同步插入child链、更新计数；执行时在线
生成下一工作，不再先单独遍历整棵树、物化完整DFS顺序后才开算。
这不是免费重叠承诺：连续两个child更新同一parent时有RAW hazard，
head/next/degree写口和转发要实现，构建仍按真实II/延迟计入时间线。
初始化必须在整个bank开始匹配前完成：parent原始ID可以大于child，不能
处理到parent行才清零head/degree，否则会删掉先插入的孩子。第一版等
当前任务的所有父边建立完成才执行/释放，避免把尚未发现的孩子误认为零。
在线唤醒仍需读child边；fanout超过窗口容量时用游标继续，计入访问/
等待周期，不把省掉全树预遍历说成零调度成本。

在当前已加载的64-row任务内，保持原parent和residual不变。引入有限
ready window，例如8行；发射条件是root，或其parent已完成且结果能合法供给。
等待parent读取的行仍保留自身身份；独立就绪行可先执行。

初始优先级采用可实现的词典序，不假设一个免费精确cost oracle：

1. 当前计算结果可直接转发，或parent已在保留槽；
2. 当前行完成能释放parent，且不会增加活跃结果数；
3. 普通就绪行按年龄处理。窗口无法推进时回到最老合法任务。

某行结果是否需要保留与它的后继相关；估计活跃结果变化可用
`has_children(row) - is_last_consumer(parent)`，不必在线求全森林最优序。
分支树上DFS不总最好，所以“换成DFS”不是最终调度方案。

关键硬件变化是**请求/返回不再靠FIFO位置隐式指认消费者**：要携带
row、parent、task/weight identity和pending状态。候选选择、元数据端口、
窗口填充、空泡、输出重排都收费。保持一个96-lane算术池，不偷偷增PE。
第一版只在行边界选择，不抢占已经部分累加的行；绕过计算途中的stall
需要额外累加context，不能用目前8-entry metadata窗口免费代替。
parent预取顺序也必须来自候选/child目录；只改最终选择器、仍按旧固定
consumer序填response FIFO，通常没有其他已返回的任务可供绕过。

示例，仅说明依赖与寿命，不用作速度测量：

- P={0,1}，Q={4,5}，A=P+{2}，B=Q+{6}，C=A+{3}；
- 稳定popcount顺序可能为P,Q,A,B,C；
- 合法亲子相邻顺序为P,A,C,Q,B，P/A的结果可更早用完。

这里只改变同一个任务内独立输出行顺序，不改变SNN timestep递推，
不跨BN屏障，不把不同kernel tap下的乘积当同一个结果。

## 3. 机制二：槽属于parent结果，而不是某一笔读请求

现有response槽主要保存一次请求对应的返回，多个孩子可重复请求同一
parent。候选把槽改为短期结果保留结构：一个完整身份tag对应一个payload，
允许当前任务的多个孩子消费它，最后消费者真正完成后才释放。

优先研究**复用现有两份1152-bit槽**的实现，而不是默认在原两槽之外
再加两个hot槽。新增的主要是tag、消费者/引用状态、等待者唤醒与释放控制；
是否需要额外buffer由实际并发冲突决定，不预写“零面积”。

结果刚算好且后继将使用时，直接转发/保留；暂时放不下的结果才考虑落
backing SRAM。父结果保留和architectural psum commit是两条不同通路：
省掉parent写不等于省掉最终输出写。

还需一个前进保证：两个槽都被长寿命parent占住、下个需求miss时，必须
能把一个victim可靠写到backing后释放并预留incoming位置。不能在没有
逃生路径时让“保留到最后消费者”锁死所有返回credit。第一版不删除
backing路径，且同一份payload不得同时被释放与授予不同identity。

不能免费假设2R1W：若同拍需要读取一个hot parent、读出另一个victim
去spill、同时写入新结果，必须仲裁、分拍或增加真实端口。第一版宁可
计入分拍，也不把三项活动挤进一拍后声称收益。

这与机制一相互依赖：没有亲子调度，槽很快被远期消费者占满；没有
结果保留，重排行序可能仍把每个parent写了又读。应联合设计、分项消融。

## 4. 机制三：检测/供数/提交与复用执行共同流水

不能只写一个`max(preprocess, compute)`就当已经隐藏检测。新调度器必须
给出逐拍时间线：下个任务何时载入、关系何时可用、就绪窗口何时形成、
parent/weight何时请求、返回槽何时被消费、architectural commit何时接受。

旧C1已有双buffer，这里要完善的是新顺序下仍能成立的可执行重叠：

- 关系表和窗口建立能否与上一任务执行重叠；
- parent预取是否针对窗口内可执行行，而非仅固定下一条；
- 计算能否绕过未返回的parent，且不污染两个独立行的累加状态；
- 输出ID与K-partition的累加次序是否被下游接受；若需要reorder/holding
  队列，必须计入。不得靠外部无限ready隐藏新增等待。

metadata可在原有多个输出channel block间复用，但这已经是既有分块优势，
不能再次计成新调度收益。真实卷积的tap/halo和psum地址也不能从调度账中消失。

## 5. parent选择留到第二阶段，而不是先上Top-4

先固定forest才知道改进来自调度。若进一步分析发现某些父边虽然少算，
却造成明显等待/保存成本，再考虑按实际可供给性选择parent或取消复用。
比较项包含残余issue、parent读取/保留和等待，而不只是subset popcount。

只用已加载任务和真实驻留/就绪状态。改变父边后同步更新residual、
依赖和剩余消费者。当前任务内没有驱逐，不能用“首选被驱逐”虚构备用收益。
多个备选中择一也不同于同时叠加多个prefix：后者还需避免重复计数。

## 6. 可检验的开发与对比顺序

| 版本 | 回答的问题 |
|---|---|
| 旧C1固定序/请求槽 | 直接现有实现基线 |
| 同forest，普通DFS/普通forwarding | 排除教科书顺序和旁路本身的收益 |
| 普通DFS＋同样两份parent-owned payload | 排除便宜静态顺序与保留的协同；不额外加两hot槽 |
| 同forest，仅ready-window | 绕过等待是否减少空泡 |
| 同forest，仅parent-owned槽 | 重复请求/物化是否减少 |
| 两者结合，真实phase overlap | 是否形成净收益，控制开销是否反噬 |
| 同一动态ready机制，age-first与reuse/lifetime优先级 | 隔离新优先级，而不是把普通就绪调度算成原创 |
| 可选cost-aware父边 | 关系选择是否还有独立增量 |

同trace、同算术宽度、同容量预算；同容量不自动等于同面积。先报告：
算术issue、依赖/队列/供数/commit等待、parent读写、槽占用、元数据构建、
总周期。随后VCS和实际宏下的面积/时序/能量。1RW/DP放在次级DSE轴，
不能为突出调度故意只给基线弱端口。

已有M2260线程序+新增2hot槽仅是CPU线索：局部phase 1.06724×，parent
backing访问−97.71%，无跨tile重叠却0.98585×。它既未复用现有response槽，
也未实现ready-window，不能用来冒充本设计的收益；它恰好说明“顺序+
保留+流水”的闭环必须一并验证。不能将该比值乘到旧1.6945×上。

本轮新增M2269在相同3样本/15,552 tiles中观察旧调度：56,166个行首
等parent的周期里，后7行仅8,139周期存在root可算，存在queued-parent可算
的周期为0；总服务周期713,655。此结果不是OOO重放或收益上界，新顺序
会改变后续状态；但它说明**只叠一个ready选择器而不改预取/槽归属很弱**。
候选必须联动关系目录、预取、结果驻留，而非把三个名字并排。
独立审阅指出queued-parent=0主要由旧按consumer顺序的FIFO不变量导致，
不是数据集中不存在独立parent复用；8,139是周期数，可能重复看到同一个root。

## 当前裁决

优先完善**就绪调度与parent结果生命周期联动的C1执行器**，不先做端口
升级、不先开多候选matcher，也不再用模块数量给新颖性打分。
目标是把已有复用机会变成一个完整可解释的硬件机制；能否成为期刊主贡献，
取决于上述强消融后的增量，而非“学全Prosperity”或换一个新名字。
