# M496 r2 OOM 独立打铁审阅

日期：2026-08-27  
审阅范围：只读检查 `m496_fc2_three_axis_matched_logic_only_dc_3p000ns_r2_20260827`、冻结 runner/TCL/contract、Synopsys crash snapshot 和 Linux `/proc` 资源证据。未启动 VCS、DC、Formality 或 PT；未修改 RTL 与 `docs/359`。

## 裁决

**`PASS_RESOURCE_FAILURE__NO_PPA__EXACT_RESOURCE_GATED_R3_REPLAY_ONLY`（94/100）**。

M496 r2 是主机资源分配失败，不是 RTL 结构错误、约束失败或已经得到的负 PPA 结果。最接近的根因是共享主机在 `vm.overcommit_memory=2` 下接近 commit admission 上限；由于 crash snapshot 没有保存当刻 `CommitLimit/Committed_AS`，对“严格 overcommit 是唯一机制”的置信度低于对“资源类失败”的置信度。r2 全部 PPA/面积/时序门均未执行完成，不得引用，也不得据此 KILL K8/K1/K1x8。

## 直接证据

| 证据 | 观察 | 判定 |
|---|---:|---|
| runner | `runner_exit_code=20`，K1 `dc.rc=1` | fail-closed 正常工作 |
| DC 进度 | analyze、elaborate、link、uniquify、precompile checks 均完成；死于 `Beginning Pass 1 Mapping` | 不支持 RTL elaboration/结构失败 |
| DC 分配失败 | 已分配 `2,254,272 KiB`，追加请求仅 `8,192 B` 即 OOM | 典型资源 admission 失败 |
| crash 时 DC 进程 | `VmSize=4,074,168 KiB`、`VmRSS=2,101,268 KiB`、3 threads | 无进程地址空间/线程硬限制证据 |
| crash 时主机 | `MemFree=15,734,344 KiB`、cache `415,011,716 KiB`、`SwapFree=57,369,596 KiB` | 共享主机空闲页偏低，但不是 kernel OOM |
| VM 策略 | `overcommit_memory=2`、`overcommit_ratio=90` | malloc 可在物理可回收页很多时因全局 commit 被拒绝 |
| crash 后约 3 分钟抽样 | `CommitLimit=541,608,164 KiB`、`Committed_AS=522,955,080 KiB`，余量仅 `13,332,564 KiB`（2.462%） | 强支持共享 commit 压力；不是 crash 同刻的完整证明 |

`check_design_precompile.rpt` 中存在大量 LINT-31/32/33/52 类连线告警，日志也有综合时忽略 simulation-only `$fatal` 的 VER-104；它们均早于 mapping 且没有触发 runner 的 unresolved/multiple-driver/latch/fatal 门，不能解释本次 8 KiB 分配失败。若后续完整综合产生 postcompile 错误，仍须按原 fail-closed 门另行裁决。

## 三类失败归因

| 类别 | 分数 | 说明 |
|---|---:|---|
| 主机/资源 | **0.95** | DC 明确 OOM；严格 overcommit、低 commit headroom、共享主机高负载相互吻合 |
| 工具内部缺陷 | 0.04 | fatal stack 是 OOM 后果；若资源门满足后稳定复现，才升级此项 |
| RTL/综合结构 | 0.01 | elaboration/link/check 已过；当前没有映射结果证明结构不可综合 |

对精确机制的判断：`strict-overcommit/global-commit-pressure` 置信度 **0.82**。保留 0.18 给未保存 crash 时 `Committed_AS`、DC 私有 allocator 或 `vm.max_map_count` 等次要可能。

## 最小恢复合同：M496 r3 resource replay

恢复目标只是得到原 r2 合同定义的三个同框结果；不得借 OOM 改变优化自由度或偷面积。

1. 新建不可覆盖的 r3 run 目录；r2 永久保留 `FAILED_OR_INCOMPLETE_DO_NOT_CITE`。
2. 冻结 r2 的 RTL、filelist、SDC、TSMC28 slow/fast DB、DC V-2023.12-SP3、3.000 ns、ideal clock、ZeroWireload、三个 `ARCH_MODE`、端口以及原硬门。
3. **TCL compile body 必须逐字保持**：`ungroup -all -flatten`；`compile_ultra`；`compile_ultra -incremental`；`compile -incremental_mapping -only_hold_time`。不得删除第二轮、不得降为 `compile`、不得降低 map/area effort、不得只综合能通过的点。
4. 三点仍按 K1→K8→K1x8 串行执行；每点独立从 analyze/elaborate 开始，禁止复用中间 mapped DDC。
5. 启动前及每个 point 之前，对 `/proc/meminfo` 做 3 次、间隔 10 秒的资源门控；三次都必须满足：
   - `CommitLimit - Committed_AS >= 64 GiB`；
   - `MemAvailable >= 128 GiB`；
   - `SwapFree >= 32 GiB`；
   - cgroup `memory.failcnt` 不增长且 `under_oom=0`；
   - 无其他 `dc_shell/common_shell_exec/fm_shell/pt_shell`，并遵守项目既定“不与 VCS 或 CPU DSE 并发”。
6. 保存每次 `/proc/meminfo`、cgroup 状态和进程清单到 r3 evidence；DC 运行期间每 10 秒记录一次，不把动态主机状态伪装成设计 PPA。
7. 任一点出现 allocation failure、fatal、输入漂移、缺报告或电气/时序失败，整个 r3 继续 fail-closed；不得拿另外两点的局部结果拼表。
8. 仅当三个点均产生原合同要求的 reports/netlist、五类 constraint clean、setup/hold clean、相同 port count 后，才计算面积与 throughput/mm² gate。

64 GiB commit headroom 不是设计需求估计，而是共享主机安全门：它约为当前 CommitLimit 的 12.4%，也显著高于本次进程约 4 GiB 的 `VmSize` 和 crash 后观测到的 12.7 GiB 余量。该阈值需要在 runner 中冻结，不得在失败后临时下调。

## `set_host_options`、flatten 与 compile 策略裁定

| 改动 | r3 是否允许 | 理由 |
|---|---|---|
| 保持当前默认单核 | **允许且首选** | DC header 已报告 `Cores = 1`；这是最小 exact replay |
| 加 `set_host_options -max_cores 1` | r3 不建议；仅新合同下条件允许 | 与已观察运行等价，但会改变 TCL 身份；不能治疗全局 commit 压力。若采用，三个点必须全部从头重跑 |
| `-max_cores > 1` | **禁止** | 增加并行资源压力，也改变编译执行条件 |
| 删除/弱化 `ungroup -all -flatten` | **禁止** | hierarchy boundary 会改变三个架构的优化自由度与面积公平性 |
| 用分层/partition compile | r3 禁止 | 可作为 resource-gated r3 仍复现 OOM 后的新 r4 方法学，但必须三点同改、重立 contract，且不能与 r2/r3 面积直接拼接 |
| 降低 compile/map/area effort 或跳过 incremental | **禁止** | 会系统性影响面积/时序，构成“靠低 effort 偷面积” |
| 改点顺序或复用 mapped DDC | **禁止** | 会把资源历史/缓存差异引入三点比较 |

如果资源门全部满足后 exact r3 仍在同一 Pass-1 位置连续两次 OOM，才允许将根因升级为 `tool/flat-graph pathology` 并设计 r4。r4 只能对三个点采用完全相同的 hierarchy-preserving flow，并重新建立 VCS→DC→Formality/SAIF/PTPX 证据链；不能把 r4 的某一点与旧 flow 的另一个点作面积比。

## 重跑准入门

- 当前结论只解锁 **一次** resource-gated exact r3 replay，不解锁 Formality/PTPX。
- r3 通过原 M496 logic Pareto gate 后，才解锁独立 receipt-blind hammer；该 hammer 通过后才可进入 matched Formality 与 SAIF/PTPX。
- r3 OOM/失败不等于 K8 性能 NO-GO；r3 也不产生 full FC2、FFN、系统倍速或 paper-ready PPA。
