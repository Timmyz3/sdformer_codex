# K16 完整覆盖：复用恢复，但 M20/H8 分块布局没有净服务收益

2026-09-12；CPU实际载荷与端口服务模型，**不是RTL加速比、全空间层或整网性能**。执行前问题/对照见 [design_before_execution.md](design_before_execution.md)，可复跑脚本 [execute.py](execute.py)，逐组逐K块数据 [results.json](results.json)。

**结论：停本次 M20/K16/H8 布局，保留 ProSparsity 家族及更大 M 未试接口。** 小K块的父复用确实恢复；列关系检测只比允许重叠的普通TCAM检测器快约0.1%，两种PR布局均明显输给当前完整直接GP。原因是跨K累计与局部状态费用，而非full-K864没有父关系。

GP在H32循环内每条NRV只读一次；PR为保住RF容量按4个H8重读原NRV、目录和父表。所有SR64/SW64/CR256响应、RF依赖和单发射槽由同一Machine执行。每个非零物理源列仍至少有一个根消费者，所以这里删源项没有删除权重行请求；CR256读取未下降。

以ordinary/corner为例：列关系版本总729,453槽中，源NRV生产123,639，父表/目录读取118,664，局部清零46,348，残差GP283,860，父继承与全局累计102,984；其余是共同填充、全局清零、Z写回和632槽检测尾部。普通TCAM尾部1322槽，绝大部分检测已被下个K块源生产隐藏。

## 状态、强对照和实做边界

- 两臂固定 SR64/SW64/CR256、96个8-lane RF、128KiB状态SRAM和128KiB系数存储；本轮同一现成expanded-FP32 dyadic编译。没有把原论文8位PE性能借过来，也没有同面积/同频结论。
- 直接GP用80个全局向量RF；PR按H8使用20 local +20 global，边界P1更少。**没有额外80个psum**，没有累加器溢出/搬回；所有局部清零及跨K累加已收费。
- 两种PR均在公共状态SRAM保留54×40=2160B父/计数表、54×8=432B目录；表在每个H8实读。原NRV和Z地址与GP一致。另列40B当块分派表、32B有限元数据输出队列，未把它们藏进RF。
- 普通PR获双缓冲TCAM：每bank20×16个ternary cell，先20拍预载，再按M+4流水给出结果；其20×16行键生产暂存也预算双份。TCAM有单query并行subset能力，不用逐对SRAM查询当其上限。
- 列关系按每bank400-bit关系+20×5-bit计数工作，预算两个bank以与后续源生产重叠。两臂都有父选择/稳定排序/残差选择控制逻辑；这些逻辑的工艺面积、扇出与时钟尚未测。原独立单任务RTL叶虽已验证，**本次双缓冲K16适配和SRAM父表重装没有RTL闭环**。
- TCAM/列关系都允许在NRV接受时收集支持，并把计算阶段之外的检测与后续K块源生产重叠；父输出真实占SW64，否则排队/尾部等待。所有54块先准备、再按H8计算，这是本轮有限RF布局；未声称复刻原作全部跨算子流水。
- 只跑预定always-ready端口场景，算术RAW/WAW/writeback仍收费；没有进一步端口/缓存/训练扫描。额外背压、TCAM宏、同面积映射均未验证。

## 保留什么

1. K16的ProSparsity复用不是死路：这里恢复了33.91–46.79%的源项共享，负结果不能外推到原作M256/N128。
2. 停本次M20/K16/H8逐片清零与全局相加布局，以及把列关系的约0.1%边际包装成标题的做法。
3. 更大M的K16、不同局部/跨K状态接口、完整原作资源比例仍未试；本轮不自动扫描或复活旧布局。原PR底座、精确父规则和本轮完整覆盖脚本保留作对照。

复跑：与现有训练环境相同的Python3.12执行 `execute.py`；不依赖GPU。
