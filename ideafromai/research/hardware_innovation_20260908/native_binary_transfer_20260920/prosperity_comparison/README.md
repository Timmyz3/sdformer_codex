# ep34同输入比较：Prosperity仍有很强复用，不应因旧融合失败退出

2026-09-20。本次实际运行了16个原生ep34 FC1输入域的全部M/K统计，并对其中3个完整算子调用**现有官方Prosperity CPU `run_fc`外层**。没有新造硬件周期公式，没有GPU、训练、EDA、生产树改动。

**结论先说：Prosperity值得继续作为强底座。** sample0的S0 block0、S2 block0、S2 block5在官方CPU模型内，product相对bit分别是 **2.7501×、2.3383×、2.4005×**。它们是原作者模型在本网络源支持上的迁移结果，不是本方创新、RTL加速或同资源战胜Gustav/G4。新G4、NRV和PSN融合不能仅对简单AAC取胜就宣布比强先验更好。

入口：[运行脚本](run_comparison.py)、[全部原始结果](results.json)、[23,688个tile逐项计数](tile_counts.csv)、[实际日志](run.log)。前一日NRV统计见[审计目录](../../handoff_review_20260919/GUSTAV_NRV_OPPORTUNITY.json)。

## 1. 输入与原规则

输入完全复用昨日16域：sample0/10的S0/S3 block0，以及S2全部6个FC1块；来自`bn_state/trace_s*_stage*.npz`和已封存`m1707.../fc_frames.bin`。按捕获合同恢复`[T,P,C]`，T=10；S0为P19200/C96/H384，S2为P1200/C384/H1536，S3为P300/C768/H3072。没有新抽样、没有换成lifting/R8/forced-code学生。

Prosperity沿用既有官方适配参数：**M256/K16/N128**、issue2、1024bit外部接口，源排列为官方`P-major、P内T`，通道顺序不变。对于真正FC使用`ep34_native_mlp_fc1`名称，**没有沿用旧conv wrapper中的kernel3/9流量处理**。

父选择严格来自官方CPU函数`simulator.py::find_product_sparsity`：

- 只搜索popcount≥2的子行；空行/onehot不找父。
- 父是非空子集；相同行作为父必须原始下标更小，避免相等依赖成环。
- 选popcount最大的父，平局取满足条件的最小原始下标（`torch.argmax`首项）。此处遵从**公开工件**，不偷换成论文文字的另一平局规则。
- 残差为原行XOR父行；按`(popcount,原始下标)`排序是合法执行序。本次每个tile逐行验证父严格较小popcount或相同popcount更小下标、父与残差不交、并集重构原支持。

关系计算复用09-07已有NumPy加速回调`c1_full_layer.Relation`；20个真实/定向/随机tile与未修改官方原关系函数的输出、父下标完全一致。另用T10/P29/K35/H197的非整tile多K/N小算子，比较原关系+原外层、加速回调+原外层及既有解析对照，全部字段相等。16域首tile还用随机signed8 W做32,768个N8整数输出核对，全部相同。这是数据流/支持的验证，不是实际FP32权重的网络数值验证。

## 2. 三个完整算子的官方模型，非分片K求和

每行是对完整T×P×K→H的一次`run_fc`调用，内部保留全部M/N/K loop。bit、product同输入、同模型资源。它们均与既有独立完整外层公式逐字段相同。

| sample0算子 | 完整M/K/H | bit模型周期 | product模型周期 | 模型内bit/product | product预处理周期 | 预处理额外stall | mem stall |
|---|---|---:|---:|---:|---:|---:|---:|
| S0 block0 FC1 | 192000/96/384 | 9,759,458 | 3,548,795 | **2.7501×** | 2,798,238 | 0 | 20 |
| S2 block0 FC1 | 12000/384/1536 | 6,135,320 | 2,623,880 | **2.3383×** | 2,034,960 | 0 | 20 |
| S2 block5 FC1 | 12000/384/1536 | 9,445,100 | 3,934,616 | **2.4005×** | 2,940,252 | 0 | 20 |

原模型默认容量是act4096bit＝512B、wgt16384bit＝2KiB、out262144bit＝32KiB；权重和输出计数均为8bit。这不是论文8/32/96KiB，也不是本方Acc24/真实28nm宏资源。`reads/writes`原计数单位为bit，不可直接当byte。

本次三层的`g_psum`读和写各3,538,944,000bit，即442,368,000B；product没有消除这项。这是**原模型逻辑片上计数**，不能说已实测流量或这些字节都要搬到DRAM。它表明后续完整实现不能只看乘积项减少，还要处理psum驻留与真实BN/PSN边界。

**模型有意理想化的内容必须保留：** issue2排序不计周期；预处理与计算以整层总量max重叠；partial-match父值取得/存储冲突不独立计时；工件没有完成本网络动态BN、完整T10 PSN、FC2/shortcut和实际更宽累加。mem stall=20是这些假设下的结果，不能外推物理存储不贵。

S0 sample0的967,354项进一步分为root201,454和child delta765,900；有569,997次PM父引用，以及215,571次EM复制，即`785568 − 215571 = 569997`。原官方数据发射计数是`967354+215571=1182925`，再乘三个N128输出块，得3,548,775计算周期；另加20初始访存周期。**所有PM父引用没有因此消失**，只是工件没有另罚其每次读取的周期。

Gustav P8的NRV作用不同：复用一次权重取得并按位置位图scatter，在这个支持级口径上并不减少`S×W`非零贡献总数；减少的主要是索引/存储/访存与调度税。G4将四个潜在贡献合成查表；Prosperity将较大公共支持变成父值依赖。三者的状态、数据宽度和执行代价不同，因此这张表既**不能写Prosperity一定硬件更快**，也不能用G4的29%说已超过Prosperity。

NRV数据与昨日16域逐条完全一致。S2 block3/5 sample0的理想NRV载荷已经比原bitmap大约9%；应给Gustav普通bitmap/密格式旁路，避免把格式税当作家族失败。P8跨T10整组OR空行远少于逐tick空行，保留细时间粒度有真实理由；时间布局变化仍需真实transpose/供数成本。

## 4. 对“相比Prosperity迁移效果”的回答

1. **Prosperity迁入本网络是有效的。** 这轮S0、S2直接支持了这一点，和09-13原完整瓶颈算子的约2.33×官方模型趋势一致；但这里没有借旧倍率，每个数字都重新调用完整官方外层。
2. **旧Prosperity∪APEC和冷窄Phi融合失败，不等于Prosperity没有性能。** 原算法已经吃掉很多重复支持；再加中心查找可能只多出税。应该保留强A，而不是删掉后拿更弱AAC做唯一标题分母。
3. **Gustav可作为不同强A，不是Prosperity升级版。** 它解决供数/状态驻留；Prosperity解决公共支持部分和复用。二者能否融合，要看有限父值/psum、NRV扫描及PSN/BN真实寿命，没有本次结果允许把两个收益相乘。
4. **G4现在值得写RTL，但角色首先是低控制成本的挑战者。** 如果它用很小表、少matcher/父状态，在真实同口同容量下胜出，才是有价值的执行组织结果；单看28.9%的组合数明显不能替代与Prosperity的比较。

最小后续建议：本轮原生AAC/G4 RTL之后，在同一捕获、同W整数函数、相同端口/状态预算上，接一份**真实父选择/合法排序/父值提交与读取**的强Prosperity执行点，至少报告完整K及冷/暖。不得只喂免费父表再说完整复制原A；允许将父关系生成作为单列、实付阶段。先观察PM父读取、psum驻留还是matcher拖慢，再选择一个确有剩余成本的融合X。新机制的必要性来自这个执行差分，不来自“Prosperity已经不行”。
