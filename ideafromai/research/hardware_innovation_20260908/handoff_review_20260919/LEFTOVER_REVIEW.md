# Grok leftover LUT + Scrooge 独立审阅（2026-09-19）

结论：**保留两条思想作为待实现候选，但不能继承“同资源周期 KEEP 29.2% / 60.4% / 链 41%”。现有程序是运算机会计数；Scrooge 还存在可复现的 FP32 证书反例。** 没有依据把 LUT、早停、Prosperity 或 skip 整个家族杀掉。

本次只读原产物，运行已有 CPU 测试和独立小探针；未跑 GPU、训练、RTL、EDA，未修改原交接或原收据。

## 1. 结论分级

| 类别 | 项目 | 独立裁决 |
|---|---|---|
| 可确认 | `nnz(S) × 384` 是当前二值 FC1 的标量选权加法数 | 正确；比用七位串行作分母更强，但尚不是硬件周期 |
| 可确认 | G4 表查询能合并同组多个有效源 | 实数/足够位宽整数恒等式成立，实际源支持有约 29% 加法机会 |
| 可确认 | `L1(A_rest) × max(abs(Y))` 给实数线性和的合法余项界 | 正确；避免为求精确余项而先算全部乘积，值得硬件验证 |

| 需限定 | 60.42% “after tax” | 只减了 `max(abs(Y))` 的人为 0.1 单位税；不是完整证书、供数、状态、组等待成本 |

## 2. 17.72% 到底测了什么

`run_remaining.py:133–157` 在 `layers.0.swin_blocks.0.mlp.fc1` 的前置 hook 上，把输入变为 `S=(x!=0)`，展开成 N×96。记录的分母和密度反推并与 `bn_state/numeric_s0_stage0.json` 一致：

- T=10、P=19,200、C=96、H=384，N=T×P=192,000。
- 每帧源位数 18,432,000；平均非零约 3,266,848；乘 384 得 1,254,469,593.6 标量加法。
- PSN 分母 P×384×10×10=737,280,000 标量 MAC。
- 不是 76,800 个空间位置，不是整网平均活动率，也不是 450-token 注意力窗。
- FC1 支持统计遍历这些源行；Scrooge 只对 `y[:, ::step]` 抽样，P=19,200 时 step=75、256 个位置/帧，再把比例应用到整层 PSN 分母。

最终 JSON 只存十帧均值，未留十帧每帧直方图、逐组停点或抽样门对拍。本次没有重新跑十帧网络，不能声称复现了原十帧统计。

## 3. LUT packed：思想保留，费用表未形成

`remaining_ops.py:297–316` 只计算：

`1 - 非空四位组数 / 非零源位数`。

代码中没有实际建立/读取权重和表，没有验证表加与原始求和结果，没有表驻留/换页、bank 冲突、建表、输入扫描、输出提交或背压。`run_remaining.py` 把 `tax=0` 和“already packed”直接写成注释；这不是生产者握手证据。

但不能反向武断地固定罚 25% 就杀掉：现有 `bn_state/trace_s*_stage0.npz` 确实存有 `source_packed:uint8[192000,12]`，来自源捕获的二值位图；96 位源可天然切成 24 个 nibble。能否零额外周期读取取决于实际输出打包、查找非空 nibble 的扫描器和端口，不能靠统一 `1/G` 税猜测。

全 H384 表为 24×16×384=147,456 个 addend。若共同整数模型 W 为 signed8，四项和至少需要 signed10：

| 参数保存形式（仅容量算术示意） | 大小 |
|---|---:|
| 原 W8 | 36 KiB |
| 完整 G4 表，理想紧密 signed10 | 180 KiB |
| 表项放 signed16 | 288 KiB |
| 表项放 signed24 | 432 KiB |

这不是说表一定失败，而是“少 29% 加法”可能换来 5–12 倍参数状态或更多字读取。有限 H8 子块可缩表，但必须实际计建表与多块遍历。若四个 singleton 直接拷贝，每组其它 11 个非零组合按子集递推构造，则全层还需约 101,376 次建表加法和表写入；长流可摊薄，但冷启动必须列出。

本次两条既有源捕获的 G4 计数收益为 28.8697% / 29.6725%，支持机会存在。它不证明原 FP32 求和逐位相同，也不等于复现完整 LUT-GEMM 论文执行器。该代码实现的是二值源的子集和计数，当前不能称“完整抄好了”。

## 4. Scrooge：数学界有用，但共享粒度会吞收益

`psn_scrooge_extra` 对每个 `(t,p,h)` 独立找首个可判断点，然后把剩余 MAC 数相加。它允许每个 t 各用一份 `|A[t]|` 排序。因此若十个 t 并行，可能同一拍请求不同源时间行；若 H8 SIMD 锁步，就等最慢 h。两个问题均未进入原税。

本次只用 s0/s10 两条旧 `bn_state` 捕获，每条抽 256 个空间位置，用全域 Gram 统计重构 live BN 输入后调用原 `psn_scrooge_extra`；不是原十帧 GPU重跑，也不是整数部署。结果见 `leftover_probe.json`：

| 计费/退休粒度 | sample0 可跳 MAC/步机会 | sample10 可跳 MAC/步机会 |
|---|---:|---:|
| 独立 `(t,h)`，与原函数一致 | 70.0922% | 71.2664% |
| H8 同一 t 等最慢 | 41.1196% | 42.5524% |
| T10 同一 h 等最慢 | 37.0954% | 39.5369% |
| T10×H8 整组等最慢 | **8.4489%** | **10.1449%** |

表中所有数字都**尚未扣任何检查/读取/状态成本，也不是周期**。这不是证明早停家族失败；它给出新增电路该解决的洞：独立已完成判决怎样取消真实发射，且不靠免费多端口、免费打包和输出重排。固定整组 T10×H8 等最慢的布局尤其不应继承 60%。

`1/T` 只近似覆盖遍历 T 个输入求 max。其它遗漏包括：

- 每个被测试前缀的 `suffix_L1 × ymax` 仍是一项乘法或等价电路；预存 L1 只消除求和，没有消除与运行时 ymax 的乘法。
- 起始 k=0 的界、每步两个边界加减/比较、锁定位、队列/重排、全部门输出。
- `|A|` 排序不同带来的读取多样性，Y 储存和回读，max 计算与生产者的真实重叠。
- 如果新增专用 bound 乘法器来重叠，就必须让全深度基线获得相同资源预算，而不是仅从工作量扣税。

**不能只把 0.1 改成另一个固定罚值就作终局裁决。** 应用有限端口执行器测量；当前 60.42% 降为单元独立取消的粗上界线索。

## 5. τ/live BN 与数值无损：一项合理、三项要修

### 合理处

MS_Spiking_Mlp 的顺序是 `sn1 → fc1 → bn1 → sn2`。`run_remaining.py:183–201` 的 hook 在 `sn2.spiking_neuron` 入口，因此 Y 已经过 live BN；`tau=theta-bias+center` 在实数模型中是正确门边界。这里不必再把 BN γ/β重复折进去。

因此“live BN 禁止 FC1 尾丢弃”与“完整 BN 后的门专用 PSN 可早停”可以同时成立。但 `THETA.md` 说这份逐 h tau 来自 BN，和本运行代码不符：它是同一 T 维边界扩展 H 份；BN 已反映到输入 Y 里。若改挂原始 FC1 输出，需要另用含均值/方差/γ/β及方向的合同。

### 可复现 FP32 错误

原函数采用 `suffix_after = reversed_cumsum(abs(A)) - abs(A)`。令：

```
A 一行 = [1, 2^-25]
Y       = [0, 1]
tau     = 2^-25
```

实数及直接 FP32 全和都是 2^-25，门应为 1。第一项执行后 psum=0，真正余量为 2^-25；但 FP32 `(1+2^-25)-1=0`，程序认定 `0 < tau`，错误提前关门。`leftover_probe.py` 对两行重复该例，**2/2 门错误**，原函数却返回 50% 跳过。补零可嵌入 T10。这个反例否定当前实现的通用 FP32 无损标签，不否定 L1-max 的实数界。

正确整数硬件可以用足够宽的系数后缀和、乘积、累加器避免此取消；若继续浮点，就需向外取整及边界回退。此外，对 A 求和重排、`addmm` 的 bias 运算顺序、τ折移也不能自动继承 PyTorch FP32 的逐位门结果。

本次两条实际捕获探针共 1,966,080 个判决，重构 CPU 参考中没有发生门差异；这不推翻反例，也不是 cuDNN/全网无损证明。

### 原“零 Y”跳过不合法

`remaining_ops.psn_zero_t_extra` 根据前 BN 的源全零推定 PSN 列零。但 live BN 将 raw_Y=0 变成 `γ(0-μ)/σ+β`，一般非零。不能把该项的 3.1% 当已验证无损。它已被低收益规则 KILL；应保留为错误口径纠正，不要复活数字。

## 6. 链 ~41% 和 AEE 的实际含义

`run_remaining.py:439–441` 的 40.7765% 为：

`(0.292339 × 1.2544696G + 0.604161 × 0.73728G) / (1.2544696G + 0.73728G)`。

这确实没有独立相乘，但混加了**一次整字选权加法**与**一次连续 MAC**，默认为等服务价。live BN 归约/标准化、表构建、位宽、所有字传输、组等待均未计入；也没有证明两者的并行比例。这是指定子链的等权算术代理，不是同资源周期模型，更不是整网 41%。十帧比例先平均再乘均值，也不是严格逐帧加权汇总；原 JSON 不足以还原所有逐帧量。

质量部分还有单独问题：

- `PRED2='sttmultires_unet.preds.2'`，所有 AEE 取该中间头的时间和并做双线性插值；不是模型返回的最终 `flow[-1]`。模型原生插值的默认模式也不同。应标成“preds.2 双线性十帧 AEE”。
- 当前十帧全是 `zurich_city_09_a_{0001,0011,...,0091}`；常量 NB0=1.454602861 是 `TCASII_服务器实验任务书_20260917.md` 中另一组 diverse10 的最终头结果。不能宣称同协议 NB0 门通过。
- LUT/Scrooge 只作为 hook 统计，没有替换 forward；`new_idea.AEE_10frame=AEE_full` 是原网络/该头 AEE，并非融合执行后 AEE。
- `Cin/Cout` 探针确实修改了计算并跑该头，值得保留，但质量通过需匹配名单/输出头再测。不是据此杀剪枝。

## 7. 一个最小值得接续的 RTL 工作单

**先做 G4 子集和 FC1，Scrooge 先保留规格，不同时造两套大核。** 理由：G4 的源表示已有实际档案，数据机会可直接复现；证书分支还欠独立退休组织和数值修正。

**A：**完整 H8 输出块的普通二值 AAC，加上原理相同的 G4 子集表执行臂。  
**B：**源中同一 4-channel 组多位活动，逐位 AAC 多发射；但 G4 表扩大参数、存在冷建表与端口代价。  
**X 候选：**有限 H8 驻留、固定 G4 位图输入、显式构表/复用边界能否把机会转成净服务；这一步先是完整强底座验证，**尚不把有限驻留本身当新颖 X**。

约定最小规格：

1. 输入真实 C96 packed bitword；H8，T10×P32 源 tile，跨若干真实 tile 连续回放。继续所有 48 个 H8 块才可报 H384 整层。
2. 使用**明确写出的共同整数函数**，例如 W8、子集和 signed10、累加 signed24，无中间舍入；若是由 FP32 新量化，标为新 QDQ 微探针，不能继承 ep34 FP32 AEE。
3. 相同 8 个加法通道、同一 128-bit 请求口、同一 outstanding 数/响应背压、相同总参数容量。AAC 可使用相同空余缓存，不剥夺基线复用。
4. RTL 真正构建/装载 LUT、扫描 packed 源、读表或 W、累加和提交；记录冷/热两套周期，建表/初始化/换块/输出必须入账。首个 H8 表 24×16×8 项可实际容纳，不以完整 H384 大表免费驻留。
5. 对真实源和 signed 极值逐元素核验完整 Y；不是只比发放率。报告 service、参数字、源字、状态和 stall。
6. ≥15% 同资源子核净服务则继续整层与 PSN；若失败，定位表宽、表驻留或扫描哪个限制吞收益，再只选一个针对性接口改动。**负结果只停这个布局，不杀 LUT 家族。**

Scrooge 后续可接的 X 应明确为“有限共享供数下的独立判决退休/剩余任务重组”，而不是再次提出 L1 上界。它要与同资源全深度时间 MAC、先前门核以及生产者融合基线共同比较。当前没有证据宣称这就是最终论文创新。
