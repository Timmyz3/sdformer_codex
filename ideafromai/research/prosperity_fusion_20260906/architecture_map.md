# Prosperity 哪些应完整接过来，哪些应针对我们替换

本轮从完整 PPU 出发，恢复 C1 的主研究方向。当前表是方法层映射，不表示这些模块已完整落入我们的生产 RTL。

| 原版环节 | 原版作用 | C1 重构中的处理 |
|---|---|---|
| Tiling 与双缓冲 | 对 M/K/N 分块，交叠取数与处理 | 保留完整流程；分别记录论文配置、本地64×16×96合同，不混用面积 |
| Detector | 并行找所有合法子集，并取得行 popcount | 保留正确关系识别；比较真实行、模式/虚拟节点的新候选来源 |
| Pruner | 每行只选一个最大子集；相同规模候选的规则固定 | 作为忠实对照；新共享节点若引入额外引用与存储，必须显式计入 |
| Dispatcher | 按 popcount、原行序稳定排序，保证父行先执行 | 保留父依赖与原坐标；融合后若有新节点，不能沿用排序正确性而不证明 |
| Processor | 取父结果，扫描残差源，累加并按原目的写回 | 保留完整数值执行；候选可替换共享结果生成/生命周期，但输出全部保留 |
| 两阶段流水 | 当前tile构图与前一tile计算重叠 | 作为强基线；新执行若短于构图阶段，不能继续默认检测成本被隐藏 |
| 神经元与SFU | 普通LIF及论文支持的注意力算子 | 接我们真实的满秩PSN/ATLIF与Motion-XOR；不照搬其算法函数 |

原文明确只处理真实行的相等/包含关系，放弃一般交集；多父设计还涉及是否重叠、额外引用和性能代价。因此融合切口在“怎样扩大有效共享而不付出完整一般图的成本”。这为借鉴 Phi、Transitive Array 或 ExSpike 提供了具体对象，而非给现有九宏改名称。[Prosperity，§III–VI](https://arxiv.org/html/2503.03379v2)

冻结输出仍是 `z=θg`。在合法固定幅值线性段，以实际贡献 `φ_c=θ_c W_c` 做集合和，继承/交集恒等式成立；θ 没有被当成 1。若幅值随事件变化，源身份须包含幅值并重新定共享条件。线性重排的有理数/整数正确性不等于 GPU FP32 算序逐位一致。

候选来源分别保留归因：Phi 的模式及双向残差，Transitive Array 的虚拟中间节点和评分表，ExSpike 的邻位置共同贡献。它们均可成为重构工具；需要比较融合整体及移除某工具的同资源对照，不能把多个论文各自倍率相乘。

## 2026-09-07 补充：完整复现时必须分开的三份身份

官方公开工件 `HW/third_party/Prosperity` 与 `/home/zhumd/work/literature_artifacts/Prosperity` 均为 commit `6ee1c6f1cb419fcf942f2eda63db84ca28248f4b`。公开树主要是模拟器，没有可直接合并的 Verilog/SystemVerilog 实现。“搬完整”应理解为按完整架构复现和对照，不能说本轮已接入官方 RTL。

| 对照身份 | 已核差异 |
|---|---|
| 原论文 | 合法最大 popcount 父平局取较大 index；典型 tile 256×16×128，Table III 缓冲为 8/32/96 KB |
| 官方 CPU/CUDA 工件 | 关系函数取较小 index；默认 accelerator 的 act/weight/out 配置为 512/2048/32768 B，另有 CACTI 配置；不是自动等于论文资源 |
| 当前 m935 | 最大子集、较小 index、三段匹配、双目录、稳定 min-key 派发、父返回队列和反压已存在；64×16×96。并非只实现了恒等式；完整层 M/N/K 供数及论文 TCAM/bitonic 组织不能由此推定 |

官方 `run_fc` 是计数模型，不计算实际 W 数值；某些 issue 模式将派发成本设零。本轮 joint-residual 参考只与封存 `cleanroom_subset` 关系函数逐 tile 交叉检查，没有冒称调用了完整官方层模拟器。新 ep34 完整层 adapter 仍需恢复原 K 范围，不能复用旧 ep35 拆成432次独立调用的代价作为完整层基线。

九宏是共同地址和使能的宽度切片，`9×128=96×12`，不是九个可独立访问的 bank。物理容量18,432B，旧64行地址域可用payload9,216B。m935的外部 psum 为96×19bit，和父槽12bit是不同接口。通用有符号纯残差在INT8诊断域可达+2048；如无额外范围约束，不能沿用12bit自然正源上界。θ 的真实精度还应另外计入部署合同。

M64扩大到M256也会扩大目的 Acc：同时保留8个96-lane输出块时，19bit纯payload从116,736B变为466,944B。父槽压缩不自动抵消这个成本。本轮主候选因此先保持M64，改变共享对象与构造方式，不靠扩大逻辑窗口产生表面机会。

## 当前主候选的替换范围

完整 Prosperity 流程仍是强对照。候选把 Detector/Pruner 拆成离线固定基图与在线已完成残差匹配；Dispatcher 按原输入顺序消费，不等待全 tile 动态图；Processor 仍完成基构造、残差构造、合并和原目的提交。已有计算功能被明确保留或替换，尚未完成同资源逐周期与映射闭环。
