# DQFS分段无死锁微架构与RTL接口合同

> 2026-07-31 实现状态：第216号文档已完成最小叶模块RTL proof，并补入`seal_seq`年龄仲裁和row-last outstanding检查。本文仍作为接口合同，验证结果以第216号文档及`results/qfit_dqfs_segmented_20260731/report.md`为准。

## 1. 目的

第九轮DATE与ASIC独立审阅确认DQFS有架构潜力，但原方案存在三个P0：

1. term buffer在row complete前满会形成循环等待；
2. forward链表append不满足单1R1W写端口；
3. epoch、output tile和window结束语义未冻结。

本文关闭这三个设计合同，作为后续RTL唯一依据。

---

## 2. 从Row Buffer改为Row-Owned Segment

### 2.1 可提前封口

一个collect context遇到以下任一条件即封口：

- 输入`row_last`；
- term容量将在本次插入后溢出；
- 当前lane出现新gate且该lane目录way已满；
- 需要切换epoch/output tile/window；
- 控制器主动flush。

封口后的segment立即可emit，不要求逻辑row已经完整。若同一row后续仍有term，
它们进入新的segment。同一`(lane,gate)`可能跨segment重复生成product，
只降低复用收益，不改变结果。

因此容量不足的行为是**性能渐退**，不是错误或死锁。

### 2.2 Row-Owned而非见Row切换即封口

W6有序term流只有6个逻辑row，但发生22次row切换。见row变化就封口时：

| 配置 | product减少 |
|---|---:|
| C128/W6 | 15.19% |
| C256/W6 | 22.42% |
| C384/W6 | 22.96% |

允许两个row-owned context交错收集后：

| 配置 | product减少 | segment | 容量封口 | way封口 |
|---|---:|---:|---:|---:|
| C128/W6 | 32.93% | 14 | 8 | 0 |
| C256/W6 | 55.56% | 8 | 2 | 0 |
| C384/W6 | 59.37% | 6 | 0 | 0 |

W6同时活跃row上界为2。该数字仅用于proof参数；post-G0若出现更多活跃row，
控制器可封口一个未完成segment，等待其emit释放后再分配，不依赖固定上界
保证正确性。

## 3. Context状态机

每个context独立处于：

```text
FREE -> COLLECT -> SEALED -> EMIT_GROUP -> EMIT_MEMBER -> DRAIN -> FREE
```

全局规则：

- 输入row优先命中相同`row_id`的COLLECT context；
- 未命中时分配FREE context；
- 无FREE context时，可将最旧COLLECT context提前封口；
- 若所有context均SEALED/EMIT，输入反压；
- emit始终选择最旧segment，保持segment级提交顺序；
- emit不等待任何未来输入，因此输入反压不会阻止资源释放。

这消除了“等待row_last才能emit、但row_last又被ready阻塞”的循环依赖。

## 4. 反向链表满足1R1W

### 4.1 Directory

每context使用lane-local目录：

```text
directory[lane][way] = {
    valid,
    gate,
    tail_pointer,
    member_count
}
```

输入每拍只属于一个lane，因此只需该lane的W路gate比较，不需要全局CAM。
目录建议使用DFF实现并由DC确认比较器路径；不能假定SRAM可同时返回6路。

### 4.2 Term SRAM

每个term entry写入：

```text
{
    source_plane,
    source_y,
    source_x,
    destination_mask,
    prev_pointer,
    prev_valid
}
```

append过程：

1. `prev_pointer = directory.tail_pointer`；
2. 新term写入当前bump pointer；
3. directory tail改为当前pointer；
4. member_count加一。

不修改旧tail，因此每个输入term只产生一次term SRAM写。emit从tail沿
`prev_pointer`反向遍历。组内顺序被反转，但在模加合同下最终Acc不变。

Term SRAM使用generation-valid或bump allocator；segment释放后只清目录和
计数，不逐项清SRAM。

## 5. 两级输出接口

### 5.1 输入

```text
in_valid / in_ready
in_row_id
in_row_last
in_window_last
in_lane
in_gate
in_source_plane/y/x
in_destination_mask
```

事务控制：

```text
txn_start(epoch, output_tile)
txn_close
epoch_advance_valid / epoch_advance_ready
```

### 5.2 Group输出

```text
group_valid / group_ready
group_lane
group_gate
group_epoch
group_output_tile
group_member_count
```

`group_fire`后product unit同步读weight并启动`gate×W`。product有效后保持到
该group所有member提交完毕。

### 5.3 Member输出

```text
member_valid / member_ready
member_source_plane/y/x
member_destination_mask
member_group_last
member_row_last
member_window_last
```

被重排输入的原始`row_last/window_last`不直接透传。context只记录segment
是否包含逻辑row/window最后一个输入；DQFS仅在该segment最后group的最后
member上重新生成标志。

---

## 6. Epoch、Tile与Window合同

- 一个context在COLLECT时锁存`epoch/output_tile/window_id`；
- context内三者恒定；
- epoch或tile切换请求到达时，当前segment先封口；
- `epoch_advance_ready`仅在所有context为FREE、product寄存器无效、TCFM和
  Acc更新流水排空时拉高；
- window close仅在包含`window_last`的segment完成且所有更早segment退休后
  发出；
- 不允许旧权重epoch的目录项读取新权重。

非法lane、gate=0、空mask、越界source/destination在写term SRAM前原子拒绝。

---

## 7. 吞吐口径

DQFS不能用“607个值键”替代周期：

```text
emit_cycles =
    member_terms
  + value_key_startup
  + weight_read_latency
  + multiplier_pipeline_bubbles
  + TCFM_backpressure
```

双context只能重叠collect与emit。第一版RTL必须暴露：

- accepted terms；
- sealed segments及封口原因；
- emitted groups/members；
- product starts；
- context-full stall；
- group/member downstream stall；
- max context occupancy；
- epoch/window drain cycles。

后续可加入下一group weight预取，但不得在基础对照中默认免费。

---

## 8. 与宽Product Cache的公平比较

第九轮DATE评审指出lane-local 4-way缓存命中66.60%，8-way为89.56%，必须
作为强基线。

> **2026-07-31口径纠正：** 当前Local5/TCFM RTL为`OUT_DIM=4`，
> `ACC_W=32`，真实product宽度为128 bit。下面1024-bit数字仅是
> `OUT_DIM=32`敏感性，不是当前主线。真实Pareto见
> `results/qfit_product_storage_pareto_20260731/report.md`。

若敏感性配置的output tile为32、Acc product为32bit：

```text
一个wide product = 32 * 32 = 1024 bit
```

忽略tag和外围时：

| 结构 | 数据位下界 |
|---|---:|
| lane-local 4-way product cache | 32×4×1024 = 131072 bit |
| lane-local 8-way product cache | 32×8×1024 = 262144 bit |

DQFS不缓存多份wide product，仅保留一个活动product寄存器。它存窄term链和
目录。以W6 proof的C256/W6双context估算：

- term SRAM：`2×256×term_entry_bits`；
- directory：`2×32×6×directory_entry_bits`；
- 一个1024bit活动product；
- 具体位数必须按fullres坐标、pointer和count宽度重算。

这个分析只说明DQFS可能用窄元数据换wide cache阵列，不能替代同SRAM宏、
同端口、同SDC的PPA。

公平基线必须统一：

- output tile宽度；
- 乘法器数量和流水；
- 总存储位及宏拼接规则；
- weight端口；
- TCFM后端；
- 完整wall-time和SAIF活动。

## 9. Exact不变量

每个已接受term必须满足：

1. 恰好分配到一个context和一个directory group；
2. 恰好写入一个term entry；
3. 恰好从一条反向链读出一次；
4. 恰好向TCFM提交一次；
5. 其product由相同`epoch/lane/gate/tile`生成；
6. destination mask不变。

SVA至少覆盖：

- accepted计数等于emitted加在途；
- context FREE前所有member已退休；
- pointer严格落在本segment已分配范围；
- member_count与链长一致；
- sealed context不再写；
- epoch切换时无旧context；
- overflow只触发封口，不丢term；
- window_last只出现一次且为最后提交。

---

## 10. RTL Proof范围

首版proof采用：

- 2个context；
- `C=16或32`便于穷举；
- 每lane `W=2`；
- 同步1R1W term SRAM；
- 一拍一term collect；
- 随机group/member反压；
- 强制term容量封口、way封口、row交错和epoch切换；
- 两级输出与软件金参考比较。

首版不接乘法器和TCFM，只验证“值键分组+member多重集+事务边界”。
该proof通过后，再接product驻留和TCFM-5。

---

## 11. 当前结论

DQFS的架构新意不在链表或双缓冲，而在：

> 用固定Local5关系的frontier信息管理少量row-owned segment，在窄term域
> 重排跨source的值等价类，再将一个驻留product送入拓扑编译的无冲突提交
> 后端。

P0合同已在设计层关闭，但尚未有DQFS RTL和PPA，因此仍是候选，不是论文
已完成贡献。
