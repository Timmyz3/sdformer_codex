## 3. 累计审计做了什么

新增 `scripts/audit_local5_numeric_coverage_v1.py`，逐 sample 只读检查：

1. shard complete/report schema、状态和 formal G0 边界；
2. NPZ 的 dtype、shape、12-block H3/H6/H12/H24 拓扑；
3. 每窗 offset 是否等于 `heads × 450 × 32` 的闭式累计；
4. 125,193,600 个冻结 `expected_acc32` 与 `actual_acc32` 是否逐元素一致；
5. release manifest、batch plan、sample receipt、report、archive 的 SHA 链；
6. 连续 sample 无缺失、重复或跨 release 冒充。

`window_token` 在该 schema 中是空间 window ID，不是 token 数；T450 由 offset 闭式和
每 sample 1,987,200 个 Acc32 约束。独立审稿初次把 `window_token` 误判为 450，复核
schema 后已撤回该意见。

复审确认最高等级现在要求固定三份 source 名称、`batch/source` 路径、精确 policy、
complete/plan source 一致和 complete row/sample receipt 一致。

## 5. 证据边界

本轮允许写：

> Local5 在 63 个 sample、756 个 canonical block-window、125.19M 个 Acc32 上，与
> 冻结软件整数金参考逐元素零失配；其中 61 个 sample 共享同一 sealed-v5 RTL。

本轮不能写：

- 软件模型被累计审计器重新独立执行；
- 100/100 sample 或全部空间 window 已验证；
- formal phase ledger 或 admission 已完成；
- full encoder、性能、能耗或 ASIC PPA 已完成；
- provenance、哈希封存和累计审计属于硬件架构创新。

累计包使用外部 shard 的工作区绝对路径和 SHA256，未复制大体积依赖，因此是
workspace-bound 证据，不是可迁移独立 artifact。
