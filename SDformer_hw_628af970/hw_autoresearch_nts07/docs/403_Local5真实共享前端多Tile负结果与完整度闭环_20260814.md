# Local5 真实共享前端多 Tile 负结果与完整度闭环

## 1. 结论

本轮把 Local5 从“单 input-head、单 output-tile”推进到同一真实 window 的：

```text
3 input heads x 3 output tiles
  -> output tile 0 从真实 Q/K 生成 score/Shiftmax5/relation
  -> admission 后 resident head 的后续 tile 直接 replay relation
  -> nonresident head 精确 fallback 重算
  -> 跨 head Acc32 归约
  -> 43,200 个最终 checkpoint INT8 Acc32
```

这证明现有 Relation Memo 组件路径是真正的“一次 relation 生成、多输出 tile 消费”，不是把前端周期按 tile 重乘的模型 `[rtl]`。它不是生产 `QS + rolling/FCSR + source-owned + TCFM5` tile 的共享前端。点名组件强基线下的周期收益只有 `1.0192x`，因此裁决为：

> `NO_GO_AS_STANDALONE_DATE_CONTRIBUTION_KEEP_AS_COMPLETENESS_EVIDENCE`

Relation Memo 不再扩成新的 Local5 主贡献；它只作为统一 Local5 数据流的跨 tile 存储消融。

## 2. 身份与范围

- `sample0/stage0/block0/window94`；
- `3` 个 input head、`3` 个 output tile、`OUT_DIM=32`；
- 真实 full-resolution Local5 Q/K、真实 checkpoint INT8 projection weight；
- baseline/memo 使用相同 transaction-indexed service seed `17717`；
- Icarus 与 Verilator/SVA 各自完成，并与独立软件整数金参考比较；
- 不是 1200-window formal admission，不是 full encoder。

同一模式的 baseline/memo `source_sha256.txt` 完全一致：

- scalar pair：`a65ef7ddbfe457d59b3ab77e0f48efdabf97876eb260672acaaffb5ca8bd1653`；
- vector pair：`768c57f30c8e12db1e4093425d44992d9c7869cfd18cdfbac9ebacbf9329445b`。

## 3. 真实共享前端账本

Memo-on 在首 output tile 为三个 head 建立 relation。基于第一遍精确 term service，只有一个 head resident；其余两个 head 在后续两个 tile 精确 fallback：

| 指标 | Memo-off | Memo-on |
|---|---:|---:|
| Q/K token requests | 4,050 | 3,150 |
| memo hit | 0 | 2 |
| exact fallback | 0 | 4 |
| replay records | 0 | 128 |
| front-end cycles | 27,772 | 23,308 |

守恒关系：

```text
hit + fallback = 3 heads x (3 tiles - 1) = 6
token requests = (3 first-build jobs + 4 fallback jobs) x 450 = 3150
```

Q/K 请求减少 `22.222%`，前端周期减少 `16.074%`；两者不能改写为 encoder 加速或能量下降。

## 4. scalar 与 vector 强基线

### 4.1 scalar child-result transfer

| 配置 | cycles | speedup |
|---|---:|---:|
| Memo-off | 695,572 | 1.0000x |
| Memo-on | 691,108 | 1.0065x |

scalar 路径中 `388,800` 个 child readout cycles、`86,400` 个 cross-head RMW cycles 和 `237,495` 个 drain cycles 不受 Memo 影响，故 4,464 个前端周期只转化为 `0.642%` 总周期下降。

报告：`results/local5_real_multitile_shared_front_ablation_20260814/report.json`，SHA256 `ae8c50cf9427ae69b0f6f525502ec9574af7f8d34d809c02227c1c464c3a0acd`。

### 4.2 OUT32 vector child-result transfer

为避免 scalar readout 弱基线，使用仓库既有 `VECTOR_RESULT_MODE=1`。这把 child partial result 从逐 scalar 传输改为 32-lane vector 传输，但不改变 score、relation、weight、Acc32 或最终输出。它是本 DUT 的点名组件强对照，不是 encoder 或生产 tile 强基线：

| 配置 | cycles | child partial results | speedup |
|---|---:|---:|---:|
| Memo-off | 236,581 | 4,050 | 1.0000x |
| Memo-on | 232,117 | 4,050 | 1.0192x |

两边最终仍为 `43,200` 个 Acc32；Icarus、Verilator 和软件整数参考三方 `0 mismatch`。在消除 scalar 稻草人后，Memo 仍仅节省同样的 4,464 个前端周期，因此不能支撑独立 DATE 性能贡献。

报告：`results/local5_real_multitile_shared_front_vector_ablation_20260814/report.json`，SHA256 `12534b096cca05666caebdadaf527c00967fc68dd2918e4fe8057561f01909f1`。

### 4.3 第二个真实样本的负证据

`sample25/stage0/block0/window374` 在同一 vector 组件对照下没有任何 resident head：

| 配置 | cycles | token requests | hit/fallback |
|---|---:|---:|---:|
| Memo-off | 244,850 | 4,050 | 0/0 |
| Memo-on | 244,890 | 4,050 | 0/6 |

Memo-on 因 replay miss/fallback 控制多 `40` cycles，速度比 `0.99984x`。Icarus、Verilator 与独立软件整数参考对 43,200 个最终 Acc32 仍为 0 mismatch。这说明 Memo 的驻留收益具有明显窗口依赖性；本轮到此停止扩大样本和 RTL。

报告：`results/local5_real_multitile_shared_front_vector_s25_ablation_20260814/report.json`，SHA256 `56994f1466f356fda92faac8dcdf43d2cda9592446177222be86c8289889a49b`。

## 5. 本轮关闭的工程缺口

1. 集成脚本的 `USE_MEMO` 与 `VECTOR_RESULT_MODE` 已变成显式、默认兼容的消融参数。
2. TB 不再把旧 synthetic workload 的固定 `2250/4/2/28` 账本强加给真实 trace；旧 workload 仍保留精确断言，真实 trace 使用 hit/fallback/token 守恒断言。
3. merge receipt 显式绑定 `USE_MEMO` 和可选 vector mode，不再只接受 `USE_MEMO=0`。
4. vector filelist 补齐既有 vector cross-head Acc、serializer 和 direct-1RW bank；没有修改这些 datapath RTL。
5. 两种模式均生成 Icarus/Verilator receipt、source bundle、result SHA 与只读 merge report。

## 6. DATE 影响

- 架构创新：保持 `3.1/5`。Relation Memo 是已有跨 output-tile relation 驻留，不是新增执行对象；强基线下 `1.0192x` 也不足以把它抬为贡献。
- 工作量：`4.9/5`。
- 验证：约 `4.8/5`。真实 Q/K、真实权重、跨 head、多 tile、live/replay/fallback 和最终 Acc32 已闭合一个真实 window。
- 实验完整度：维持约 `3.2/5`。同端口周期与两个真实 window 的 Memo 组件多 tile 已完成，但不是生产 QS+rolling 多 tile，且仍缺 Synopsys SAIF/DC/STA/PTPX。
- 工程：`4.8/5`。
- 综合：约 `3.1/5`，仍是 Borderline Reject；工作量和验证不能替代架构创新。

## 7. 下一步

1. 不再扩 Relation Memo、第三种 replay 编码或新 admission 名称。
2. Synopsys 机优先完成 1R1W/1RW matched with-IO SAIF、DC、STA、PTPX。
3. GPU 空闲后执行 Motion 多样本 raw Q/K 真实 RTL 流水线。
4. 停止扩大 Relation Memo 的 window/RTL；不把本轮 `1.0192x` 或负样本周期写入 `docs/359` 主表。
