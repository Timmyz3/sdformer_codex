# M1598｜M1582/M1574 TSBG capture-permit independent rehammer

Verdict: **NO-GO. M1582 passes the requested ordinary forgery and consumption checks, but a closure registry is not a security boundary against same-process Python reflection. No M1558 capture is authorized.**

The exact source, author test, M1574 lineage, M1576 finding, M1582 contract/author receipt, and docs/359 identity were pinned and their seals verified. The independent hammer ran under CPython 3.10.18 and 3.6.8. In each runtime, all 28 requested checks passed: the production and synthetic registries were separate closure-owned dictionaries shared by the matching issuer and `consume()` method; plain `object.__new__`, shallow copy, deep copy, pickle, and double consumption did not yield a receipt; a mismatched output/inventory or occupied namespace removed the registry entry before raising, so retry remained impossible. A legitimate production permit retained the exact real-disk observation.

Two stronger attacks invalidate admission under the same reflective threat model used by M1576. First, the exact permit classes are exported mutable Python objects. Replacing `__hash__` and `__eq__` allowed an `object.__new__` forgery to alias a legitimately minted dictionary key and pop its record. This emitted both production and synthetic typed receipts. Second, Python function closure cells are introspectable. The hammer retrieved each registry through `function.__closure__`, inserted an unminted exact object with a caller-chosen record, and obtained a typed receipt. The production witness reported caller-selected `free_bytes_before=2^60` without using the production issuer for that handle.

M1582 therefore improves ordinary API-misuse resistance relative to M1574 but does not establish the claimed adversarial provenance boundary. A minimal successor should place issue, real-disk checking, consume, and producer construction inside one clean fixed-entry child process; no permit object or mutable registry should cross into caller-controlled Python. The alternative is to narrow the threat model explicitly and stop treating the in-process closure as a security capability.

The hammer constructed no producer and opened no payload. It imported no torch module and triggered no checkpoint, GPU, SSH, remote, capture, release, TSBG DSE, RTL, or EDA path. Only source-boundary successor work is authorized. One M1558 binary capture remains unauthorized, and TSBG DSE/RTL remains unauthorized.
