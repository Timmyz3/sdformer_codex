# M1256 read-only M1250 C1/R11 VCS failure forensic

Verdict: **the one-shot M1250 attempt compiled and ran, but it is not a
functional VCS PASS.  Random transaction 0 is not a legal integrated-M935
transaction: the TB manufactures a wrapper request at the parent connection
while the reset M935 core has no executable task.  M935 correctly raises its
sticky core fault when the joined response is presented.  Freeze this R11
execution identity; do not repair M935 or M1162 RTL.**

## Sealed execution boundary

The consumed-attempt marker exists and states `automatic_retry=false`.  The
94-member failure quarantine verifies recursively through `SHA256SUMS`, and
the outer seal verifies the manifest.  Compile/elaborate/link completed; the
simulator process returned through `$finish`, but the release runner correctly
returned 31 because the required phase/PASS gates were absent.  The canonical
result was not promoted and `functional_vcs_verified=false` remains binding.

## What executed

Directed, reset-pending, sticky-attack, and service-assumption phases all
completed.  Random phase entered and failed in transaction 0.  There are no
unmasked SVA assertion failures in the sealed R11 log.  The terminal oracle at
439.501 ns reports cycle 147 with wrapper request and responses retired,
`boundary_fault=0`, but both `core_fault=1` and `m935_fault=1`.  Thus R11 did
repair the earlier R9 request/response hold choreography, but exposed a deeper
stimulus-object mismatch before any normal M935 task ran.

## Exact first-fault reconstruction

After `reset_dut()`, transaction 0 never calls the task loader.  Both M935
banks remain `BANK_FREE`, `prep_active=0`, `match_active=0`, `exec_active=0`,
and no active row context exists.  Consequently the M935-internal
`issue_request_valid` expression is false.

The random helper nevertheless hierarchically forces the *parent boundary
connection* `dut.issue_request_*` and `dut.core_issue_data_ready`.  This lets
M1162 accept a synthetic tuple and service requests even though the child M935
has not produced a request.  Transaction 0's frozen PRNG update is
`0xbf3db94d`: `first=1`, response skew is three negedges, and response hold is
three sampled posedges.  Once the weight and psum responses are both present,
M1162 asserts `core_issue_data_valid` even while forced core ready is low.

At that first joined-response hold edge, M935 sees `issue_data_valid=1` while
its own real `issue_request_valid=0`.  Line 752 of the frozen M935 RTL therefore
sets `fault_condition_w`, and the next sequential update makes `fault_q`
sticky.  The terminal post-retirement edge is cycle 147; the exact R11
choreography places response acceptance at cycle 146 and the three joined
hold samples at cycles 143--145.  Therefore the first core-fault update is
cycle 143 (427.5 ns), not the post-retirement release window.

The alternative hypothesis that `retire_random_forced_issue_tuple()` creates
the fault after acceptance is contradicted by the RTL schedule.  The task exits
the acceptance loop only after `#1ps`; on the accepting edge M1162 has already
cleared `request_active_q` by NBA, so `core_issue_data_valid` is zero before the
tuple is released.  Moving tuple release to the following negedge would not
repair the actual violation.

Only one M935 fault predicate is live in this reset state: the unsolicited
`issue_data_valid && !issue_request_valid` check.  Residual data is zero and
INT8-format legal; no context, queue, scratch, bank-execution, relation, or
overflow predicate is active.  `boundary_fault=0` is expected: M1162 sees a
self-consistent forced wrapper tuple, while M935 correctly detects that data
arrived without a real core request.

## Relation to R9, M1225, and M1232

R9 used the same reset-then-force random model but never checked
`core_protocol_error` at random retirement.  Its per-transaction reset silently
cleared the sticky M935 fault, so all 24 random transactions could print
completion tokens despite not being legal integrated-core traffic.  M1225's
TB service-order diagnosis remains valid for R9's terminal normal-phase
timeout and 26 hold assertions, but its description of the random traffic as
legal was too broad.

M1232 correctly added exact request/response retirement and a post-retirement
core-fault oracle.  Its source checker, however, proved choreography around the
synthetic tuple; it did not prove that the request was generated by a prepared
M935 task.  The R11 post-retirement oracle is behaving correctly: it detects a
fault created earlier during the joined-response hold.

## Admission and repair decision

- **No retry:** M1250 is consumed and immutable.
- **No RTL repair:** M935's fail-closed predicate is correct; M1162's zero
  boundary fault is also correct for the tuple visible at its own boundary.
- **No narrow release-order TB patch:** keeping the forced tuple longer cannot
  make an unprepared M935 request legal.
- **Only a source-level TB redesign is logically admissible.**  There are two
  honest modes.  The preferred integrated mode loads a minimal real M935 task,
  waits for its unforced request, and randomizes only external service timing;
  response backpressure comes from real downstream sink readiness.  A narrower
  M1162-boundary-only mode may instead stub the *child core-output seam* by
  forcing `dut.u_frozen_m935.issue_request_*` and the corresponding child
  `issue_data_ready` output, rather than the parent connection.  That seam mode
  must reset M935 around every case and may claim only wrapper protocol
  behavior, never legal integrated-M935 execution.  Merely moving the existing
  parent force is not enough.  Either mode requires all 24 transactions, zero
  M935/M1162 faults, zero unmasked SVA failures, and the frozen real normal task.
- **Schedule recommendation:** freeze the R11 common-charge VCS chain unless
  the integrated protocol test is required for paper admission.  Existing C1
  evidence must not cite M1250 as a PASS.  If the chain is continued, it needs
  a materially new real-task stimulus, not another choreography-only R12.

This forensic ran no VCS, simv, EDA, GPU, or remote command and changed no DUT,
SVA, TB, contract, result, or frozen document.
