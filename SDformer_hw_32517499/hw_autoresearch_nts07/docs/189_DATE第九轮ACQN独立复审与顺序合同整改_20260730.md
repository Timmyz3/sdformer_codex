# DATE 第九轮 ACQN 独立复审与顺序合同整改

## 1. 独立复审结论

独立 DATE 硬件审稿结论为：

> **Weak Reject，2.2 / 5**

| 分项 | 评分 | 判断 |
|---|---:|---|
| 新颖性 | 2.2 / 5 | 保序 ACQN 仍接近 histogram softmax + index replay |
| 完整度 | 1.8 / 5 | 无 RTL、逐拍协议和物理存储实现 |
| 证据 | 2.5 / 5 | 原序整数检查有效，但不是 hardware-order RTL |

复审确认：

1. `ORDERED_MEMBER_REPLAY` 可以进入 RTL 证伪，但只能算算子微架构候选；
2. `CLASS_GROUPED_REPLAY` 才可能形成跨 normalizer/term-builder 数据流贡献；
3. 按类重排必须比较最终 Acc commit，而不是要求 member stream 保序；
4. Local5 只有接口兼容性，没有 post-G0/fullres ordered 收益证据；
5. Motion fission/fusion 继续保持淘汰状态。

## 2. 复审发现的四个整数合同漏洞

### 2.1 K 标志与 payload 可矛盾

旧随机向量独立生成 `k_nonzero` 与 `k_bits`，两套参考可能共享同一错误。

整改：

```text
k_nonzero == (k_bits != 0)
```

不满足时直接拒绝输入。

### 2.2 一个 row 混入多个 context

旧随机向量允许同一 normalization row 内逐 member 改变 context，但 denominator
却混合计算。

整改：

```text
一个 normalization row 只能属于一个 context
```

双 context 是两个独立 row 的流水重叠，不是同一 denominator 的混合输入。

### 2.3 active multiplicity 缺少独立 identity

旧参考把一个 active member 重复 `multiplicity` 次，但 destination、member id
和 K 完全相同，不能代表多个逻辑 identity。

整改：

- active member 必须逐 identity 保存，`multiplicity=1`；
- `multiplicity>1` 只允许用于不输出 member 的 zero-K class count；
- topology quotient 的 active multiplicity 必须另带完整 destination/relation
  identity list，不能借用本 ACQN 参考偷省。

### 2.4 `last` 被重复或丢失

旧参考会把输入 `last` 随 multiplicity 重复；若最后输入是 invalid/zero-K，
active 输出又可能没有 `last`。

整改：

- 输入 `last` 只标记 row 边界；
- active 输出在 invalid/zero-K 过滤后重新生成；
- 非空 active stream 只允许最后一项 `last=1`。

## 3. 整改后的结果

| 项 | 结果 |
|---|---:|
| directed rows | 10 |
| random rows | 20,000 |
| preserve-mean on/off row checks | 40,020 |
| mismatch | 0 |
| synthetic exp-eval reduction | 76.20% |

严格比较：

```text
row_sum_q8
n_tokens
原序 {context,member,destination,K,gate,last}
```

没有对输出排序。覆盖显式 T=`1/2/5/162/163/450`、score class `0..162`、
zero-K、invalid、宽 score span 和 equal-score active member。

76.20% 来自随机生成分布，只用于回归，不进入论文性能表。Motion 真实
profile100 的 exp/LUT work 仍使用：

- 无 exp cache：减少 83.97%；
- 2608-bit/context exp cache：减少 91.98%。

## 4. 架构状态重新冻结

### 4.1 不列贡献

以下不能作为 DATE 独立贡献：

- 163-entry histogram；
- occupied bitmap；
- 双 context；
- 保序 member SRAM replay；
- exp cache；
- 40,020 个 Python 检查。

这些是实现 ACQN 的必要机制和验证证据。

### 4.2 条件候选

只有以下结构可能晋级：

```text
score/class collect
  -> class-owned K-lane/destination structure
  -> normalization
  -> direct term emission
```

关键必须是**取消逐 member gate replay 和中间 gated-K 物化**，而不是把
member 链表按 class 排序后换一个名字。

### 4.3 双线边界

Motion：

- 有真实 ordered class/work profile；
- 允许进入 class-to-term 架构存储和周期预筛。

Local5：

- `Shiftmax5` 是强专用基线；
- 等 post-G0/fullres ordered trace；
- 在证据到达前不使用共享 ACQN 获益主张。

---

## 5. 下一轮架构证伪顺序

1. 先核算 `class-owned term` 相对
   `SCS active member + final-gate directory` 的完整状态、写端口和扫描周期；
2. 若固定 bitmap 使状态超过保序链路 1.20x，立即转为 lane-sharded sparse
   term/event store，不为 gate-stationary 强行保留大 bitmap；
3. Motion 用真实 ordered trace 报 slot/event overflow、mean/p95/p99；
4. Local5 单独评估 source-owned stencil wavefront，不强行共享 Motion
   normalizer；
5. 通过模型门槛后再写最小 score-to-term RTL。

当前结论不是“ACQN 已成为架构创新”，而是：

> **保序 ACQN 已具备 RTL 证伪所需的整数基础；真正的架构创新必须取消
> member replay，或者改变 Local5 的数据拥有者与执行顺序。**
