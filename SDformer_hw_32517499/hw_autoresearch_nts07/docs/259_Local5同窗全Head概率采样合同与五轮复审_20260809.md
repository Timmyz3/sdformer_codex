# Local5 同窗全 Head 概率采样合同与五轮复审

## 1. 本轮目标

上一轮 DATE 独立评审否决了 Relation Memo 的 1.342x headline：旧模型从同 stage 的 per-head group 池独立 bootstrap，既破坏同一 window 的 head 相关性，也没有保持 head 条件分布。

本轮只解决一个最高优先级缺口：为最终 epoch29 建立同一 `sample/block/window` 的全 head 正式 trace，并保证该 trace 能无偏估计全帧工作负载。

## 2. 为什么第一版仍不合格

第一版使用确定性轮转，每个 sample/block 只选一个 window。它能保证同窗全 head，但不能支持全帧推断：

- S0 每个 block 只覆盖 100/440 个位置，340 个位置没有实际覆盖。
- S1 只覆盖 100/120。
- sample id 是分层 cohort 的执行顺序，固定轮转会把样本内容与空间位置确定耦合。
- 没有纳入概率和分析权重，无法给出设计型置信区间。

因此第一版未启动正式 GPU profile。

## 3. 冻结后的概率采样合同

正式采样 ID：`uniform_plan_window_all_heads_v1`。

### 3.1 预提交计划

- 固定 seed：20260809。
- 对每个 `sample/stage/block`，用与数据值无关的 SHA256 PRF 派生本地 seed，并从该 block 的全部 window 中均匀抽一个。
- 每个 window 的纳入概率为 `1 / batch_windows`，所有 window 均有非零概率。
- 分析时使用 `batch_windows` 作为 Horvitz-Thompson 权重，并以 sample 为 cluster 计算置信区间。
- 计划在模型推理前写出并绑定 cohort SHA256、计划 SHA256、seed、stage/head/window 几何。

计划文件：

`results/local5_fullres_bb1e4_joint_heads_profile100_20260809/joint_window_selection_plan.json`

计划含 1200 条记录，即 `100 samples x 12 blocks`。实际抽中位置的去重覆盖不是无偏性的前提，但作为审计信息为：

| Stage | 每 block window 总数 | 两个/多个 block 的实际去重覆盖 |
|---:|---:|---|
| S0 | 440 | 88、93 |
| S1 | 120 | 71、69 |
| S2 | 30 | 28--30 |
| S3 | 10 | 10、10 |

### 3.2 同窗全 head 编码

每个被抽中的 window 必须按 canonical head 顺序导出：

- S0：head 0--2。
- S1：head 0--5。
- S2：head 0--11。
- S3：head 0--23。

正式预计组数为：

`100 x (2x3 + 2x6 + 6x12 + 2x24) = 13800`。

采样 wrapper 只在独立进程中临时替换基类 selector，原 `profile_local5_hardware_features.py` 文件和旧 `coprime_rotating_flat_window_head_v1` 合同均未修改。

## 4. Fail-closed qualification

正式输出必须同时通过：

1. 100 samples、12 modules、精确 stage/block 集合。
2. 固定 stage→heads 映射 `{0:3, 1:6, 2:12, 3:24}`。
3. 固定 stage→batch-windows 映射 `{0:440, 1:120, 2:30, 3:10}`。
4. 每个 module/sample 恰好一个计划 window，head 按升序全覆盖。
5. `flat_group = window x heads + head`。
6. T450、32 lanes、13800 groups。
7. 每条记录 sampling ID、selection plan 和 run identity 一致。

身份加载器要求固定的十项 source-binding 名称、路径和 SHA256，不能再由 identity 自报任意非空文件集合。release receipt 还会与 ranking、best epoch、checkpoint 和 config 逐字段交叉验证。

## 5. 输出完整性与 GPU 独占

### 5.1 输出完整性

`output_complete()` 不只检查 manifest 和组数，还重新验证：

- ordered payload 的存在与 SHA256。
- cohort 文件的存在与 SHA256。
- projection contract JSON/NPZ 的存在与 SHA256。
- run identity、selection plan、config、checkpoint 与 source bindings。
- GPU 独占审计回执中的 identity/manifest/payload SHA256。

### 5.2 GPU 独占审计

Local5 与未来 Motion profile 共用 `results/gpu_profile_lease.lock`。Local5 正式运行还增加运行期 watchdog：

1. 启动前目标 GPU 的 compute PID 必须为空。
2. 每 2 秒读取 compute PID，只允许当前 runner 的子孙进程。
3. 出现外来 PID、`nvidia-smi`/`ps` 异常或子进程异常时，审计状态写为 `INVALID`。
4. 清理按 PGID 执行 TERM→30 秒→SIGKILL；即使父进程先退出，也必须等整个 PGID 消失后才释放 lease。
5. 只有退出码为 0，且 manifest/payload/identity 哈希闭合后，才写 `PASS`。
6. `output_complete()` 必须看到 `PASS`，所以独占失败后留下的完整 manifest 也不能被下次误复用。

审计文件：

`results/local5_fullres_bb1e4_joint_heads_profile100_20260809/gpu_exclusivity_audit.json`

## 6. 验证结果

- `[测试]` 新采样与旧 ordered sink 联合单测 14/14 PASS。
- `[测试]` 正式 plan/identity dry-run：1200/1200 key 加载通过。
- `[测试]` stage-head 错配与缺 head 均被 qualification 拒绝。
- `[测试]` canonical head 顺序通过。
- `[测试]` 父进程先退出、后台子进程仍存的 orphan-PGID 场景完成强制清理。
- `[测试]` GPU audit 为 `INVALID` 时，`output_complete()` 返回 false。

这些是 profile 基础设施验证，不是 DATE 架构贡献。

## 7. 五轮独立复审

| 轮次 | 主要发现 | 整改结果 |
|---:|---|---|
| 1 | 固定轮转存在空间采样偏差；identity、payload、head 映射和顺序不够严格 | 改成预提交均匀概率计划，并补全 provenance/完整性/canonical order |
| 2 | GPU lease 未约束未接入锁的 producer | 增加运行期 compute-PID watchdog，Motion runner 接入同一 lease |
| 3 | 独占失败后旧 manifest 仍可能复用；通用异常无 KILL 兜底 | 引入 `RUNNING_UNVERIFIED/INVALID/PASS` 审计与统一 TERM→KILL |
| 4 | 父进程已退出时可能遗留同 PGID 子进程 | 清理判据改为 PGID 存在性，不再依赖父进程 poll |
| 5 | 无剩余阻断或高风险 | 批准启动等待型正式 watcher |

## 9. Relation Memo 的下一门槛

正式 trace 完成后，必须直接使用同窗 head 集合，不再独立 bootstrap head：

1. 以计划权重计算全帧 recompute 与 7 KiB pack/replay/fallback 周期。
2. 以 sample 为 cluster 做 bootstrap 置信区间。
3. Acc32 逐项零失配。
4. 全帧 speedup 的 95% 置信下界不低于 1.15x。

通过后才允许把 Relation Memo 接入最终 checkpoint-bound 单顶层 RTL；未通过则降级为待 SRAM 能耗验证的候选，不再扩大 RTL。
