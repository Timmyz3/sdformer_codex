# Local5 三输入头 OUT32 跨头数值与 12-Block 结构闭环

日期：2026-08-09

## 1. 本轮结论

本轮只推进 `docs/274` 独立 DATE 评审指定的唯一最高优先级缺口：把 scheduler 的
`head_job` 真正接到生产宽度 T450 数值引擎，并在同一个 output tile 内完成三输入头
Acc32 精确归约。

- `[rtl]` 新增 `qfit_local5_cross_head_tile_executor`，复用一个 T450/OUT32 数值引擎
  顺序执行三个 input head；
- `[rtl]` 真实 `gatestack_output_tile_scheduler` 直接发出三个 `head_job`，没有由 TB
  手写 head 顺序；
- `[rtl]` 43200 个 partial Acc32 完成 43200 次 exactly-once 跨头累加写入，最终
  14400 个 Acc32 逐项等于三个独立 Python head oracle 的整数和；
- `[rtl]` 最后一个 `head_done` 被 scheduler 接受后才开始 final drain，最后一个
  final result 被接受后才产生 `tile_done`；
- `[rtl]` 三种随机 Token/weight 服务时序与 final-result 反压在 Icarus 和
  Verilator/SVA 中周期、账本和数值完全一致；
- `[rtl]` 错 head-job tag 与错 head id 在发出任何 Token、weight 或 partial write
  之前 fail-closed；
- `[rtl]` 新增 `qfit_local5_encoder_t450_numeric_shell`，把现有 12-block frame
  scheduler 和同一个 tile executor 做了结构级直连。

本轮显著前移的是 Local5 系统完整度，不是新增 DATE 架构创新。1RW 累加、跨头求和、
FSM、ready/valid 和 12-block 时间复用本身都不得单列为论文贡献。

## 2. 修复了什么断点

此前存在两条彼此独立的证据：

1. `docs/273` 证明 12-block scheduler 的 1320 group、6720 tile、54000 head job
   控制账本；
2. `docs/274` 证明一个 input head、一个 output tile 的 tagged T450 数值作业。

两者之间没有真实连线，也没有跨 input-head partial-sum 合并。因此不能回答：

- scheduler 发出的 head/tag/tile 身份是否能直接驱动数值核；
- 每个 head 的 14400 个 OUT32 partial 是否只写一次正确地址；
- 中间 head 是否会提前暴露 tile result 或 `tile_done`；
- 最终 OUT32 是否等于所有 input head 的整数和；
- 错 head/tag 是否会污染已经建立的跨头 Acc32。

本轮把这五个问题放入同一个 transaction 和同一套回归。

## 3. RTL 数据流

```text
12-block frame descriptor
  -> qfit_local5_encoder_job_scheduler
       -> tile_start {stage, block, window, output_tile, head_count, tag}
       -> head_job[0 .. head_count-1]
            |
            v
       qfit_local5_cross_head_tile_executor
            -> 单套 qfit_local5_tagged_t450_job_engine
                 -> Q7 score / integer Shiftmax5
                 -> relation transpose
                 -> source-major term
                 -> TCFM5 five-bank projection
                 -> 450 x OUT32 partial Acc32
            -> shared 1RW cross-head Acc32 address space
                 head 0: first-touch write
                 head 1..N-1: read-modify-write
            -> 450 x OUT32 final drain
       <- head_done after each complete partial stream
       <- tile_done after final drain
```

物理上只有一套 T450 数值引擎，不按 3/6/12/24 个 head 或 12 个 encoder block
实例化。scheduler 通过描述符把 stage、block、window、head 和 output tile 映射为
时间上的作业序列。

## 4. 跨头 Acc32 合同

单个 output tile 的最终地址空间是：

```text
addr = (((plane * 15 + y) * 15 + x) * 32) + out
depth = 2 * 15 * 15 * 32 = 14400
width = 32 bit
storage contract = 460800 bit
```

每个 head 的 tagged 引擎必须严格按地址 0 到 14399 输出 partial。executor 同时检查
tag、input head、output tile、坐标、out、顺序和 `last`：

- head 0 对每个地址执行 first-touch write；
- 后续 head 使用单端口同步 read-modify-write；
- RMW 未提交时对子引擎施加反压；
- `perf_accumulator_writes` 在 clean `head_done` 时必须等于
  `perf_partial_results`；
- 任何身份或顺序错误都不得产生对应的 memory command。

整数加法使用 32-bit 二补码合同，与 Python oracle 的部署整数顺序一致。本轮没有
加入饱和、舍入或近似。

## 5. Scheduler 完成时序

```text
tile_start accepted
  -> head 0 job -> 14400 partial accepted -> child release -> head_done 0
  -> head 1 job -> 14400 partial/RMW committed -> head_done 1
  -> head 2 job -> 14400 partial/RMW committed -> head_done 2
  -> scheduler enters tile wait
  -> 14400 final results drain under backpressure
  -> tile_done
  -> group_done
```

`head_done` 和 `tile_done` 都是可反压 ready/valid。SVA 要求它们在 stall 时身份和
error 字段稳定；`tile_done` 的首次 valid 必须紧跟最后一个 final result 的真实
握手，不能只跟内部读请求或最后一个 head 的结束脉冲。

## 6. 数值与协议证据

一键入口：

```bash
sim_qfit/run_qfit_local5_cross_head_out32_checks.sh
```

产物：

```text
results/qfit_local5_cross_head_out32_20260809/report.{md,json}
```

三个 Python head 使用不同 Q/K 随机种子和同一可审计 INT8 weight 函数：

| 账本 | 数量 |
|---|---:|
| scheduler tile | 1 |
| input head | 3 |
| Token request/response | 1350 |
| weight request/response | 3072 |
| partial Acc32 | 43200 |
| accumulator write | 43200 |
| final Acc32 | 14400 |

跨模拟器正式结果：

| 服务种子 | Icarus 周期 | Verilator/SVA 周期 | result stall | mismatch |
|---:|---:|---:|---:|---:|
| 17717 | 263621 | 263621 | 14400 | 0 |
| 44257 | 263888 | 263888 | 14462 | 0 |
| 48879 | 263844 | 263844 | 14450 | 0 |

周期包含 TB 的 1--4 拍服务延迟、final-result 随机反压和 1RW RMW，不能解释为 SRAM
macro 周期、目标频率、整帧吞吐或 FPS。

## 7. 故障与 SVA

两个定向故障在接受 tile 后分别注入：

1. 首个 head job 的 tag 错一位；
2. 首个 head job 的 input-head id 从 0 改为 1。

Icarus 和 Verilator/SVA 均观察到 `head_done_error`，且 Token request、weight request、
partial result、accumulator write、final result 和 `tile_done` 全为 0。SVA 还覆盖：

- head/tile completion 和 final result 反压稳定；
- final result 几何范围；
- clean head 的 partial/write 完整账本；
- clean tile 的 final-result 完整账本；
- accumulator write 永不领先 partial；
- protocol error 粘滞且停止外部工作。

`docs/274` 复审指出的 Token Q/K/mask 和 weight data response payload 稳定性也已在
子引擎 SVA 中补齐，并重新通过原四种时序与 12 类故障回归。

## 8. 12-Block 结构边界

`qfit_local5_encoder_t450_numeric_shell` 实际例化：

```text
qfit_local5_encoder_job_scheduler
  + qfit_local5_cross_head_tile_executor
```

所以 12-block scheduler 的 `tile_start/head_job/head_done/tile_done` 已有同一顶层真实
连线，能够在外部 Token/weight/result service 完整时执行全帧。但本轮没有运行
54000 个真实数值 head job；按当前串行核每个 tile 数十万拍，直接全帧回放既昂贵，
也不能替代 relation memo 和系统性能建模。

更重要的是：当前 shell 对后续 output tile 仍重新计算 relation。scheduler 的
`decode_required/cache_release` 已传入并做身份检查，但 relation memo 尚未接入数值
路径。因此该 shell 是 exact 的完整性基线，不是最终性能架构。

## 9. 开放综合口径

Yosys 对 executor 和 12-block shell 分别执行 hierarchy check、`memory_collect`、
flatten 和结构检查。报告中的 generic cell 和 `$mem_v2` 只用于证明模块与 460800-bit
Acc32 存储合同可综合读取。

不得把这些值写成：

- DC 面积；
- SRAM macro 面积；
- STA 频率；
- SAIF/PTPX 功耗；
- ASIC EDP。

最终数值以 `results/qfit_local5_cross_head_out32_20260809/report.md` 为准，不在本文
手抄可能变化的开放工具统计。

## 10. DATE 贡献边界

本轮可以作为论文可信度证据写：

> `[rtl]` Local5 的生产宽度 scheduler-to-projection 路径已在真实 T450、三输入头、
> OUT32 和跨头 Acc32 下完成 bit-exact 数值闭环；一个物理引擎按 descriptor 时间复用
> 服务 encoder 作业，并通过 transaction-level completion 保证中间 partial 不外露。

但它不应单列成“新架构贡献”。论文的创新性仍应来自已冻结或待完成的上层机制：

- Local5 关系结构驱动的 source-major/TCFM5 数据流；
- relation 在多个 output tile 间的 exact memo/replay；
- workload 证明后才能成立的本土化复用或流量消除机制；
- Motion 线独立的 SCS/NMF/DCTF/RQTB2S，不与 Local5 强行混写。

## 11. 仍未完成

- `[待验证]` relation memo 的首访建立、后续 output-tile replay 和最后 tile release
  尚未接入本轮 scheduler-to-numeric shell；
- `[待验证]` Local5 fullres checkpoint 的 theta/invalid-mask/hardware-order exact
  语义仍等待算法侧最终产物；
- `[待验证]` 跨头 bias、no-running BN、requant 和残差端口；
- `[待验证]` 多 stage/tile 的真实 trace 数值回放；
- `[待验证]` 真实 SRAM latency、DC/STA/SAIF/PTPX。

## 12. 下一轮唯一最高优先级

把已有 FCSR/relation memo 接入本轮真实 scheduler 路径：首个 output tile 对每个 head
建立 relation/term memo，后续 output tile 从 memo replay，最后 output tile 在 clean
completion 后 release。签核必须同时比较 recompute baseline 与 memo path 的 Acc32、
Token/descriptor traffic、周期和存储占用；若真实多 tile 不能产生净收益，就保留本轮
recompute shell 作为基线，不把 memo 包装成贡献。

Motion 线不停止。Local5 完成这项系统闭环期间，Motion 继续维护现有多样本
SCS/NMF/DCTF/RQTB2S 回归，并在有真实 profile 支撑时再扩新机制。

## 13. 独立 DATE 评审

独立只读 DATE 审稿人给出：

| 范围 | 评分 | Recommendation |
|---|---:|---|
| 本轮工程证据包 | 4.0/5 | 条件通过，可作为 bit-exact 单 tile 集成基线 |
| 整个 Local5 硬件线 | 3.7/5 | 边界附近，仍需 major revision |
| 架构创新性 | 2.0/5 | 不因常规累加器/FSM/时间复用加分 |

相对 `docs/274` 的整个 Local5 `3.4/5` 提升 0.3，来源是 scheduler-to-T450 真实
连接、三头 OUT32 归约、completion 时序和错误路径；不是创新性提升。

审稿 findings 及处理如下：

1. **高：12-block 只是结构连接，不是全帧数值闭环。** 判断成立，本文第 8、11 节
   和结果报告均已明确只数值回放一个 stage0 三头 tile；不修改证据边界。
2. **中：exactly-once 缺少运行中 duplicate/drop/乱序/错 last 注入。** 判断成立。
   当前由地址顺序检查、最终 miter 和账本间接证明；下一轮在 memo/recompute 共用
   partial 边界加入定向注入，不能把当前覆盖说成完整形式证明。
3. **中：fail-closed SVA 没有直接观察 accumulator memory command。** 判断成立。
   当前错误 TB 只覆盖作业入口错 tag/head。下一轮增加运行中错误，并直接断言坏
   partial 当拍不产生 memory command、错误后 write 计数冻结。
4. **低：审稿材料中没有 Yosys 原始命令/版本。** 该意见不适用于完整仓库证据包：
   一键 runner、`tool_versions.txt`、两个 Yosys log、hierarchy/flatten JSON 和源码
   SHA 均已落盘；但主文仍只把它们称作开放工具代理。

最终结论：本轮按“工程完整度包”收口，不再用常规控制修补追求创新分。下一轮唯一
任务维持第 12 节：真实 scheduler 多 output-tile 的 recompute/memo/replay/fallback
单顶层，同时补 partial 流和内部 memory-command fail-closed 故障。
