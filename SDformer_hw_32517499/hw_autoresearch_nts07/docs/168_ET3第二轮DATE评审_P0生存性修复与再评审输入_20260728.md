# ET3 第二轮 DATE 评审、P0 生存性修复与再评审输入

## 1. 第二轮独立评审结论

独立 DATE 审稿 subagent 对 `docs/167` 与首版 ET3 RTL 的结论是：

| 项目 | 结果 |
|---|---:|
| Recommendation | Reject |
| 当前完整度 | 2/5 |
| 当前创新性 | 2/5 |
| 证据完整度 | 1/5 |
| 目标潜力 | 3/5 |

审稿人认为首版 ET3 尚未区别于普通：

```text
typed CAM/group-by
+ segmented queue
+ overflow FIFO
+ multiplicity scalar folding
```

这个判断成立。首版输入已经是 `{gate,lane,multiplicity,destination}`，尚未把 Motion SCS/NMF 或 Local5 Shiftmax/MFEP 直接接入目录，因此不能声称已经实现“tile-to-term transduction”，只能称为 typed-term aggregation/execution 原型。

## 2. 审稿人发现的三个 P0 正确性问题

### 2.1 目录与 fallback 同时满时死锁

首版只有收到 `source_head_last` 后才开始发射。若最后一个 source item 之前目录和 fallback 同时满：

```text
source_ready = 0
无法接收最后 item
无法看到 source_head_last
无法切换到 emit
```

这是结构性死锁，首版小测试未覆盖。

### 2.2 不同 group 的 accumulator 污染

首版只在 `run_start` 清 accumulator，却允许一次 `run_start` 连续处理多个 group。不同窗口通常复用相同 local destination ID，因此前一个 group 的结果会污染下一个 group。

首版测试让 Motion 与 Local5 使用不相交 destination，掩盖了该问题。

### 2.3 zero-term group 无法表达

首版 group 结束只能附着在最后一个 source item 上；若整个 head/window 没有 term，就没有 item 可以携带 `head_last`。这与 Motion 高 empty ratio 以及 Local5 的零 term window-head 不符。

## 3. 本轮修复

### 3.1 Drain-and-resume

当满足以下条件时：

```text
state == COLLECT
source_valid == 1
source contract valid
directory full for this key
fallback full
```

目录不接受也不丢弃当前 source item，而是：

1. 将当前 chunk 标记为 non-final。
2. 发射已有 directory 与 fallback。
3. 清空 chunk 容量，但保留 `group_tag` 与 group 生命周期。
4. 回到 COLLECT。
5. 上游仍保持的 source item 随后被接受。

新增 `count_partial_drains` 审计实际发生的中途排空次数。

### 3.2 每 group 一个 run epoch

新合同规定：

1. 每个非空或空 group 前必须单独 `run_start`。
2. `run_start` 清 accumulator 与 executor 工作计数。
3. 收到最终 `cmd_head_last` 后，executor 自动将 `run_active` 拉低。
4. `run_active=0` 时顶层禁止接受新 source 或 group close。
5. 下一 group 必须再次 `run_start`，因此相同 destination ID 不会串组。

该合同保持结果在 `group_done` 后可读，直到下一次 `run_start`。

### 3.3 显式 empty-group close

新增独立接口：

```text
group_close_valid
group_close_ready
group_close_tag
```

它可在没有任何 source item 时结束 group。目录完成 zero-term commit 后，通过 `empty_group_commit` 让 executor 产生 `group_done` 并退出当前 epoch。

### 3.4 单一首 beat product 节点

首版 term 首 beat 对 `product_q` 和 accumulator 各调用一次 `make_product()`。虽然综合器可能做公共子表达式消除，但计数器不足以证明结构共享。

修复后先生成唯一 `first_product[out]` 组合节点，再同时写入 `product_q` 与首 destination accumulator。该修改仍不能替代门级网表检查，但消除了 RTL 中的重复函数调用。

## 4. 增强后的验证

测试参数改为：

```text
KEY_CAP=2
SEG_DEPTH=2
FALLBACK_DEPTH=1
```

现在覆盖：

1. Motion SET 同 key 分段。
2. Local5 MULTISET 同 key 分段。
3. 两个 group 均先填满目录与 fallback，再由 held source 触发 drain-and-resume。
4. Motion 与 Local5 复用相同 destination ID，验证每 group epoch 清零。
5. 独立 zero-term group close。
6. 输出随机相序式确定性反压和 stalled payload 稳定。
7. 两个非空 group 分别与 dense integer accumulator 对比。

回归结果：

```text

Icarus: PASS
Verilator lint: PASS
Verilator simulation: PASS
Yosys check: PASS
```

## 5. 修复后仍不成立的主张

下列拒稿原因没有因为 P0 修复而消失：

1. 当前目录输入已经是 term source item，未接 normalization 或 MFEP，不能称为完整 tile-to-term。
2. 未做 post-G0/full-resolution ordered Local5 trace。
3. 未比较普通 per-destination native-m queue 与流式 ET3。
4. 目录是寄存器/CAM 风格原型，尚未给出可宏化的 tag/payload 分层。
5. executor 仍是小尺寸单体数组，不是最终 bank-local SRAM 实现。
6. 无目标工艺 DC/STA/SAIF。

因此，当前创新性分数最多只能保持 2/5。修复提高的是正确性与生存性，不应包装为新贡献。

## 6. 主线决策

保持：

- **Motion：唯一硬件主线。**
- **Local5：shadow track。**

Local5 只有在 post-G0/full-resolution ordered trace 下证明在线 ET3 能保留足够复用并带来净收益后，才重新比较是否切主线。

## 7. 下一轮唯一候选切片

遵循审稿人建议，下一轮只做：

> Local5 post-G0/full-resolution ordered trace 下，普通 per-destination native-m queue 与流式 ET3 的生存性和收益比较。

预冻结淘汰门槛：

1. 任意 mismatch 或 deadlock：立即淘汰。
2. 可宏化容量下保留不足 70% 的离线 product-reuse 机会：淘汰。
3. 相对普通 native-m queue 的周期或关键流量净改善不足 15%：不进入目标工艺 PPA。

在 GPU 被 full-resolution 训练占用期间，只能准备 trace schema、CPU replay 和 RTL 接口，不能用 synthetic ordered vectors替代该决定性证据。
