# H67 GateStack 双窗口投影架构与文献反证（2026-07-15）

> **2026-07-15 存储架构迭代**：本文的固定 destination bitmap 方案存在 token-major 写、lane-major 读的 SRAM 转置端口问题，已降级为反例消融。当前主线改为容量安全的 `TERM-CSR/RAW` 双格式 head slot、活动 token 跳读和双 context，详见 `docs/84_GateStack_CSR容量安全存储与架构主线修正_20260715.md`。GateStack 的最终门码复用和 head-stacked 循环仍保留。

## 1. 定位

本方案把现有 G1“最终门码目录行核”扩展为完整 projection 数据流，暂命名：

> **GateStack：面向全二值事件注意力的 Head-Stacked Final-Gate Reuse Architecture**

它不采用异构 dense/sparse 双核。核心是利用 H67 在 single Shiftmax 之后产生的最终 gate code，把相同 gate 的 token 目的集合压成目录，并通过 **跨 output-tile 重放、跨 head 持久累加、双窗口上下文和无损双格式 fallback**，形成可验证的系统级投影架构。

创新判断必须克制：双缓冲、ping-pong、流水和 bitmap 本身都不是新颖点。可争取的新颖性来自 H67 特有的最终门码等价关系如何改变完整多 head 投影的循环顺序、存储表示和无损执行协议。

## 2. 软件语义和完整计算边界

对一个窗口、一个输出通道 `o`：

```text
Y[t,o] = B[t,o]
       + Σ_h Σ_l (G[h,t] × K[h,t,l]) × W[h,l,o]
```

其中：

- `t ∈ [0,161]`，窗口 token 数固定为 162；
- 每个 head 的 `D=32`；stage 的 head 数为 `H={3,6,12,24}`；
- `G` 是 single Shiftmax 后的定点最终 gate；
- `K` 是 all-binary gated-K event；
- `W` 是投影权重；
- `B`、累加和输出 requant 的位宽需独立冻结。

若两个 token 在同一 head 上具有相同最终 gate code，且某个 K lane 均为 1，则该 lane 对这两个 token 使用完全相同的 `gate × weight-vector`。GateStack 只复用这个 **bit-exact 公共乘积**，不裁剪 token、不近似 gate、不修改 Shiftmax 分母。

## 3. 为什么现有 G1 不是完整 projection

现有 `hitflow_g1_projection_top` 的真实覆盖是：

```text
1 个输入 head × 1 个 output tile × 162 token × 32 lane
```

缺少：

- `global_input_channel = head_id × 32 + lane_id`；
- `output_tile = 0 ... H-1`；
- 同一 output tile 跨全部输入 head 的持久部分和；
- 最后一个输入 head 后才进行 bias/final；
- overflow 时的 direct 无损路径；
- output requant 与下一 ATLIF event 接口。

因此 GateStack 不是给现有顶层加一个状态，而是重写 projection 的循环和上下文生命周期。

## 4. 核心数据流

### 4.1 循环重排

常规逐 head 流式执行容易在每个 output tile 反复解析 token/gate。GateStack 先为窗口内全部 head 建立最终门码目录，再跨 output tile 重放：

```text
for window w:
    for input_head h:
        build GateDirectory[w][h]       # 每个 head 仅建一次

    for output_tile ot:
        clear AccTile[w][ot]
        for input_head h:
            replay GateDirectory[w][h]
            fetch W[h, lane, ot]
            product -> multicast -> accumulate
        commit bias
        requant/final emit
```

第二个窗口上下文同时接收下一窗口 token：

```text
Context A: replay/drain window n
Context B: build window n+1
完成后交换 A/B
```

这把测得的 `T=162` build 相与目录/backend 相重叠；它不是声称所有三相都免费，bias/requant 是否可重叠由端口和 RTL replay 决定。

### 4.2 单 head 目录格式

主格式：

```text
slot[0:S-1]: {valid, gate_code[8:0], lane_bitmap[D][T]}
occupied_mask[S][D]
```

默认 `S=4,D=32,T=162`，主要 bitmap 为：

```text
4 × 32 × 162 = 20,736 bit = 2.53125 KiB/head
```

不能沿用当前 G1 的固定 128 项扫描。builder 在写 destination bitmap 时同步置位 128-bit `{slot,lane}` occupancy mask；replay 使用分层 priority iterator，只访问置位项。该结构额外 `128 bit = 16 B/head`，约为 bitmap 的 0.62%，且不会产生“一个 token 新增 32 条索引”的多写口问题。profile100 平均约 10.6 条有效项，OBI（Occupied-Bit Iterator）是 GateStack 能否抵消目录扫描开销的必要结构，必须与 fixed-scan 做 RTL/PPA 消融。

profile100 中 `S=4` 仅 95/672000 个 trace group overflow。低概率不能成为静默丢数的理由，必须使用 exact fallback。

### 4.3 双格式无损 fallback

建表时同步保存当前 head 的原始：

```text
RawHead[t] = {gate_code[8:0], K_bits[31:0]}
```

每 head 原始暂存：

```text
162 × (9 + 32) = 6,642 bit = 0.811 KiB
```

提交规则：

1. 不 overflow：提交目录格式，释放 raw scratch。
2. overflow：把该 head slot 标为 `DIRECT`，保存 raw 表示；replay 时逐 token 走 direct product。
3. 两种格式都执行同一个数学式，结果必须 bit-exact。

若保守按 overflow 后复制 162 个 token 计，profile100 平均额外代价约为：

```text
95 × 162 / 672000 = 0.0229 cycle/group
```

实际代价仍以 RTL cycle replay 为准。

## 5. 存储层次

### 5.1 三级存储

```text
L0  GateStack context SRAM
    - 两个窗口的 head directory/direct slot
    - 每个 context 的 head valid/mode/overflow 元数据

L1  Projection working SRAM
    - 一个 162×32×32-bit AccTile
    - 当前 head raw scratch
    - 分段 multicast queue

L2  Weight/Bias SRAM
    - 按 {output_tile, input_head, lane} 顺序提供 32-lane weight vector
    - 独立 bias 和 requant 参数端口
```

### 5.2 上下文容量

不计 weight SRAM，按双窗口目录、一个 `162×32×32-bit` 累加 tile 和一个 raw scratch：

| Stage | H | 双 context 目录 | OBI mask | AccTile | Raw scratch | 合计 |
|---|---:|---:|---:|---:|---:|---:|
| 0 | 3 | 15.19 KiB | 0.09 KiB | 20.25 KiB | 0.81 KiB | **36.34 KiB** |
| 1 | 6 | 30.38 KiB | 0.19 KiB | 20.25 KiB | 0.81 KiB | **51.63 KiB** |
| 2 | 12 | 60.75 KiB | 0.38 KiB | 20.25 KiB | 0.81 KiB | **82.19 KiB** |
| 3 | 24 | 121.50 KiB | 0.75 KiB | 20.25 KiB | 0.81 KiB | **143.31 KiB** |

stage3 仍低于暂定 160 KiB 门槛，但还未计 SRAM ECC、bank padding、FIFO 和 metadata；综合前必须由 memory compiler 宏尺寸重算。

## 6. 微架构模块与接口

| 模块 | 职责 | 关键接口 |
|---|---|---|
| `gatestack_window_scheduler` | 管理 stage/window/head/tile 生命周期 | descriptor、context ownership、done |
| `gatestack_exact_builder` | 建目录并同步 raw scratch | gate/K token stream、head commit |
| `gatestack_context_sram` | 双窗口 head-stacked 存储 | build port、replay port、mode metadata |
| `gatestack_replay_scheduler` | 按 output tile 和 input head 重放 | global channel、tile、term/bitmap |
| `gatestack_direct_fallback` | DIRECT slot 逐 token 无损执行 | raw token、weight request、product |
| `gatestack_product_cluster` | 默认 `P=1` gate×weight vector | weight req/rsp、product ready/valid |
| `gatestack_segmented_multicast` | bitmap 到 token bank 更新 | segment、bank backpressure |
| `gatestack_persistent_accumulator` | 跨全部输入 head 保持部分和 | update、tile start、bias、final |
| `gatestack_requant_emit` | 定点截断/饱和并生成下一层 event | acc、scale/shift、binary event |
| `gatestack_perf_counters` | 分账 build/replay/fallback/stall | 周期和事件计数器 |

必须显式携带的标识：

```text
{window_tag, context_id, stage_id, input_head_id, output_tile_id,
 global_input_channel, token_id, format_mode}
```

所有 payload 通道使用 ready/valid；context 只有在最后一个 output tile final handshake 后才能释放，不能仅凭内部 FSM 到达 DONE 就覆盖。

## 7. 控制状态和不变量

建议把控制拆为 context manager 与 tile executor，避免一个巨型 FSM。

Context 状态：

```text
FREE -> BUILD_HEADS -> READY -> REPLAYING -> RETIRE -> FREE
```

Tile executor 状态：

```text
TILE_START -> REPLAY_HEADS -> WAIT_DRAIN -> BIAS -> REQUANT -> TILE_DONE
```

必须用 SVA 验证：

1. overflow head 只能进入 DIRECT，不能同时重放不完整目录。
2. bias 只能在该 tile 的最后一个 input head drain 后提交。
3. final 之前每个 token 的 bias 恰好提交一次。
4. `global_input_channel = head_id × 32 + lane_id` 且不越界。
5. output tile 覆盖 `0 ... H-1`，每个 tile 恰好完成一次。
6. context 未 retire 前不可被新窗口覆盖。
7. 任意 backpressure 下 tag、bitmap、product 和 accumulator 不串窗。

## 8. 性能模型和淘汰线

当前 ordered-trace 单组模型给出：

- 当前 G1 扫描下界相对可流式 direct：`1.176x`；
- 双 context 候选：`1.556x`；
- 三相全重叠上界：`2.537x`，只作上界。

完整窗口模型 `scripts/model_gatestack_full_projection.py` 进一步按连续 head 聚合 132000 个窗口，并允许 direct 基线同样使用两个输入 context。默认 `S=4,P=1,M=4,L=32,B=4`：

| delivery效率 | fixed-scan双context | OBI单context | OBI双context |
|---:|---:|---:|---:|
| 100% | 0.449x | 1.581x | 1.825x |
| 85% | 0.446x | 1.497x | **1.692x** |
| 70% | 0.440x | 1.386x | 1.526x |

固定扫描在完整 output-tile 重放后会比 direct 慢，说明 OBI 是主架构必要组成，不是可选优化。85% delivery 敏感性下分 stage 结果为：stage0 `1.821x`、stage1 `1.117x`、stage2 `1.519x`、stage3 `2.050x`。控制器因此保留 descriptor 级 `DIRECT/OBI` 模式；stage1 是否旁路目录由目标库 EDP 决定，不能只凭 cycle 决定。

完整 GateStack 必须新增按 stage/head/output-tile 的 cycle replay，公平计入：

```text
build + directory fixed scan + weight SRAM wait + product + multicast
+ accumulator bank conflict + fallback + bias + requant + context switch
```

量化淘汰门槛：

| 项 | 最低门槛 | 目标 |
|---|---:|---:|
| bit-exact | 100% | 100% |
| overflow directed coverage | 每 stage 至少 1000 组 | 随机+形式辅助 |
| cycle speedup vs streaming direct | 1.20x | 1.40x 以上 |
| p99 context stall | 不高于 direct | 降低 20% |
| stage3 非 weight SRAM | ≤160 KiB | ≤150 KiB |
| fallback 平均周期占比 | <1% | <0.1% |
| 目标库频率 | 500 MHz WNS≥0 | 留 10% 裕量 |
| 能效 | 同工艺同频同 SRAM 端口 EDP 改善 ≥15% | ≥25% |

任何一项不满足时的处理：数值失败立即淘汰；速度低于 1.20x 时降级为后端算子；SRAM 超标时先评估单 context 或 stage3 分块，不能隐去存储成本。

### 对“蝶形网络包装”的结论

现在不应该为了论文名义强行加入蝶形网络。复旦 ISSCC 工作和 FABNet 的蝶形机制都有明确的结构化稀疏或算法变换前提，而 H67 当前可证明的是动态最终门码和 K event 的稀疏。若没有权重结构化训练、路由冲突统计和 EDP 正收益，蝶形只会增加控制、交换和审稿反证风险。

蝶形候选只有同时满足以下条件才重新进入 DSE：

1. 软件权重或 token 路由呈可映射的固定结构。
2. 相同 bank/端口预算下，交换网络 EDP 至少改善 15%。
3. 不改变 H67 bit-exact 输出，或算法变化重新完成 full30/valid825。
4. 相对 segmented multicast 的面积和布线收益由目标库/物理估计证明。

## 10. 可投稿贡献表述

在完整 RTL 和 PPA 通过前，只能写成候选：

1. **最终门码等价类驱动的精确投影复用**：把 single Shiftmax 后的 gate code 与 binary K lane 组合为动态 multicast 目录，不做 token pruning。
2. **Head-stacked 循环重排与双窗口执行**：目录按输入 head 持久化一次，跨所有 output tile 重放，并使下一窗口 build 与当前窗口 replay 重叠。
3. **双格式无损稀疏表示**：在同一 head slot 内按运行时 gate-class overflow 选择目录或 direct 表示，保证任意输入 bit-exact。
4. **H67 workload 驱动的软硬件协同选择**：由真实 ordered trace 冻结 `S=4`、目录容量、context 深度和淘汰门槛，并用 full30/valid825 保证算法侧不因硬件近似退化。

其中第 2 条中的“双窗口”不能单独作为贡献；它必须与“head-stacked 最终门码目录跨 tile 重放”作为一个完整数据流主张。第 4 条是方法论和证据链，不替代架构贡献。

## 11. 实施顺序

1. 写完整 Python reference：覆盖多 head、所有 output tile、目录/direct 两种格式和 bias/requant。
2. 写完整 cycle model：按 stage/head/tile 和真实 ordered trace 分账。
3. RTL v1：单 context、多 head/tile、persistent accumulator、exact fallback。
4. RTL v2：双 context build/replay 重叠和 backpressure。
5. 回归：定向 overflow、随机 gate/K/weight/bias、随机 SRAM 延迟、随机 output stall。
6. 同约束对照：streaming direct、单 context GateStack、双 context GateStack。
7. 目标库 DC/SAIF/LEC；不过淘汰线则回退，不把模型上界写成芯片结果。

## 12. 当前结论

GateStack 比“异构双核”更贴合 H67 当前真实 workload：它直接利用 82.49% final-gate work-item 减少和极低 `S=4` overflow，同时避免复制 dense/sparse 双核。但架构新颖性仍是待验证命题，必须由完整 loop RTL、无损 fallback、ordered cycle replay 和同约束 PPA 对照共同成立。
