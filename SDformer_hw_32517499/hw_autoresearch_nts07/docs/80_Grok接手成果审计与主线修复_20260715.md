# Grok 接手成果审计与主线修复（2026-07-15）

## 1. 审计结论

Grok 接手期间完成的 profile100、pow2safe 旁路、规模 TB 和 CPU 分账工作大部分可继承，但证据范围必须重新分档：

| 项目 | 审计结论 | 可用于论文的表述 |
|---|---|---|
| H67/H68/TTX ordered profile100 | **接受** | 可作为 `[prof]` workload 证据 |
| H67 K-zero、pair empty、final-gate work 减少 | **接受** | 可直接用于架构动机，需绑定 profile 哈希 |
| `TOKENS=2^n` 截断修复 | **接受并已合入主线** | 可写工程正确性修复，不是创新点 |
| 31/31 PASS | **降级** | 只能称“G1 单 head/tile 切片回归” |
| 有效 `1.51x` | **降级** | 旧模型点，不是 RTL 或 ASIC 加速 |
| full-encoder 最优约 23 FPS | **保留为模型** | 不能声称真实吞吐或未达 30 FPS 的最终结论 |
| G1 已可直接 DC 发论文 | **否定** | 完整投影生命周期和目标库证据均未闭合 |

当前硬件主线仍锁为 **H67 + SCS + NMF/GateStack，`S=4`**。下一步不是继续堆单行核优化，而是把最终门码目录扩展为完整多 head、多 output-tile、无损 fallback、双窗口重叠的数据流架构。

H67 可用于架构决策的关键数据：

| 指标 | 数值 | 直接硬件含义 |
|---|---:|---|
| token K-zero | 88.6766% | 门控后 K 通道高度稀疏 |

这些数字证明“值得设计稀疏目录架构”，不自动证明“目录架构更快或更省电”。后者仍需 cycle replay、目标库综合和 SAIF。

## 3. 相序模型复核

新增 `scripts/audit_projection_phase_model.py`，统一使用 H67 ordered trace，对旧模型和候选重叠模型做敏感性复核。

| 口径 | 总周期 | 周期/输入 head 组 | 相对可流式 direct |
|---|---:|---:|---:|
| 旧 buffered direct | 470,098,134 | 699.55 | 不作为公平基线 |
| 旧 NMF，不计固定扫描 | 311,310,972 | 463.26 | 1.407x |
| 当前 G1 扫描下界 | 372,192,804 | 553.86 | **1.176x** |
| 可流式 direct | 437,880,204 | 651.61 | 1.000x |
| 双 context 候选 | 281,476,617 | 418.86 | **1.556x** |
| 三相全重叠乐观上界 | 172,612,617 | 256.86 | 2.537x |

旧 `1.510x` 可以复算，但它混用了 buffered direct 基线，并假定固定 `S × D = 128` 项目录扫描被完全吸收。当前平均 backend 仅约 137 周期，固定扫描与有效工作同量级，不能忽略。

上述表仍是 `[prof]+[模型]`：默认 product 与 multicast 理想重叠，未计 weight SRAM、跨 head/tile 切换、fallback、requant 和输出存储。因此论文主表不得把它标成 RTL speedup。

## 4. RTL 审计与已合入修复

### 4.1 Power-of-two 修复

主线 `rtl_hitflow/hitflow_banked_accumulator.sv` 已将：

```systemverilog
input_token < TOKEN_ID_W'(TOKENS)
```

改为：

```systemverilog
32'(input_token) < 32'(TOKENS)
```

根因是 `$clog2(TOKENS)` 位无法表示 `TOKENS` 本身；当 `TOKENS=2^n` 时，原常量截断为 0，导致 `update_ready` 永远为假。

### 4.2 主线规模回归

新增入口：`sim_hitflow/run_projection_g1_mainline_scale_checks.sh`。

| 配置 | 结果 | 三个用例周期 |
|---|:---:|---|
| accumulator `T=32` | PASS | 叶级自检 |
| top `T=32,L=8` | PASS | 189 / 557 / 277 |
| top `T=64,L=8` | PASS | 365 / 1069 / 511 |
| top `T=162,L=32` | PASS | 1385 / 10507 / 4043 |

三个顶层用例均满足 direct 与 NMF 整数结果一致且无 overflow。这里的 `T=162,L=32` 只是接口尺度覆盖，仍是单输入 head、单输出 tile。

### 4.3 31/31 回归的准确边界

Grok 的 31/31 包含 iverilog、Verilator、assert、Yosys 结构检查、Erie lint 和 Python reference，作为回归基础是有效的。但它不是 RTL skill 的最终签核：

1. Verilator 使用 `--Wno-fatal`，顶层仍有 `PINCONNECTEMPTY`、`WIDTHEXPAND` 和 unused 类 warning，尚未逐项修复或登记 waiver。
2. NMF fallback 的 payload 被顶层固定 ready 后丢弃，只设置 sticky overflow。
3. `term_input_channel` 只等于局部 lane，缺少 `head_id × 32` 全局偏移。
4. `term_output_tile` 固定为 0，没有 output-tile 循环。
5. 累加器每个 group 在单 head 后提交 bias/final，未跨全部输入 head 保持部分和。
6. bias 使用 `PRODUCT_W`，但软件契约仍要求独立冻结 bias/acc/requant 位宽。
7. Yosys `memory -nomap` 单元数不是目标工艺面积、时序或功耗。

因此 `memory/rtl-design/run_state.md` 已改为 `CONDITIONAL_PASS_SLICE_ONLY`。

## 5. DC/SAIF 环境审计

当前环境：

| 项 | 状态 |
|---|---|
| `dc_shell` | 不存在 |
| `genus` / `fc_shell` | 不存在 |
| ASIC `.db/.lib` 目标库 | 工作区未发现 |
| Yosys / Verilator | 可用 |
| SDC 探索目标 | 500 MHz、500000 um²、100 mW |

所以当前不能产出可发表的 DC 面积、WNS、SAIF 功耗或 LEC。可以先准备可移植 DC handoff，但所有 PPA 结果必须等用户提供目标库、corner、memory macro 模型和可用综合工具后再生成。

## 6. 当前准入门槛

进入真实 DC 前必须全部满足：

| 门槛 | 通过条件 |
|---|---|
| 数值语义 | Python 金参考与完整多 head/tile RTL bit-exact |
| fallback | 强制 overflow directed test，无 payload 丢失 |
| 生命周期 | 所有输入 head 累加完成后才提交 bias/final |
| 索引 | 全局 input channel 和所有 output tile 均有 coverage |
| 位宽 | gate、weight、product、bias、acc、requant 契约冻结 |
| 回归 | `T=162,D=32,H={3,6,12,24}`；随机 backpressure；无 fatal warning |
| 性能 | ordered trace cycle replay 相对可流式 direct 至少 1.20x，目标 1.40x |
| 存储 | stage3 双 context SRAM 不超过 160 KiB，不计 weight SRAM |
| 综合 | 目标库 WNS/TNS、面积、功耗和 LEC 齐全 |

若双 context 完整 RTL 在公平基线下低于 `1.20x`，GateStack 不再作为主架构贡献，只保留为门码压缩后端。

## 7. 下一步

1. 冻结 GateStack 完整 projection loop 和接口。
2. 先实现单 context 的多 head/tile + exact fallback，并跑 bit-exact。
3. 再加入双 context，使下一窗口 build 与当前窗口 replay/drain 重叠。
4. 用 ordered trace 驱动 RTL cycle replay，和 streaming direct 使用同一 SRAM/端口约束。
5. 最后进入目标库 DC/SAIF，而不是用 Yosys 单元数替代 PPA。
